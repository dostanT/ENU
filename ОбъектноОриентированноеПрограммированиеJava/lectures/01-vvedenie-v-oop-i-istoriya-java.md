Введение в ООП. Краткая история Java. Основы классов и объектов

Суть

Каждый день ты пользуешься программами на Java, даже не подозревая:
Minecraft (Java Edition) целиком написан на Java, у Netflix и Uber
на Java работает серверная часть, Android годами строился на Java.
Причина не случайна: Java спроектирована так, чтобы одна и та же
программа работала одинаково на Windows, macOS, Linux и Android, не
требуя переписывания под каждую систему. Эта лекция - про то, откуда
Java взялась, как она устроена изнутри (компилятор → байткод → виртуальная
машина), и про первый строительный блок любой Java-программы - класс и
объект.

Игра "угадай программу" - зачем вообще Java, а не просто C

Представь: на дворе начало 1990х, вокруг полно разных устройств -
телевизоры, приставки, стиральные машины - и у каждого свой процессор
и своя операционная система. Программа, написанная для одного
устройства, физически не запускалась на другом - нужно было
переписывать код под каждый отдельный процессор заново. Команда Green
Project в Sun Microsystems (Джеймс Гослинг, Патрик Нотон, Майк
Шеридан, 1991 год) решала именно эту задачу: как написать программу
ОДИН раз, чтобы она заработала на любом устройстве. Новый язык
назывался сначала Oak (в честь дуба за окном офиса), тестировался на
портативном контроллере Star7 (1992), и только когда команда поняла,
что та же идея "одна программа - много устройств" идеально ложится на
только что набирающий популярность интернет - язык переименовали в
Java (1995) и выпустили публично. Отсюда ключевая идея Java, которую
ты будешь видеть постоянно: "написано один раз - работает везде" (Write
Once, Run Anywhere, WORA).

Механизм - как одна программа работает на разных системах

Вот и разгадка игры выше: обычный компилятор (как в C) переводит код
сразу в машинный код КОНКРЕТНОГО процессора - поэтому программа для
одного процессора не запускается на другом. Java делает иначе, в два
шага:

Шаг 1 - компиляция. Компилятор javac переводит исходный код (файл
.java) не в машинный код конкретного процессора, а в промежуточный
байткод (файл .class) - универсальный набор инструкций, одинаковый для
всех систем.

Шаг 2 - выполнение. На каждой системе (Windows, macOS, Linux, Android)
стоит своя JVM (Java Virtual Machine, виртуальная машина Java) - именно
она понимает байткод и на лету переводит его в машинный код именно
этого процессора. Один и тот же файл .class, без единой перекомпиляции,
запускается JVM на любой из систем.

Отсюда и три термина, которые постоянно путают:
JDK (Java Development Kit) - полный набор для РАЗРАБОТКИ: включает
компилятор javac, отладчик, и саму JRE внутри. Нужен разработчику.
JRE (Java Runtime Environment) - окружение для ЗАПУСКА готовых программ:
включает JVM и стандартные библиотеки классов, но без компилятора.
Нужен конечному пользователю, который просто запускает готовую программу.
JVM (Java Virtual Machine) - "движок" внутри JRE, который реально
выполняет байткод. Пользователь с ней напрямую не взаимодействует, она
работает внутри JRE.

Пример - Hello World, весь цикл целиком

```java
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello World!");
    }
}
```

Обязательная структура: у каждой Java-программы есть класс (здесь
HelloWorld - контейнер для кода), метод main - это точка входа, именно
с него JVM начинает выполнение (сигнатура должна быть записана ровно
так: public static void main(String[] args)), и внутри main - операторы
(statements), каждый из которых заканчивается точкой с запятой. Имя
класса должно совпадать с именем файла (HelloWorld.java → класс
HelloWorld), иначе компилятор откажется собирать файл.

Реально собрано и запущено (javac + java, JDK 25 в этом окружении):

```
$ javac HelloWorld.java
$ java HelloWorld
Hello World!
```

javac переводит исходный код в HelloWorld.class (байткод), java
запускает JVM, которая этот байткод выполняет - см. "Механизм" выше,
здесь это тот же самый цикл, просто на реальной машине, а не на
диаграмме.

Класс и объект - основной строительный блок ООП

Объектно-ориентированное программирование (ООП) - это способ писать
программу как набор взаимодействующих объектов, а не как
последовательность команд подряд (это другой способ - императивный
стиль, см. "Java - язык с несколькими парадигмами" ниже). У каждого
объекта есть состояние (данные, которые он хранит) и поведение
(действия, которые он умеет выполнять).

Класс - это шаблон (чертёж), который описывает, какие данные (поля) и
какие действия (методы) будут у объектов этого типа. Сам класс памяти
не занимает - это просто описание. Объект - конкретный экземпляр класса,
создаётся оператором new, и у каждого объекта - собственные значения
полей, даже если класс один и тот же на всех.

Пример - класс Car (проверено, реально собрано и запущено)

```java
class Car {
    private String brand;
    private int year;

    public Car(String brand, int year) {
        this.brand = brand;
        this.year = year;
    }

    public void start() {
        System.out.println("The engine is started!");
    }
}

public class Main {
    public static void main(String[] args) {
        Car myCar = new Car("Toyota", 2020);
        myCar.start();
    }
}
```

Вывод (реально собрано и запущено, javac + java):

```
The engine is started!
```

Механизм по частям: brand и year - поля (state), они private, то есть
доступны только изнутри самого класса Car, не напрямую снаружи - это и
есть инкапсуляция, см. ниже. Car(String brand, int year) - конструктор,
специальный метод с именем как у класса, вызывается автоматически при
new Car(...) и заполняет поля нового объекта начальными значениями.
this внутри конструктора - ссылка на текущий, только что создаваемый
объект, нужна, чтобы отличить поле объекта (this.brand) от параметра
конструктора с тем же именем (brand). start() - метод (behavior) -
описывает, что объект умеет делать. myCar.start() - отправка сообщения
объекту myCar: вызвать его метод start().

Пример - класс Student с несколькими полями и методами (проверено)

```java
class Student {
    String name;
    int age;
    double gpa;

    Student(String name, int age, double gpa) {
        this.name = name;
        this.age = age;
        this.gpa = gpa;
    }

    void showInfo() {
        System.out.println("Name: " + name + ", Age: " + age + ", GPA: " + gpa);
    }

    void increaseGpa(double delta) {
        gpa += delta;
        if (gpa > 5.0) gpa = 5.0;
    }
}
```

Вызов `new Student("Anna", 20, 4.3)`, затем `showInfo()`, затем
`increaseGpa(0.2)`, затем снова `showInfo()` - реально собрано и
запущено, вывод:

```
Name: Anna, Age: 20, GPA: 4.3
Name: Anna, Age: 20, GPA: 4.5
```

Второй вызов showInfo() показывает GPA уже 4.5 - increaseGpa(0.2)
реально изменила состояние именно этого объекта (4.3+0.2=4.5), другие
объекты Student, если бы они были, эта операция не затронула бы - у
каждого объекта своё, независимое состояние.

Три принципа ООП

Инкапсуляция - объединить данные и методы внутри класса и спрятать
внутреннее устройство от внешнего кода. Пример - BankAccount ниже: поле
balance приватное, снаружи к нему нельзя обратиться напрямую
(myAccount.balance - ошибка компиляции), только через методы deposit()
и getBalance() - а внутри deposit() ещё и стоит проверка (amount > 0),
которую невозможно обойти, если менять баланс только через этот метод.

```java
class BankAccount {
    private double balance;

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public double getBalance() {
        return balance;
    }
}
```

Реально собрано и запущено: после `deposit(100)` и `deposit(50)`,
`getBalance()` возвращает 150.0 - ровно сумму двух пополнений, и нет
способа обойти проверку amount>0 и напрямую испортить баланс отрицательным
числом, раз поле закрыто.

Наследование - один класс (подкласс) перенимает поля и методы другого
класса (суперкласса) и может их расширить или переопределить. Смысл -
переиспользовать код и выразить отношение "является разновидностью"
(dog "is a" animal).

Полиморфизм - один и тот же метод по имени работает по-разному в
разных классах-наследниках, и какая именно версия выполнится -
определяется реальным типом объекта в момент вызова, а не типом
переменной, в которой он лежит.

Пример - наследование и полиморфизм вместе (проверено)

```java
class Animal {
    void speak() { System.out.println("Some sound"); }
}

class Dog extends Animal {
    @Override
    void speak() { System.out.println("Woof!"); }
}

class Cat extends Animal {
    @Override
    void speak() { System.out.println("Meow!"); }
}
```

Вызов:
```java
Animal a1 = new Dog();
Animal a2 = new Cat();
a1.speak();
a2.speak();
```

Реально собрано и запущено, вывод:

```
Woof!
Meow!
```

Обе переменные объявлены одним и тем же типом Animal, но выводят
разное - потому что реально внутри a1 лежит объект Dog, а внутри a2 -
объект Cat, и вызов a1.speak() смотрит не на тип переменной (Animal), а
на то, каким классом реально создан объект. Это и есть полиморфизм: код
`a.speak()` можно написать один раз и использовать для любого потомка
Animal, а результат будет автоматически правильным для каждого
конкретного случая.

Java - язык с несколькими парадигмами (ООП и функциональный стиль)

Парадигма программирования - это набор базовых идей о том, как делить
задачу на части и как эти части должны взаимодействовать. Java
исторически построена вокруг ООП (потому исторически её и изучают
первой), но начиная с Java 8 полноценно поддерживает ещё и
функциональный стиль (FP) через лямбда-выражения и Stream API.

Разница на одной и той же задаче - сложить числа массива:

Императивный/ООП стиль (шаг за шагом, с явным изменением состояния):
```java
int sum = 0;
for (int x : arr) {
    sum += x;
}
```

Функциональный стиль (описываем ЧТО хотим получить, а не КАК именно
это сделать по шагам):
```java
int sum = Arrays.stream(arr).sum();
```

Главная идея FP - функции не меняют данные, а создают новые значения
(immutability, неизменяемость), и одна и та же функция при одних и тех
же входных данных всегда возвращает один и тот же результат (чистые
функции, pure functions) - от этого код становится проще тестировать и
безопаснее распараллеливать.

Пример - обычная функция и Stream API (проверено, реально собрано и запущено)

```java
static int add(int a, int b) {
    return a + b;
}
```
```java
int result = add(3, 5);

List<Integer> list = List.of(1, 2, 3);
List<Integer> doubled = list.stream()
        .map(n -> n * 2)
        .toList();

int sum = Arrays.stream(new int[]{1, 2, 3, 4}).sum();
```

Вывод:
```
add(3, 5) = 8
doubled: [2, 4, 6]
sum: 10
```

map(n -> n * 2) - лямбда-выражение (короткая запись функции без имени):
для каждого элемента исходного списка возвращает его же, умноженный на
2, и .toList() собирает результат в новый список, НЕ изменяя исходный
list - это и есть иммутабельность на практике: list после этого кода
всё ещё [1, 2, 3], а doubled - отдельный, новый список [2, 4, 6].

ООП и FP - не взаимоисключающие лагеря, а два инструмента: ООП обычно
удобнее для крупных систем с явным состоянием (игры, приложения с
интерфейсом), FP - для обработки данных и вычислений, где важна
предсказуемость и параллелизм. Java 8+ поддерживает оба стиля
одновременно, и выбор - по задаче, а не идеология.

Ввод и вывод в консоли - System.out и Scanner

System.out.println(...) - вывод строки с переводом строки в конце,
System.out.print(...) - то же самое, но без перевода строки. Для ввода
от пользователя нужен класс Scanner: nextLine() читает строку целиком,
nextInt() - целое число, nextDouble() - дробное. После работы со
Scanner его принято закрывать через close().

Пример (проверено, ввод подан программно вместо реальной клавиатуры):

```java
import java.util.Scanner;

public class ScannerDemo {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        System.out.print("Enter your name: ");
        String name = sc.nextLine();
        System.out.print("Enter your age: ");
        int age = sc.nextInt();
        System.out.println("Hello, " + name + "! You are " + age + " years old.");
        sc.close();
    }
}
```

Реально собрано и запущено (вход "Anna", затем "20"):

```
Enter your name: Enter your age: Hello, Anna! You are 20 years old.
```

Приглашения "Enter your name:"/"Enter your age:" оказались склеены в
одну строку без переноса - это ожидаемо и не ошибка: print() (в отличие
от println()) не добавляет перевод строки сам, а ввод в этом прогоне
шёл не с настоящей клавиатуры, а заранее заготовленным текстом, без
пауз между вводом пользователя и следующим print().

Инструменты разработки (коротко, без проверки - это факты про
инструменты, а не код)

IDE (интегрированная среда разработки) - программа, которая помогает
писать, запускать и отлаживать код в одном месте: подсветка синтаксиса,
автодополнение, встроенный компилятор/отладчик. Три популярных варианта
для Java: IntelliJ IDEA (самый "умный", стандарт для профессиональной
разработки), Eclipse (бесплатный, лёгкий, хорош для обучения), VS Code
(нужен отдельно поставить расширение для Java, быстрый и универсальный
редактор). Java-проект обычно организован в стандартную структуру папок:
код лежит в src/, внутри - пакеты (package, группируют классы по смыслу,
например com.example), а сами классы - в .java файлах внутри пакета.

Частые путаницы и ошибки

Путают JDK, JRE и JVM - JDK включает в себя JRE (плюс инструменты
разработки вроде javac), JRE включает в себя JVM (плюс стандартные
библиотеки). Для разработки нужен JDK, для простого запуска готовой
программы формально хватило бы JRE (хотя на практике почти всегда
ставят сразу JDK).

Путают класс и объект - класс не занимает памяти и не может ничего
"делать" сам по себе, это только описание/шаблон. Объект - то, что
реально создано оператором new и занимает память, и именно у объекта,
а не у класса, есть конкретные значения полей.

Забывают, что имя класса и имя файла должны совпадать (с учётом
регистра) для public-класса - иначе javac откажется компилировать файл.

Путают инкапсуляцию с "просто сокрытием данных ради сокрытия" - смысл
не спрятать данные вообще, а не дать менять их в обход проверок класса
(см. пример с BankAccount выше: deposit() проверяет amount>0, а прямая
запись в приватное поле снаружи в принципе невозможна).

Думают, что полиморфизм - это про переменную. На самом деле, какая
версия метода выполнится, решает реальный тип ОБЪЕКТА в памяти (Dog
или Cat), а не тип, которым объявлена переменная (Animal) - см. пример
выше.

Считают Java чисто объектно-ориентированным языком без исключений. С
Java 8 в языке полноценно живёт функциональный стиль (лямбды, Stream
API) - выбор между императивным/ООП и функциональным стилем зависит от
задачи, а не является жёстким правилом языка.
