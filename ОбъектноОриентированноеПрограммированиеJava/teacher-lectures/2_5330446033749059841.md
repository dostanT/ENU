# demo

A small Spring Boot task-list API, built one Git commit per tutoring
week. Each commit adds exactly one concept on top of the last, so you
can follow the whole course by reading the commits in order.

Scaffolded from [start.spring.io](https://start.spring.io) (same as
https://spring.io/quickstart), Maven, Java 17, Spring Boot 4.1.1.

## How to use this repo in class

Walk through the commits one at a time instead of reading the
finished code straight away - each one is small enough to read top
to bottom, and the commit message explains *why*, not just *what*.

```
git log --oneline                 # see all 13 commits
git show <commit>                 # see exactly what that week changed
git checkout <commit>             # check the project out as it stood that week
git checkout main                 # back to the finished project
```

## Running it

```
./mvnw spring-boot:run             # start the app on http://localhost:8080
./mvnw test                        # run the tests from Week 13
```

## File-by-file breakdown

Grouped by architectural layer rather than by week, mapped to the
Spring concept each file exists to demonstrate.

### Entry point

- **`DemoApplication.java`** — `@SpringBootApplication` is three
  annotations in one (`@Configuration`, `@EnableAutoConfiguration`,
  `@ComponentScan`). The `main` method hands control to
  `SpringApplication.run`, which starts the embedded Tomcat server,
  scans `com.example.demo` for Spring-managed beans, and wires
  everything together — this one file is the whole bootstrap.

### Controllers — web layer

- **`HelloController.java`** — the smallest possible controller:
  `@RestController` + a single `@GetMapping("/hello")` returning a
  plain `String`. No model, no service, no persistence — isolates
  "how does Spring turn an HTTP GET into a method call" before any
  other concept is introduced.
- **`TaskController.java`** — the real resource controller.
  `@RequestMapping("/api/tasks")` at the class level sets a shared
  base path; each method adds `@GetMapping`/`@PostMapping`/
  `@PutMapping`/`@DeleteMapping` on top of it. `TaskService` is
  injected through the constructor (no `@Autowired` needed — Spring
  auto-wires the sole constructor). `@PathVariable` pulls `{id}` out
  of the URL, `@RequestBody` deserializes incoming JSON into a `Task`,
  and `@Valid` tells Spring to run Bean Validation on that `Task`
  before the method body runs. `deleteTask` returns
  `ResponseEntity<Void>` with `.noContent().build()` to produce a
  204 with no body — showing that a controller method's return type
  controls the HTTP response, not just the JSON payload.

### Model — domain object and JPA entity in one

- **`Task.java`** — starts as a plain POJO (fields + getters/setters)
  and later gains `@Entity`, `@Id`, and
  `@GeneratedValue(strategy = GenerationType.IDENTITY)` to become a
  JPA-managed table row, plus `@NotBlank` so the same class doubles
  as the Bean Validation target for `@Valid` in the controller. One
  class playing three roles (JSON shape, validation target, DB row)
  is a deliberate simplification for teaching — production code would
  usually split these.

### Repository — data access layer

- **`TaskRepository.java`** — an empty interface that extends
  `JpaRepository<Task, Long>`. There's no implementation anywhere in
  the codebase; Spring Data JPA generates one at runtime (a dynamic
  proxy) that already supports `findAll`, `findById`, `save`,
  `delete`, paging, and sorting. This is the single clearest example
  in the repo of Spring doing work you never write.

### Service — business logic layer

- **`TaskService.java`** — `@Service` marks it as a Spring-managed
  bean; the constructor takes `TaskRepository`, keeping persistence
  out of the controller. `findById` turns JPA's `Optional<Task>` into
  either a `Task` or a thrown `TaskNotFoundException` via
  `.orElseThrow(...)`, so the controller never has to think about
  "what if it's missing." `update` copies fields onto the existing
  entity rather than replacing it outright, which is why only
  `title`/`done` change and the original `id` and JPA identity are
  preserved.

### Exception handling — cross-cutting concern

- **`TaskNotFoundException.java`** — a plain `RuntimeException`
  subclass; nothing Spring-specific about it, which is itself the
  point — your domain exceptions don't need to know about HTTP.
- **`GlobalExceptionHandler.java`** — `@RestControllerAdvice` applies
  to every controller in the app. One `@ExceptionHandler` catches
  `TaskNotFoundException` and turns it into a 404 with a JSON error
  body; the other catches `MethodArgumentNotValidException` — the
  exception Spring throws automatically when `@Valid` fails — and
  turns it into a 400 with a field-name → message map. This is what
  keeps `TaskController` free of any try/catch blocks: exceptions
  thrown deep in the service layer are translated into HTTP responses
  in exactly one place.

### Configuration and seed data

- **`application.properties`** — points `spring.datasource.url` at a
  *named* in-memory H2 database (`jdbc:h2:mem:demodb`) instead of a
  randomly-named one, so the H2 console can reconnect to it; enables
  that console at `/h2-console`; and sets
  `spring.jpa.defer-datasource-initialization=true` so Hibernate
  creates the tables from `@Entity` classes *before* `data.sql` tries
  to insert into them — ordering that trips people up the first time
  they add seed data to a JPA project.
- **`data.sql`** — two `INSERT` statements. Spring Boot runs any
  `data.sql` on the classpath automatically after schema creation —
  no code required, just the file being in the right place.

### Tests

- **`DemoApplicationTests.java`** — a single empty `@Test` method
  under `@SpringBootTest`. It asserts nothing explicitly; if the
  Spring application context fails to start (a missing bean, a
  misconfigured property), this test fails. It's a smoke test for
  wiring, not behavior.
- **`TaskControllerTests.java`** — `@SpringBootTest` +
  `@AutoConfigureMockMvc` boots the full application context and
  gives you `MockMvc` to fire simulated HTTP requests at it without a
  real server or port; `@Transactional` rolls back any database
  changes after each test so they don't leak into one another. The
  four tests exercise the stack end to end: listing seeded tasks,
  creating one successfully, creating one with a blank title (checks
  the validation path lands in `GlobalExceptionHandler`), and
  fetching a nonexistent id (checks the `TaskNotFoundException` path).
  This is where every earlier concept — persistence, validation,
  exception handling — gets verified together instead of in
  isolation.

## API reference (as of Week 13)

| Method | Path              | Body                          | Notes                       |
|--------|-------------------|--------------------------------|------------------------------|
| GET    | `/hello`          | -                               | From Week 2, plain text      |
| GET    | `/api/tasks`      | -                               | List all tasks               |
| GET    | `/api/tasks/{id}` | -                               | 404 if not found             |
| POST   | `/api/tasks`      | `{"title": "...", "done": false}` | 400 if `title` is blank    |
| PUT    | `/api/tasks/{id}` | `{"title": "...", "done": false}` | 404 if not found           |
| DELETE | `/api/tasks/{id}` | -                               | 404 if not found, else 204   |

H2 console (Week 12): http://localhost:8080/h2-console, JDBC URL
`jdbc:h2:mem:demodb`, user `sa`, empty password.
