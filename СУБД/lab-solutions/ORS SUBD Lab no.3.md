Microsoft SQL Server. Лабораторная 3. Выборка данных

Суть лабы и как она проверена

В отличие от лаб 1 и 2, здесь весь код - обычный, переносимый SQL
(SELECT/WHERE/ORDER BY/LIKE/IN/IS NULL/BETWEEN), а не T-SQL-специфика
вроде хранимых процедур или системных функций. Только сами таблицы
AdventureWorks2008 (Person.CountryRegion, Person.Person,
Production.Product, HumanResources.vEmployee и т.д.) в этом окружении
недоступны. Поэтому: T-SQL-код ниже - основной, ровно в том синтаксисе,
что нужен на реальном MS SQL Server (конкатенация через `+`,
`[Name]` в квадратных скобках, `Substring`, `CONVERT`). Но логику
каждого запроса реально проверил - собрал маленькие таблицы с теми же
именами столбцов и парой представительных строк и прогнал ту же логику
через sqlite3 (там конкатенация через `||`, а не `+`, и функция
называется `substr`, а не `Substring` - это чисто синтаксические
различия диалектов, не разница в сути запроса). Где задача зависит от
реальных прав пользователя на сервере - это отдельно помечено как
непроверяемое, как и в лабе 2.

Задание 2. Список стран с кодом и датой последнего изменения записи

Механизм (код дан в задании): `Person.CountryRegion` - имя таблицы с
префиксом схемы `Person` (схема - это просто пространство имён внутри
базы, группирует таблицы по смыслу; в AdventureWorks2008 схема Person
отвечает за сотрудников и подразделения). `[Name]` - в квадратных
скобках, потому что `Name` - зарезервированное или потенциально
неоднозначное слово для T-SQL, скобки говорят "это имя столбца, не
ключевое слово". `AS` переименовывает столбец в выводе (алиас) - не
меняет данные, только подпись в результате.

```sql
SELECT CountryRegionCode AS 'Code', [Name] AS 'Country',
       ModifiedDate AS 'Modified Date'
FROM Person.CountryRegion
```

Проверено (sqlite3, макет таблицы с 4 строками - US/CA/GB/DE): запрос
возвращает все страны с переименованными столбцами Code/Country/Modified
Date, ничего не потеряно и не задвоено.

Задание 3. Фамилия + первая буква имени + идентификатор, отсортировано

Механизм (код дан в задании): `LastName+' '+Substring(FirstName,1,1)+'.'`
- в T-SQL строки складываются оператором `+` (не специальным оператором
конкатенации, как в некоторых других диалектах). `Substring(FirstName,
1, 1)` берёт из FirstName подстроку длиной 1 символ, начиная с позиции
1 (T-SQL, как и большинство SQL-диалектов, считает позиции в строке с
1, а не с 0). Получившийся псевдоним `[Employee Name]` (через AS) тут
же используется в ORDER BY - раз алиас задан, можно сортировать прямо
по нему, а не переписывать заново всё выражение.

```sql
SELECT LastName+' '+Substring(FirstName,1,1)+'.' as [Employee Name], BusinessEntityID
FROM Person.Person
ORDER BY [Employee Name]
```

Проверено (sqlite3: `LastName || ' ' || substr(FirstName,1,1) || '.'`,
макет из 4 сотрудников): результат отсортирован по фамилии+инициалу
корректно (Duffy T., Sanchez K., Tamburello R., Walters R.) - по
умолчанию ORDER BY сортирует по возрастанию (ASC можно не писать явно,
для убывания нужен DESC).

Задание 4. Товары с ценой от $12 до $20, отсортированные по цене

Механизм (два равнозначных варианта из задания): первый - обычное
логическое И двух сравнений; второй - оператор `BETWEEN a AND b`,
который делает ровно то же самое (включая ОБЕ границы диапазона), но
короче и читаемее. `ORDER BY 2` в первом варианте - сортировка по
НОМЕРУ столбца в SELECT (2-й столбец - ListPrice), а не по имени; так
можно, но менее наглядно, чем явно написать `ORDER BY ListPrice`, как
во втором варианте.

```sql
SELECT [Name], ListPrice From Production.Product
WHERE (ListPrice>=12) and (ListPrice<=20)
ORDER BY 2
```
```sql
SELECT [Name], ListPrice From Production.Product
WHERE ListPrice Between 12 and 20
ORDER BY ListPrice
```

Проверено (sqlite3, макет из 6 товаров с разными ценами): оба варианта
дают ОДИНАКОВЫЙ результат - Mountain Bottle Cage (12.99), Road Bottle
Cage (14.99), Patch Kit (19.99), по возрастанию цены - подтверждает, что
BETWEEN и двойное сравнение действительно взаимозаменяемы, границы 12
и 20 включаются в обоих случаях.

Задание 5. Сотрудники и должности вне США

Механизм (код дан в задании): `LIKE` ищет текст по шаблону, а не по
точному совпадению; `%` в шаблоне означает "любые 0 или более
символов в этом месте". `NOT LIKE '%United States%'` - шаблон "где-то
внутри строки встречается 'United States'", а `NOT` перед LIKE
инвертирует условие - берём тех, у кого этой подстроки НЕТ.

```sql
Select LastName, JobTitle From HumanResources.vEmployee
Where CountryRegionName Not Like '%United States%'
```

Проверено (sqlite3, макет vEmployee из 4 записей - 2 из США, 1 из
Канады, 1 из Британии): результат - ровно двое не из США (Канада,
Британия), оба сотрудника из США корректно исключены.

Задание 6. Сотрудники из США и Канады

Механизм (код дан в задании): `IN (список значений)` проверяет
принадлежность списку - по сути сокращённая запись для цепочки условий
через OR (`CountryRegionName = 'United States' OR CountryRegionName =
'Canada'`), но короче и быстрее читается, особенно если значений в
списке много.

```sql
Select LastName, JobTitle From HumanResources.vEmployee
WHERE CountryRegionName IN ('United States', 'Canada')
```

Проверено (sqlite3, тот же макет): результат - все трое из США и
Канады, сотрудник из Британии корректно исключён.

Задание 7. Товары без указанного цвета

Механизм (код дан в задании): отсутствие значения (NULL) - это не
пустая строка и не 0, это специальное состояние "значение неизвестно
или не задано", и сравнивать его через `= NULL` не получится (такое
сравнение в SQL всегда даёт "неизвестно", а не истину) - для проверки
именно на отсутствие значения есть отдельный оператор `IS NULL`.

```sql
SELECT [Name] FROM Production.Product WHERE Color IS NULL
```

Проверено (sqlite3, тот же макет из 6 товаров, у 2 из них Color не
задан): результат - ровно те два товара (Mountain Bottle Cage, Patch
Kit), у которых Color действительно NULL.

Самостоятельная работа

1. Способы доставки (ShipMethod), если есть право на чтение

Механизм: тот же приём, что в lab-solutions/ORS SUBD Lab no.2.md,
Task 2 - проверка нулевого бита маски PERMISSIONS перед тем, как
показывать сами данные.

```sql
IF PERMISSIONS(OBJECT_ID('Purchasing.ShipMethod')) & 1 = 1
    SELECT * FROM Purchasing.ShipMethod
ELSE
    PRINT 'No selection rights'
```

Не проверено выполнением: зависит от реальных прав текущего
пользователя на сервере - см. то же ограничение в лабе 2.

2. Список сотрудников: EmployeeID, дата рождения в формате dd.mm.yyyy, возраст на сегодня

Механизм: `CONVERT(VARCHAR, BirthDate, 104)` - код стиля 104 в T-SQL
означает именно формат "день.месяц.год" (у CONVERT для дат есть
таблица числовых кодов стиля вывода, 104 - "немецкий" формат с
точками). Возраст - не просто разница годов: `DATEDIFF(YEAR,
BirthDate, GETDATE())` считает разницу КАЛЕНДАРНЫХ годов (2026 минус
год рождения), не полных прожитых лет - если день рождения в этом году
ещё не наступил, полных лет на самом деле на один меньше. Поэтому нужна
поправка: если месяц/день рождения ещё впереди по сравнению с
сегодняшними месяцем/днём - вычесть 1.

```sql
SELECT EmployeeID,
       CONVERT(VARCHAR, BirthDate, 104) AS BirthDateFormatted,
       DATEDIFF(YEAR, BirthDate, GETDATE())
       - CASE WHEN (MONTH(BirthDate) > MONTH(GETDATE()))
                 OR (MONTH(BirthDate) = MONTH(GETDATE()) AND DAY(BirthDate) > DAY(GETDATE()))
              THEN 1 ELSE 0 END AS Age
FROM HumanResources.Employee
```

Проверено (sqlite3, та же логика поправки на ещё-не-наступивший день
рождения, макет из 3 сотрудников, дата "сегодня" - 17.09.2026):
1969-01-29 -> 29.01.1969, возраст 57 (день рождения в январе уже
прошёл); 1971-08-01 -> 01.08.1971, возраст 55 (август уже прошёл);
1974-11-12 -> 12.11.1974, возраст 51, а не 52 (ноябрь ещё впереди -
поправка сработала правильно).

3. Снятые с производства товары (SellEndDate) с указанием цвета

Механизм: `SellEndDate IS NOT NULL` - обратная проверка к заданию 7:
если дата окончания продаж ЗАДАНА (не NULL), значит товар уже сняли с
производства.

```sql
SELECT [Name], Color FROM Production.Product WHERE SellEndDate IS NOT NULL
```

Проверено (sqlite3, тот же макет товаров, у одного из шести задан
SellEndDate): результат - ровно этот один товар (Patch Kit), с его
цветом (в данном случае тоже NULL - у товара не указан ни цвет, ни
актуальность продажи, это разные независимые поля).

4. Места хранения (Production.Location), содержащие 'Paint' в названии

Механизм: `LIKE '%Paint%'` - шаблон "где угодно в строке встречается
Paint" (в отличие от заданий 5-6, здесь ищем совпадение, а не его
отсутствие).

```sql
SELECT [Name] FROM Production.Location WHERE [Name] LIKE '%Paint%'
```

Проверено (sqlite3, макет из 5 мест хранения): результат - "Paint" и
"Paint Shop", остальные три места (Tool Crib, Sheet Metal Racks, Frame
Forming) корректно не попали в выборку.

5. Страны, где зарегистрированы клиенты (из представления vIndividualCustomer)

Механизм: задание прямо объясняет, почему нужно представление
(view), а не таблица напрямую - у обычной таблицы клиентов недостаточно
данных для такого запроса (страна клиента там не хранится впрямую, это
требует соединения нескольких таблиц - адрес, регион и т.д., что уже
сделано один раз внутри самого представления vIndividualCustomer,
и не нужно повторять вручную). `DISTINCT` - убирает повторяющиеся
значения, раз нужен именно список стран, а не одна строка на каждого
клиента.

```sql
SELECT DISTINCT CountryRegionName FROM Sales.vIndividualCustomer
```

Проверено (sqlite3, макет из 5 клиентов, среди них дважды 'United
States'): результат - 4 уникальные страны (United States один раз,
хотя в исходных данных клиентов из США двое) - DISTINCT действительно
убирает дубликаты.
