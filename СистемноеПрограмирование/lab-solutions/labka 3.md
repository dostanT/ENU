числа Фибоначчи, второй простые числа, оба выводят результат на экран,
после остановки показать, сколько чисел каждого вида нашли.

Теория - четыре механизма синхронизации, коротко

По книге, глава 6, "Синхронизация потоков в Windows" (Побегайло,
стр. 109-143):

Critical Section - не объект ядра ОС, живёт только внутри одного
процесса. Быстрее остальных трёх, потому что вход/выход не требует
переключения из пользовательского режима в режим ядра (6.1, стр. 115).
Функции: InitializeCriticalSection, EnterCriticalSection,
LeaveCriticalSection, DeleteCriticalSection.

Мьютекс - объект ядра, поэтому работает и между процессами, не только
между потоками одного процесса. Медленнее критической секции именно
из-за этого переключения режима. Функции: CreateMutex,
WaitForSingleObject (захват), ReleaseMutex (освобождение), CloseHandle.

Событие - объект ядра для оповещения: один поток сигналит, другие ждут
через функции ожидания. Бывает с ручным сбросом (снимается только
вызовом ResetEvent, все ждущие потоки освобождаются разом) и с
автоматическим сбросом (снимается сам после того как один ждущий поток
освободился - см. 6.4, стр. 128). Функции: CreateEvent, SetEvent,
ResetEvent, WaitForSingleObject.

Семафор - тоже объект ядра, но в отличие от мьютекса пускает не одного,
а до N потоков одновременно (N задаётся при создании как
lMaximumCount). Функции: CreateSemaphore, WaitForSingleObject,
ReleaseSemaphore.

Итог по варианту 10: критическая секция - лучший выбор для защиты вывода
внутри одного процесса (быстрее); мьютекс и бинарный семафор решают ту же
задачу, но медленнее и без выигрыша; событие с ручным сбросом - естественный
сигнал остановки для нескольких потоков одновременно; событие с автосбросом
требует по одному событию на поток.

Контрольные вопросы

Что такое поток? Чем он отличается от процесса? - поток - это
последовательность выполняемых команд внутри процесса со своим стеком и
контекстом (регистры, программный счётчик), но общими с другими
потоками того же процесса адресным пространством и ресурсами
(подробно - lectures/02-potoki-i-processy.md). Процесс - это отдельное
адресное пространство и владелец ресурсов, внутри которого работает как
минимум один поток. Главное отличие: несколько потоков одного процесса
делят память между собой напрямую (поэтому и нужна синхронизация из
этой лабы), а два разных процесса по умолчанию друг у друга в памяти не
роются.

Что такое критическая секция и чем она отличается от мьютекса? -
критическая секция - объект взаимного исключения, который не является
объектом ядра ОС и работает только внутри одного процесса; мьютекс -
тоже объект взаимного исключения, но уже объект ядра, поэтому доступен
из разных процессов. Из-за того что критическая секция не требует
обращения к ядру, она быстрее мьютекса (см. выше и стр. 115 книги).

Как работает событие auto-reset и manual-reset? - у события с ручным
сбросом (manual-reset) сигнальное состояние снимается только явным
вызовом ResetEvent - если его не сбросить, оно остаётся сигнальным
сколько угодно и пропускает через себя всех, кто его ждёт. У события с
автоматическим сбросом (auto-reset) сигнальное состояние снимается само
сразу после того, как ОДИН ждущий поток освободился по этому событию
(функция ожидания сама вызывает эквивалент ResetEvent) - остальные
ждущие потоки остаются ждать дальше. Manual-reset подходит для "открыть
дорогу всем", auto-reset - для "пропустить ровно одного".

Как с помощью WaitForMultipleObjects дождаться завершения нескольких
потоков? - передать в lpHandles массив дескрипторов потоков, в nCount -
их количество, bWaitAll выставить в TRUE (ждать, пока ВСЕ объекты не
станут сигнальными - дескриптор потока становится сигнальным, когда
поток завершается), dwMilliseconds - INFINITE, если не нужно
ограничение по времени. Именно так это сделано в варианте 10-А:
WaitForMultipleObjects(2, hThreads, TRUE, INFINITE).

Что произойдет, если не вызвать CloseHandle для мьютекса/семафора? -
дескриптор объекта ядра не освободится, пока процесс не завершится сам
(ОС сама закрывает все оставшиеся дескрипторы процесса при его
завершении) - до этого момента объект продолжает занимать системные
ресурсы. Если такое повторяется много раз за время жизни долгоживущего
процесса (например каждый раз при создании нового мьютекса в цикле без
закрытия) - это утечка ресурсов, и рано или поздно процесс упрётся в
лимит дескрипторов.

Почему критическая секция быстрее мьютекса? - потому что мьютекс -
объект ядра ОС, и любое обращение к нему (захват, освобождение)
требует переключения потока из пользовательского режима в защищённый
режим ядра и обратно - это дорогая операция. Критическая секция не
является объектом ядра, поэтому обходится без этого переключения в
подавляющем большинстве случаев (стр. 115 книги).

В каких случаях стоит использовать семафор, а не мьютекс? - когда
разрешённое количество потоков, работающих с ресурсом ОДНОВРЕМЕННО,
больше одного, но всё равно ограничено. Мьютекс - это по сути семафор с
максимальным значением 1 (пропускает ровно одного). Семафор нужен,
например, для пула из N одинаковых ограниченных ресурсов (N соединений
с сервером, N слотов буфера) - до N потоков работают параллельно, а
(N+1)-й ждёт, пока кто-то не освободит слот.

1. Критическая секция - гонка на общем счётчике

Механизм: два потока миллион раз подряд увеличивают одну и ту же
переменную. Без защиты часть увеличений теряется (оба потока успевают
прочитать одно и то же старое значение до того как кто-то из них
запишет новое) - результат будет меньше 2000000 и от запуска к запуску
разным. С критической секцией вокруг ++counter - результат всегда
ровно 2000000.

```c
#include <windows.h>
#include <iostream.h>

CRITICAL_SECTION cs;
long counter = 0;

DWORD WINAPI Worker(LPVOID lpParam)
{
    for (int i = 0; i < 1000000; ++i)
    {
        EnterCriticalSection(&cs);
        ++counter;
        LeaveCriticalSection(&cs);
    }
    return 0;
}

int main()
{
    HANDLE hThreads[2];
    DWORD dwId;

    InitializeCriticalSection(&cs);

    hThreads[0] = CreateThread(NULL, 0, Worker, NULL, 0, &dwId);
    hThreads[1] = CreateThread(NULL, 0, Worker, NULL, 0, &dwId);
    if (hThreads[0] == NULL || hThreads[1] == NULL)
        return GetLastError();

    WaitForMultipleObjects(2, hThreads, TRUE, INFINITE);

    cout << "Итог: " << counter << " (ожидалось 2000000)" << endl;

    CloseHandle(hThreads[0]);
    CloseHandle(hThreads[1]);
    DeleteCriticalSection(&cs);
    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows/MSVC в этом окружении) -
проверено по логике API, не запуском. Без
EnterCriticalSection/LeaveCriticalSection вокруг ++counter итог на
любой машине выходит заметно меньше 2000000 и разным от запуска к
запуску - в этом и есть гонка данных, о которой предупреждает теория.

2. Мьютекс - та же гонка, другой Win32-примитив

Механизм: ровно та же задача, что и в демо 1, но вместо CRITICAL_SECTION
- объект ядра mutex: WaitForSingleObject вместо EnterCriticalSection,
ReleaseMutex вместо LeaveCriticalSection. Результат тот же самый (2000000
без потерь), но медленнее, потому что каждый захват/освобождение - это
обращение к объекту ядра, а не к обычной памяти процесса (см. lectures/06,
"Критические секции").

```c
#include <windows.h>
#include <iostream.h>

HANDLE hMutex;
long counter = 0;

DWORD WINAPI Worker(LPVOID lpParam)
{
    for (int i = 0; i < 1000000; ++i)
    {
        WaitForSingleObject(hMutex, INFINITE);
        ++counter;
        ReleaseMutex(hMutex);
    }
    return 0;
}

int main()
{
    HANDLE hThreads[2];
    DWORD dwId;

    hMutex = CreateMutex(NULL, FALSE, NULL);
    if (hMutex == NULL)
        return GetLastError();

    hThreads[0] = CreateThread(NULL, 0, Worker, NULL, 0, &dwId);
    hThreads[1] = CreateThread(NULL, 0, Worker, NULL, 0, &dwId);
    if (hThreads[0] == NULL || hThreads[1] == NULL)
        return GetLastError();

    WaitForMultipleObjects(2, hThreads, TRUE, INFINITE);

    cout << "Итог: " << counter << " (ожидалось 2000000)" << endl;

    CloseHandle(hThreads[0]);
    CloseHandle(hThreads[1]);
    CloseHandle(hMutex);
    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows/MSVC в этом окружении) -
проверено по логике API, не запуском. Результат по логике тот же, что
и в демо 1 (итог ровно 2000000 без потерь) - разница между
критической секцией и мьютексом здесь только в цене вызова (обращение
к объекту ядра у мьютекса дороже), не в итоговой корректности.

3. Событие - дождаться сигнала о готовности (блокируясь, не опрашивая)

Механизм: главный поток должен продолжить только после того, как
рабочий поток закончит "долгую работу". В отличие от варианта 10-А (labka 3 - 10а.md)
(где поток каждые 150мс САМ ПРОВЕРЯЛ, не пришёл ли сигнал остановки -
это опрос), здесь главный поток просто блокируется на
WaitForSingleObject(hEvent, INFINITE) и не тратит процессорное время
вообще, пока не придёт SetEvent - это и есть настоящее "условие" из
lectures/05, а не активное ожидание.

```c
#include <windows.h>
#include <iostream.h>

HANDLE hDoneEvent;

DWORD WINAPI Worker(LPVOID lpParam)
{
    cout << "Рабочий поток: начал длинную работу..." << endl;
    Sleep(1000);
    cout << "Рабочий поток: работа готова, сигналю." << endl;
    SetEvent(hDoneEvent);
    return 0;
}

int main()
{
    HANDLE hThread;
    DWORD dwId;

    hDoneEvent = CreateEvent(NULL, FALSE, FALSE, NULL);
    if (hDoneEvent == NULL)
        return GetLastError();

    hThread = CreateThread(NULL, 0, Worker, NULL, 0, &dwId);
    if (hThread == NULL)
        return GetLastError();

    cout << "Главный поток: жду сигнала о готовности..." << endl;
    WaitForSingleObject(hDoneEvent, INFINITE);
    cout << "Главный поток: дождался, продолжаю." << endl;

    WaitForSingleObject(hThread, INFINITE);
    CloseHandle(hThread);
    CloseHandle(hDoneEvent);
    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows/MSVC в этом окружении) -
проверено по логике API, не запуском. WaitForSingleObject(hDoneEvent,
INFINITE) действительно блокирует главный поток без траты
процессорного времени, пока рабочий поток не вызовет SetEvent - поток
не "просыпается" раньше времени и не крутится впустую, а ждёт
по-настоящему, пока сигнал не придёт.

4. Семафор - пул из 2 мест на 4 потока

Механизм: 4 потока хотят поработать с ограниченным ресурсом, но
одновременно к нему допускается не больше 2 (в отличие от мьютекса -
это не "один за раз", а "N за раз"). Каждый поток занимает слот
(семафор -1), работает, освобождает слот (семафор +1).

```c
#include <windows.h>
#include <iostream.h>

HANDLE hSlots;
CRITICAL_SECTION csOut;   // только для аккуратного вывода, не путать с семафором

DWORD WINAPI Worker(LPVOID lpParam)
{
    int id = (int)(INT_PTR)lpParam;

    WaitForSingleObject(hSlots, INFINITE);      // занять слот

    EnterCriticalSection(&csOut);
    cout << "Поток " << id << ": занял слот, работаю..." << endl;
    LeaveCriticalSection(&csOut);

    Sleep(400);

    EnterCriticalSection(&csOut);
    cout << "Поток " << id << ": освобождаю слот." << endl;
    LeaveCriticalSection(&csOut);

    ReleaseSemaphore(hSlots, 1, NULL);          // освободить слот
    return 0;
}

int main()
{
    HANDLE hThreads[4];
    DWORD dwId;

    InitializeCriticalSection(&csOut);
    hSlots = CreateSemaphore(NULL, 2, 2, NULL);  // 2 места сразу, максимум 2
    if (hSlots == NULL)
        return GetLastError();

    for (int i = 0; i < 4; ++i)
    {
        hThreads[i] = CreateThread(NULL, 0, Worker, (LPVOID)(INT_PTR)i, 0, &dwId);
        if (hThreads[i] == NULL)
            return GetLastError();
    }

    WaitForMultipleObjects(4, hThreads, TRUE, INFINITE);

    for (int i = 0; i < 4; ++i)
        CloseHandle(hThreads[i]);
    CloseHandle(hSlots);
    DeleteCriticalSection(&csOut);
    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows/MSVC в этом окружении) -
проверено по логике API, не запуском. По той же логике в любой момент
"работают" не больше 2 потоков сразу - третий и четвёртый не могут
занять слот (WaitForSingleObject(hSlots, ...) их не пропустит), пока
кто-то не освободит место через ReleaseSemaphore - это и есть семафор
в действии, в отличие от мьютекса он пускает больше одного, но не
безгранично.
