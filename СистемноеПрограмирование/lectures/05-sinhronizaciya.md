Глава 5. Синхронизация

Суть

Эта глава - теория без единой строчки Win32 API, зато она объясняет,
откуда вообще берутся критическая секция, мьютекс, событие и семафор
из следующей главы: все четыре - это просто разные частные случаи
одной и той же идеи "подожди условия, потом сделай действие". Не зная
эту главу, можно пользоваться Win32-функциями синхронизации как
чёрным ящиком, но будет непонятно, почему их именно четыре и чем они
принципиально отличаются друг от друга - а не просто именами.

Две задачи, ради которых всё это затевается

Прежде чем вводить формальности, две жизненные ситуации.

Первая: поток А готовит данные (например читает файл), поток Б должен
их обработать, но только ПОСЛЕ того как А закончит - раньше нечего
обрабатывать. Поток Б должен как-то дождаться сигнала "данные готовы".
Это называется условной синхронизацией.

Вторая: два потока одновременно хотят изменить одну и ту же
переменную - например оба прибавляют к общему счётчику. Если оба
одновременно прочитают старое значение, оба прибавят единицу к нему и
оба запишут результат - одно прибавление физически потеряется, хотя по
коду выглядит, что прибавили дважды. Нужно гарантировать, что в
конкретном опасном куске кода находится только один поток за раз. Это
называется взаимным исключением, а сам опасный кусок кода - критической
секцией.

Всё, что дальше в этой главе - это формализация именно этих двух
задач и разбор того, как их решать программно и аппаратно.

Действие и непрерывное действие

Действием называется изменение контекста потока - по сути, любая
последовательность команд, которая что-то меняет (переменные, которые
она использует - это и есть контекст действия). Действие называется
непрерывным (атомарным), если у него есть два свойства: оно не
прерывается во время своего выполнения, и его контекст меняется только
им самим, никем больше. Если непрерывное действие - это ровно одна
команда микропроцессора, его называют атомарной командой.

На однопроцессорной машине первое свойство обеспечить просто:
запретить прерывания на время действия, и его точно никто не прервёт.
Но на нескольких процессорах этого недостаточно: запрет прерываний на
одном процессоре не мешает другому процессору в это же время менять
тот же контекст - поэтому там непрерывность нужно обеспечивать иначе
(см. "Аппаратная реализация" ниже).

Определение синхронизации через await

Чтобы говорить о синхронизации потоков формально (а не просто "пусть
как-то подождёт"), книга вводит оператор await с синтаксисом:

await(логическое условие) действие;

Работает он так: ждёт, пока условие не станет истинным, и как только
это случилось - сразу (одним непрерывным шагом, без прерывания между
проверкой условия и выполнением действия) выполняет действие.
Синхронизация потоков - это и есть исполнение потоками таких условных
непрерывных действий.

Из этого общего оператора получаются ровно два частных случая, и это
как раз наши две задачи из начала главы:

await(условие); - без действия, просто ждать выполнения условия. Это
условная синхронизация, а само условие как раз и называют событием
(event) - "поток ждёт наступления события".

await(TRUE) действие; - условие всегда истинно, значит действие
выполняется безусловно, но всё равно непрерывно (без вмешательства
других потоков). Это взаимное исключение, а код внутри действия -
критическая секция.

То есть "событие" и "критическая секция" - это не два случайных
термина, а буквально два края одного и того же оператора await: один
без действия, другой с условием TRUE.

Программная реализация - самое простое решение условной синхронизации

На одном процессоре await можно грубо реализовать через обычную
глобальную переменную и цикл ожидания. Пример: поток thread_2 после
своих действий сигналит событие, поток thread_1 ждёт его перед тем как
продолжить.

```c
bool event = false;

void thread_1() {
    actions_before_event();
    while (!event);          // крутимся, пока событие не наступило
    actions_after_event();
}

void thread_2() {
    some_actions();
    event = true;             // сигналим о наступлении события
    other_actions();
}
```

Просто, но у этого решения есть цена: пока thread_1 крутится в
while(!event), он не делает никакой полезной работы, а только жрёт
процессорное время - это называется активным ожиданием, и это главный
недостаток всех решений в этой главе вплоть до "Примитивов
синхронизации" ниже.

Задача взаимного исключения и алгоритм Петерсона

Чтобы решение задачи взаимного исключения вообще считалось правильным,
книга требует от него трёх свойств:

безопасность - в любой момент внутри критической секции находится не
больше одного потока (это то самое требование, ради которого всё
затевалось);

поступательность - потоки не блокируют друг друга бесконечно в
ожидании входа (если один поток не в критической секции, второй рано
или поздно попадёт внутрь);

справедливость - каждый поток попадает в критическую секцию за
ограниченное время, а не ждёт вечно, пока другие проходят раз за
разом.

Простейшее известное решение для двух потоков - алгоритм Петерсона
(1981). Механизм на пальцах, без формул: у каждого потока есть свой
флаг "я хочу войти" (x1, x2), и есть общая переменная q - "чья сейчас
очередь". Прежде чем проверять, свободен ли вход, поток честно
уступает очередь другому (q = номер другого потока) и только потом
ждёт, но ждёт с условием "либо соперник не хочет войти, либо сейчас не
его очередь". Вежливость этого протокола (сначала уступи, потом
проверяй) и не даёт обоим потокам войти одновременно.

```c
bool x1 = false;
bool x2 = false;
int  q;                        // чья сейчас очередь

void thread_1() {
    while (true) {
        non_critical_section_1();
        x1 = true;              // хочу войти
        q = 2;                  // уступаю очередь thread_2
        while (x2 && q == 2);   // жду, если соперник тоже хочет и сейчас его очередь
        critical_section_1();
        x1 = false;
    }
}

void thread_2() {
    while (true) {
        non_critical_section_2();
        x2 = true;
        q = 1;
        while (x1 && q == 1);
        critical_section_2();
        x2 = false;
    }
}
```

Книга доказывает все три свойства строго через булеву алгебру - здесь
это не повторяется целиком, важно понять идею: обмен "хочу войти" +
"уступаю очередь" исключает ситуацию, когда оба потока одновременно
считают, что путь свободен.

Аппаратная реализация синхронизации

Программные решения вроде алгоритма Петерсона работают только на
одном процессоре (там команды разных потоков всё равно выполняются по
очереди, просто чередуясь). На нескольких физических процессорах этого
недостаточно - контексты параллельных действий могут пересечься
по-настоящему одновременно, а не только "как будто одновременно". Для
настоящей многопроцессорной синхронизации нужны специальные
непрерывные команды самого процессора, которые на время своего
выполнения блокируют шину памяти для остальных процессоров. Книга
разбирает две такие команды:

Проверить и установить (test-and-set, команда tas у Motorola 68000):
атомарно читает старое значение переменной, ставит новое значение 1,
возвращает старое. На ней строится замок: while(tas(lock)); - крутимся,
пока не получим в ответ 0 (значит, замок был свободен и теперь наш).

Обменять содержимое переменных (exchange, команда xchg у Intel x86):
атомарно меняет местами значения двух переменных. Замок строится так
же: свой локальный ключ выставляем в 1 и обмениваем его местами с
общим lock, пока в ключе после обмена не окажется 0.

Оба варианта называют спин-блокировкой (spinlock) или активным
ожиданием - потому что это опять цикл while, который крутится, ничего
полезного не делая, пока не получит разрешение войти. У аппаратных
решений, в отличие от программных, нет ограничения на число потоков -
они работают для любого их количества. Но главный недостаток остаётся
общим и для программных, и для аппаратных решений этой главы: впустую
тратится процессорное время на ожидание в цикле. Отсюда общее название
- алгоритмы активного ожидания (busy waiting algorithms).

Примитивы синхронизации

Чтобы не жечь процессорное время на активное ожидание, логичный шаг -
не крутить ждущий поток в цикле, а по-настоящему ЗАБЛОКИРОВАТЬ его
(приостановить), и разбудить только когда придёт время. Программное
средство, которое это делает, и называется примитивом синхронизации -
на практике это почти всегда объект ядра операционной системы. У
каждого примитива есть своя очередь заблокированных потоков (в книге -
класс ThreadQueue, который умеет ставить поток в очередь и
приостанавливать его - EnqueueThread через SuspendThread, и снимать с
очереди и возобновлять - DequeueThread через ResumeThread).

Условие (Condition) - бинарный примитив, прямой аналог "события" из
await. Внутри - тот же булев флаг event, что и в самодельном примере
выше, но проверка и ожидание устроены не через цикл, а через
блокировку потока:

```c
class Condition {
    bool event;
    ThreadQueue tq;
public:
    Condition(bool b) : event(b) {}

    void Signal() {                 // сигнализировать о наступлении условия
        disable_interrupt();
        if (!tq.DequeueThread())    // если кто-то ждёт - разбудить его
            event = true;           // если никто не ждёт - запомнить флаг
        enable_interrupt();
    }

    void Wait(Thread t) {           // ждать выполнения условия
        disable_interrupt();
        if (event)
            event = false;          // условие уже наступило - не блокируемся
        else
            tq.EnqueueThread(t);    // иначе встаём в очередь и блокируемся
        enable_interrupt();
    }
};
```

Условие решает обе наши задачи с начала главы. Для условной
синхронизации - ровно как в самодельном примере, только вместо
while(!event) вызывается event.Wait(thread_1), а поток при этом реально
приостановлен, не крутится вхолостую. Для взаимного исключения -
Condition создаётся сразу истинным (event(true), "вход разрешён"),
вход в критическую секцию - event.Wait(thread), выход - event.Signal()
(разрешить следующему).

Семафор (Semaphore) - обобщение условия: вместо булева флага - счётчик.
Signal() увеличивает счётчик (или сразу будит одного из очереди),
Wait() уменьшает счётчик, если он больше нуля, иначе блокирует поток.
Семафор, который принимает только 0 и 1, называют бинарным - это то
же самое, что условие. Если же он принимает любые неотрицательные
целые - его называют считающим, и используют для подсчёта готовых
"единиц ресурса": потоки-производители увеличивают счётчик (произвели
ресурс), потоки-потребители уменьшают (забрали ресурс). Ещё один
нюанс: если очередь заблокированных потоков у примитива обслуживается
строго по FIFO ("первый пришёл - первый вышел"), примитив называют
сильным, иначе - слабым; если в документации явно не написано, что
очередь FIFO, полагаться на этот порядок нельзя (обслуживание может
идти и по приоритетам потоков).

Частые путаницы и ошибки

Путают "активное ожидание" (busy waiting, цикл while, жрущий CPU) и
блокировку через примитив синхронизации (поток реально приостановлен,
CPU освобождён для других) - первое это то, с чего глава начинается
как с наивного решения, второе - то, ради чего она вообще написана.

Думают, что событие (event) и критическая секция (мьютекс) - это
принципиально разные механизмы. На уровне этой главы это два частных
случая одного оператора await - разница только в том, есть у await
условие или оно всегда истинно.

Забывают, что программные решения (Петерсон, флаги) работают только
на одном процессоре - на нескольких физических процессорах нужны уже
аппаратные атомарные инструкции (test-and-set, exchange), про это
отдельно предупреждает раздел "Аппаратная реализация".

Путают бинарный семафор с обычным условием (Condition) - это,
по книге, одно и то же по сути, разница только в диапазоне значений
счётчика (0/1 против произвольного неотрицательного числа).
