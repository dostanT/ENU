Глава 1. Операционные системы и их интерфейсы

Суть

Это вводная глава — она задаёт словарь, которым книга будет пользоваться дальше. Тут объясняется, зачем вообще нужна операционная система, какие бывают типы ОС, что такое Win32 API (набор функций, через который программы общаются с Windows), как устроены типы данных в этом API, и что такое объекты и дескрипторы — центральное понятие, которое будет всплывать в каждой следующей главе. Поток, процесс, файл, канал — всё это "объекты", и работать с ними ты будешь только через дескрипторы.

Зачем нужна операционная система

У компьютера есть ресурсы: физические (процессор, оперативная память, диск, шины, устройства ввода-вывода) и логические, или информационные (данные и программы, которые лежат в памяти). Когда говорят про все ресурсы сразу, физические и логические, используют термин "ресурсы компьютера" или "системные ресурсы".

Чтобы программа вообще могла выполниться, ей нужен доступ к этим ресурсам. Кто-то должен этот доступ выдавать и следить, чтобы программы не мешали друг другу. Этим и занимается операционная система — по сути это администратор или менеджер ресурсов компьютера. У неё две главные задачи: управлять ресурсами компьютера и распределять (диспетчеризовать, планировать) их между программами, которые хотят работать одновременно.

Какие бывают операционные системы

Книга вводит несколько осей классификации, по которым ОС отличаются друг от друга.

По числу программ, которые могут работать одновременно: однопрограммная (она же однопользовательская) ОС может выполнять только одну пользовательскую программу за раз. Мультипрограммная (она же многопользовательская) может выполнять сразу несколько.

По числу процессоров, на которых она способна работать: однопроцессорная ОС работает только на компьютере с одним процессором. Мультипроцессорная умеет работать и на компьютерах с несколькими процессорами.

По типу задач: обычная ОС обрабатывает информацию под управлением пользователя — ты сидишь и работаешь за компьютером. ОС реального времени управляет каким-то объектом (роботом, самолётом, станком) без участия человека, и для неё критично быстро реагировать на внешние события. Если такая система затормозит хоть немного, это может привести к поломке оборудования или аварии. Обычную ОС медленная реакция просто раздражает пользователя, а не ломает физическое оборудование — в этом разница по цене ошибки.

Книга дальше рассматривает только ОС от Microsoft — Windows 98 и Windows 2000. Они устроены по-разному внутри, но используют один и тот же интерфейс для программирования приложений — Win32 API, и именно поэтому книгу можно читать, не задумываясь, под какую конкретно систему ты пишешь код. Windows CE (для бытовой электроники, контроллеров и коммуникационного оборудования) в книге отдельно не рассматривается, но те же самые приёмы потом пригодятся и там. Windows XP тоже отдельно не разбирается, но все приёмы, которые в книге показаны для Windows 2000, работают и в XP.

Что такое Win32 API

Win32 API — это набор функций и классов, через которые пишутся приложения под Windows. Тут важно сразу понять механизм: твоя программа не лезет напрямую в железо или во внутренности системы, она вызывает готовые функции API, а уже они внутри делают всю грязную работу.

У разных функций API есть нюанс — не все они одинаково ведут себя в Windows 98 и Windows 2000, какие-то работают только в Windows 2000. Но таких различий немного, книга явно предупреждает о них там, где они есть, а в остальном не делает разницы между версиями Windows, чтобы не загромождать текст.

Функционально весь Win32 API разбит на категории:
- Base Services (базовые сервисы) - доступ приложения к ресурсам компьютера
- Common Control Library (библиотека общих элементов управления) - готовые классы окон
- Graphics Device Interface (интерфейс графических устройств) - вывод графики на экран, принтер и другие устройства
- Network Services (сетевые сервисы) - работа в компьютерных сетях
- User Interface (интерфейс пользователя) - взаимодействие с пользователем через окна
- Windows NT Access Control (управление доступом для Windows NT) - защита информации, контроль и ограничение доступа к защищаемым объектам
- Windows Shell (оболочка Windows) - работа с оболочкой системы
- Windows System Information (информация о системе Windows) - работа с конфигурацией ОС

Курс системного программирования, и эта книга, занимается в основном первой категорией и предпоследней — Base Services и Windows NT Access Control. Остальные категории, особенно всё, что касается графического интерфейса (Common Control Library, GDI, User Interface) — это уже другая дисциплина, "Программирование пользовательских интерфейсов в Windows", в этой книге она не разбирается. Именно поэтому все примеры в книге — консольные приложения: это осознанное упрощение, чтобы не тратить код и текст на рисование окон, а сосредоточиться на том, как работают процессы, потоки, память, файлы и безопасность.

Типы данных в Win32 API

Win32 API рассчитан на язык C, точнее на процедурные языки вообще, поэтому в нём нет и не может быть того, что есть только в C++ — классов, ссылок, механизма исключений. Всё построено на простых типах и структурах.

Чтобы интерфейс меньше зависел от конкретного языка программирования и конкретного железа, разработчики Win32 API не стали использовать стандартные типы C напрямую, а завели для них собственные имена — по сути псевдонимы через typedef, записанные ЗАГЛАВНЫМИ буквами, чтобы визуально отличать "типы Win32 API" от обычных типов C. По смыслу большинство из них — это просто переименованные стандартные типы C:

```
typedef char CHAR;
typedef unsigned char UCHAR;
typedef UCHAR *PUCHAR;
typedef unsigned char BYTE;
typedef BYTE *PBYTE;
typedef BYTE *LPBYTE;

typedef short SHORT;
typedef unsigned short USHORT;
typedef USHORT *PUSHORT;
typedef unsigned short WORD;
typedef WORD *PWORD;
typedef WORD *LPWORD;

typedef int INT;
typedef int *PINT;
typedef int *LPINT;
typedef int BOOL;
typedef BOOL *PBOOL;
typedef BOOL *LPBOOL;

typedef unsigned int UINT;
typedef unsigned int *PUINT;

typedef long LONG;
typedef long *LPLONG;

typedef unsigned long ULONG;
typedef ULONG *PULONG;
typedef unsigned long DWORD;
typedef DWORD *PDWORD;
typedef DWORD *LPDWORD;

typedef float FLOAT;
typedef FLOAT *PFLOAT;

typedef void *LPVOID;
typedef const void *LPCVOID;
```

Тут стоит один раз навсегда запомнить систему в приставках, потому что дальше по книге она встретится сотни раз:
- P перед именем типа значит "указатель на" (pointer). Например PBYTE — это указатель на BYTE
- LP тоже значит "указатель на", исторически это "long pointer" — в 16-битном мире Windows раньше были отдельно near- и far-указатели, в Win32 это различие исчезло, но обозначение LP осталось как соглашение по именованию
- C внутри имени, как в LPCVOID, значит const — указатель на то, что нельзя изменить через этот указатель

Ещё в Win32 API определены свои символические константы для булевых значений — FALSE (0) и TRUE (1), заданы через обычный препроцессорный #define, а не через настоящий булев тип.

Кроме простых типов в Win32 API есть ещё и сложные — структуры и перечисления. У них, как правило, узкое конкретное назначение, поэтому книга не сваливает их все в одну кучу в первой главе, а описывает каждую отдельно, в той главе, где эта структура реально используется.

Объекты и дескрипторы в Windows

Это последний, но самый важный кусок первой главы — механизм, без которого не работает вообще ничего в Win32 API, и дальше он будет использоваться в каждой следующей главе книги.

Объектом в Windows называется структура данных, которая представляет системный ресурс. То есть когда система даёт тебе файл, канал (pipe), поток, процесс — с точки зрения Win32 API все они одинаково называются "объект". Windows делит объекты на три категории:
- User - объекты интерфейса пользователя, например окна и курсоры
- Graphics Device Interface - объекты для вывода на графические устройства, например кисти и перья
- Kernel - объекты ядра операционной системы, например процессы и файлы

Курс системного программирования занимается только объектами категории Kernel: процессы, потоки, файлы, объекты синхронизации и так далее. Объекты User и GDI — это снова область программирования графических интерфейсов, не эта книга.

Дальше — ключевой механизм. Приложение не имеет прямого доступа к объекту. Это важно понять буквально: ты никогда не держишь в руках сам объект, у тебя нет указателя на структуру объекта в памяти ядра, и не может быть. Вместо этого приложение обращается к объекту косвенно — через дескриптор (handle). В Win32 API дескриптор имеет тип HANDLE.

Что такое дескриптор на самом деле: это запись в таблице, которую ведёт и поддерживает сама операционная система. Эта запись хранит адрес объекта и информацию о том, что это за тип объекта. То есть дескриптор — это не сам объект и не прямой адрес объекта в твоём распоряжении, а что-то вроде номерка в гардеробе: ты получаешь номерок (дескриптор), а сама вещь (объект) остаётся у системы, и обращаешься ты к ней всегда только через этот номерок.

Дескрипторы создаёт сама операционная система, а возвращают их приложению функции Win32 API, которые создают объекты. У этих функций почти всегда одинаковое по смыслу имя: CreateObject, где слово Object заменяется на имя конкретного типа объекта. Например, процесс создаётся функцией CreateProcess, и она возвращает дескриптор именно этого созданного процесса. По соглашению, если такая функция вернула значение, не равное NULL и не отрицательное, значит объект создан успешно.

Когда работа с объектом закончена, его дескриптор нужно закрыть функцией CloseHandle. Тут важная тонкость, в которой все путаются: CloseHandle закрывает именно дескриптор, а не обязательно сам объект. Дело в том, что в Windows на один и тот же объект могут ссылаться сразу несколько разных дескрипторов одновременно, например если дескриптор продублировали или он унаследовался в дочерний процесс. CloseHandle реально уничтожает объект только тогда, когда на него больше не осталось ни одного дескриптора. Это по сути подсчёт ссылок: пока хоть кто-то держит дескриптор на объект, объект живёт.

Пример - закрытие дескриптора

```
BOOL CloseHandle(
    HANDLE hObject   // дескриптор объекта
);
```

Разбор по частям:
- BOOL - тип возвращаемого значения, это Win32-псевдоним int из предыдущего раздела. Функция сообщает "успех или неуспех"
- CloseHandle - имя функции
- HANDLE hObject - единственный параметр, дескриптор объекта, который нужно закрыть. Тип HANDLE — это тот самый универсальный тип для дескриптора любого объекта
- при успехе функция возвращает ненулевое значение, при ошибке — FALSE

Обрати внимание, что сигнатура функции ничего не говорит о том, какой именно это объект — файл, процесс или поток. HANDLE один и тот же тип для всех, а какой это объект на самом деле, знает только сама операционная система внутри своей таблицы дескрипторов.

Частые путаницы и ошибки

- Путать объект и дескриптор. Объект — это ресурс внутри системы, ты его никогда не видишь напрямую. Дескриптор — это твой "номерок" для доступа к нему. Когда говорят "передай дескриптор функции", это не то же самое, что "передай сам объект" — передать сам объект ты физически не можешь, у тебя его нет.
- Думать, что CloseHandle всегда сразу уничтожает объект. Не всегда — если на объект есть ещё дескрипторы, например в другом процессе после наследования или дублирования, объект продолжит жить, пока не закроется последний дескриптор.
- Считать типы данных Win32 API какими-то особыми магическими типами. На самом деле почти все они — это просто C-типы, переименованные в верхний регистр ради единообразия интерфейса. DWORD — это по сути unsigned long, BOOL — это по сути int.
- Воспринимать приставки P и LP как просто буквы в названии типа. Они несут смысл: если видишь тип с P или LP в начале, это почти наверняка указатель на одноимённый тип без приставки.
- Путать категории Win32 API между собой. Base Services и Windows NT Access Control — это системное программирование, то, чем занимается эта книга. Common Control Library, GDI, User Interface — это программирование интерфейсов, отдельная тема, в этой книге сознательно не рассматривается, поэтому все примеры дальше — консольные приложения, а не окна.
