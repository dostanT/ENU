Глава 2. Потоки и процессы

Суть

Это теоретическая глава, ещё без Windows и без конкретных функций API — она вводит словарь, которым дальше будет пользоваться вся книга: что такое поток, что такое контекст потока, какие у потока бывают состояния, как система решает, кому из потоков сейчас дать процессор, и чем поток отличается от процесса. В главе 3 те же понятия появятся уже как конкретные функции Windows.

2.1 Определение потока

Представь, что программа - это карта с развилками (if, циклы), а процессор - путник, который идёт по этой карте от начала до конца, на каждой развилке сворачивая туда, куда велят условия и входные данные. Конкретный пройденный маршрут - от первой выполненной инструкции до последней - и называется потоком управления, или просто потоком (по-английски thread, отсюда иногда говорят "нить").

Важный момент: один и тот же текст программы может породить РАЗНЫЕ потоки, в зависимости от входных данных. Возьмём программу, которая читает два числа a и b и печатает минимальное:

```
#include <iostream.h>
int main()
{
  int a, b;
  cout << "Input two integers: ";
  cin >> a >> b;
  if (a == b)
  {
    cout << "There is no min." << endl;
    return 0;
  }
  if (a < b)
    cout << "min = " << a << endl;
  else
    cout << "min = " << b << endl;
  return 0;
}
```

Если пользователь ввёл a == b, инструкции выполнятся одни; если a < b - другие; если a > b - третьи. Это три разных потока управления в рамках одной и той же программы, потому что поток - это конкретная пройденная последовательность инструкций, а не просто текст кода.

Дальше вводится разница между однопоточной и многопоточной программой. Если в программе одновременно может существовать только один поток - она однопоточная. Пример: функция main вызывает функцию sum(a, b) и ждёт, пока та вернёт результат, чтобы напечатать его. Раз main не может продолжить, пока не получит ответ от sum, это всё ещё один поток - просто последовательный вызов.

А теперь представь, что main вызывает sum, но НЕ ждёт результата и сразу продолжает работать дальше. Вот тут появляются два независимых потока: один - это продолжение main, второй - вычисление внутри sum. Они не имеют общих зависимых переменных, выполняются параллельно, и нет никакой гарантии, в каком порядке они завершатся - может оказаться, что main напечатает сумму раньше, чем sum её вообще посчитает. Именно отсутствие ожидания превращает обычный вызов функции в отдельный, независимый поток.

Отсюда вывод: чтобы явно пометить функцию как "эта функция порождает отдельный поток", операционной системе нужна особая нотация - специальные средства для создания потоков. В Windows это конкретные функции API, о них - в главе 3.

2.2 Контекст потока

Контекст потока - это содержимое памяти, к которой поток имеет доступ, пока выполняется. Проще говоря - то, что поток видит и может менять во время работы. От того, что именно лежит в этом контексте, зависит, можно ли безопасно вызывать функцию параллельно из нескольких потоков одновременно.

Разберём три похожие функции с разным результатом.

Первая использует только локальную переменную:

```
int f(int n)
{
  if (n > 0)
    --n;
  if (n < 0)
    ++n;
  return n;
}
```

Сколько бы потоков ни вызвали f параллельно, каждый вызов получает свою собственную, независимую копию переменной n - они друг другу не мешают. Такая функция называется безопасной для потоков автоматически, без всяких дополнительных мер.

Вторая использует глобальную переменную:

```
int n;
void g()
{
  if (n > 0)
    --n;
  if (n < 0)
    ++n;
}
```

Здесь n одна на всех. Если два потока вызовут g одновременно, оба будут читать и менять ОДНУ И ТУ ЖЕ ячейку памяти без всякой очерёдности - результат непредсказуем, это гонка данных (race condition).

Третья использует статическую переменную внутри функции:

```
int count()
{
  static int n = 0;
  ++n;
  return n;
}
```

Статическая переменная, в отличие от обычной локальной, не создаётся заново при каждом вызове - она одна на все вызовы функции, как и глобальная. Поэтому здесь та же проблема: параллельные вызовы ломают счётчик.

Отсюда определение: функция называется реентерабельной (повторно входимой, от reentrant), если она одновременно:
- не использует глобальные переменные, которые меняются параллельными потоками
- не использует статические переменные, объявленные внутри функции
- не возвращает указатель на статические данные, объявленные внутри функции

Реентерабельная функция ничего общего не трогает, поэтому она безопасна для параллельного вызова "бесплатно", без каких-либо специальных мер.

Отдельно вводится понятие безопасной для потоков функции (thread-safe). Это функция, которая обеспечивает блокировку доступа к ресурсам, которые использует - то есть может трогать общую память, но делает это по очереди, не позволяя двум потокам залезть в одно и то же место одновременно. Как именно устроена такая блокировка - тема глав 6 и 7 (критические секции, мьютексы, семафоры и так далее), здесь важно только само понятие.

Отсюда логика: реентерабельность и потокобезопасность - не одно и то же, хотя и связаны. Реентерабельная функция безопасна, потому что ей нечего защищать - она не трогает общее состояние. Функция, которая трогает общее состояние (не реентерабельна), может стать потокобезопасной, если добавить к ней блокировку доступа. А если она трогает общее состояние и блокировки НЕТ - она не реентерабельна и не потокобезопасна одновременно, то есть попросту небезопасна: это и есть гонка данных, как в примерах с g и count выше.

Есть и соседнее, более низкоуровневое понятие - реентерабельность кода микропроцессора: программа в машинных кодах называется реентерабельной, если она не изменяет свой код во время исполнения. Это нужно, чтобы несколько экземпляров одной и той же программы могли выполняться одновременно, прерывая и возобновляя друг друга, не портя общий код.

2.3 Состояния потока

Поток в каждый момент времени можно описать парой: состояние процессора (выделен потоку сейчас процессор или нет) и состояние программы (готова ли она выполняться, то есть свободны ли все нужные ей ресурсы). Комбинаций формально четыре, но одна из них невозможна: процессор не может быть выделен программе, которая не готова выполняться. Значит, осмысленных комбинаций три:
- блокирован - процессор не выделен, программа не готова
- готов - процессор не выделен, но программа готова, ждёт своей очереди
- выполняется - процессор выделен, программа готова и работает

Добавив ещё два технических состояния - новый (поток ещё не начал работу) и завершён (поток отработал до конца) - получаем модель пяти состояний (рис. 2.1 в книге). Переходы между ними делаются операциями:
- Create - создаёт поток из функции, переводит из "новый" в "готов"
- Exit - выполняется самим потоком при завершении, переводит из "выполняется" в "завершён"
- Run - операционная система даёт готовому потоку процессор, переводит из "готов" в "выполняется"
- Interrupt - операционная система забирает процессор (кончился квант времени или её прервали по другой причине), переводит из "выполняется" в "готов"
- Block - поток сам уходит в ожидание какого-то события (например, ответа от диска), переводит из "выполняется" в "блокирован"
- Unblock - ожидаемое событие наступило, переводит из "блокирован" в "готов"

Дальше модель расширяется операциями Suspend и Resume - это когда ОДИН поток приостанавливает или возобновляет работу ДРУГОГО потока, независимо от того, в каком состоянии тот сейчас находится. Приостановленный поток называют "подвешенным". Так к трём рабочим состояниям добавляются "подвешен и готов" и "подвешен и блокирован" - получается модель семи состояний (рис. 2.2).

Наконец добавляются операции Sleep и Wakeup: поток может сам себя усыпить на заданный интервал времени (перейти в состояние "спит"), а операционная система разбудит его, когда интервал закончится. С учётом ещё и "подвешен и спит" получается полная модель девяти состояний (рис. 2.3) - это самая подробная теоретическая картина. Важно: реальная модель состояний потока в Windows (глава 3) немного отличается от этой идеализированной схемы, но опирается на те же самые идеи.

2.4 Диспетчеризация и планирование потоков

В однопрограммной системе одновременно может выполняться только один поток. Он блокируется, только когда сам ждёт события (например, окончания операции ввода-вывода), и в этот момент процессор просто простаивает без дела - это и есть главный недостаток однопрограммных систем, низкая производительность.

В мультипрограммной системе одновременно существует несколько потоков, и нужна дисциплина - порядок, в котором им выделяется процессор. Время работы процессора делится на кванты (небольшие интервалы). По истечении кванта поток прерывается, и процессор передаётся следующему потоку. Распределением квантов занимается менеджер потоков (планировщик).

При переключении с одного потока на другой менеджер потоков обязан:
- сохранить контекст прерываемого потока
- восстановить контекст запускаемого потока
- передать ему управление

Контекст потока - это как раз содержимое регистров процессора на момент прерывания: сохранить контекст значит списать текущие значения регистров в память, восстановить - записать их обратно перед тем, как продолжить именно этот поток с того самого места, где он остановился.

Если все потоки равноправны (одинаковый приоритет), они выстраиваются в одну очередь и обслуживаются в порядке FIFO (first in - first out, кто раньше пришёл - тот раньше обслужен), а прерванные потоки становятся в конец очереди. Это называется циклическим обслуживанием, оно же FCFS (first come - first served) - никто не остаётся необслуженным навсегда, просто ждёт своей очереди.

Если у потоков разные приоритеты, используется несколько очередей - по одной на каждый уровень приоритета. Простейший алгоритм: сначала до конца обслуживаются потоки из очереди с наивысшим приоритетом, и только потом - остальные.

Управление потоками делится на две разные задачи, которые легко перепутать по звучанию:
- планирование - в какую очередь поставить прерванный поток (этим может двигать приоритет)
- диспетчеризация - в каком порядке потом обслуживаются сами очереди

Любой алгоритм управления потоками пытается одновременно оптимизировать пять вещей:
- максимальную загрузку процессора работой (чтобы он не простаивал)
- максимальную пропускную способность системы
- минимальное время нахождения потока в системе целиком
- минимальное время ожидания потока в очереди
- минимальное время реакции системы на запрос

Размер кванта времени - это всегда компромисс: слишком маленький квант - много времени уходит на само переключение контекста (накладные расходы), слишком большой - долго ждут короткие, интерактивные потоки, пока освободится процессор, занятый тяжёлым потоком.

2.5 Определение процесса

Процесс (или задача) - это запущенное на компьютере приложение вместе со всеми ресурсами, которые нужны для его работы. Все эти ресурсы вместе называют контекстом процесса. Процессу обязательно принадлежат:
- адресное пространство процесса
- потоки, которые выполняются в этом адресном пространстве

Адресное пространство - это виртуальная память, выделенная процессу для работы программы (подробно - в главе 20). Ключевое свойство: адресные пространства разных процессов не пересекаются, и один процесс не может напрямую залезть в память другого. Это как отдельная запертая комната для каждого процесса: если что-то сломалось внутри одной комнаты, это не портит соседние - отсюда и надёжность системы в целом.

Потоки, которые работают в контексте одного процесса, живут в ОДНОЙ этой комнате и потому могут напрямую обращаться к одним и тем же адресам памяти - им не нужно ничего пересылать друг другу специальными средствами, можно просто читать и писать общие переменные. А вот двум разным процессам, чтобы обменяться данными, приходится пользоваться отдельными, более дорогими по затратам механизмами (через операционную систему) - именно поэтому в системном программировании вообще появилось отдельное понятие потока: разделять работу на несколько параллельных путей внутри ОДНОГО процесса намного дешевле, чем гонять данные между несколькими процессами.

Частые путаницы и ошибки

Поток - это не то же самое, что процесс. Поток - конкретный путь выполнения кода. Процесс - контейнер с памятью и ресурсами (в том числе с адресным пространством), внутри которого этот путь выполняется. У процесса минимум один поток, но может быть и много.

Один и тот же текст программы - не значит один и тот же поток. В примере с min/max один код даёт три разных потока в зависимости от входных данных (a==b, a<b, a>b): поток определяется реально пройденной последовательностью инструкций, а не просто текстом функции.

Вызов функции сам по себе - это ещё не новый поток. Если вызывающий код ждёт результата (обычный синхронный вызов) - это по-прежнему один поток. Новый независимый поток появляется только тогда, когда вызывающий НЕ ждёт завершения вызванного и они работают параллельно.

Реентерабельность и потокобезопасность - разные понятия, их легко перепутать. Реентерабельная функция не трогает общую изменяемую память и поэтому безопасна сама по себе. Потокобезопасная функция может трогать общую память, но защищает доступ к ней блокировкой. Нереентерабельная функция БЕЗ блокировки - это гонка данных, а не "почти безопасный" вариант.

Состояние "процессор выделен, но программа не готова" в модели состояний невозможно - его специально исключают, поэтому базовых рабочих состояний потока три, а не четыре.

Suspend/Resume - это не Block/Unblock. Suspend делает над потоком кто-то ДРУГОЙ, и неважно, в каком состоянии поток сейчас находится. Block поток вызывает сам, потому что ждёт какого-то конкретного события (например, ответа от диска).

Планирование и диспетчеризация - разные задачи, несмотря на похожее звучание: планирование решает, в какую очередь поставить поток, диспетчеризация - в каком порядке обслуживать сами очереди.
