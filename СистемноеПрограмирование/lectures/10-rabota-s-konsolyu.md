Глава 10. Работа с консолью

Суть

Глава 9 объяснила, из чего состоит консоль (входной буфер + буфер(ы) экрана). Эта глава - про жизненный цикл самой консоли целиком: как её создать, как от неё избавиться, и через какие "стандартные" дескрипторы к ней обращаются функции ввода-вывода. Важное правило на старте: один процесс может быть связан только с ОДНОЙ консолью одновременно - не с несколькими.

10.1 Создание консоли

Представь консоль как персональный кабинет сотрудника. У каждого сотрудника (процесса) ровно один кабинет, не два. Нового сотрудника можно поселить в кабинет двумя способами: выдать ему готовый новый кабинет с мебелью по заказу, либо нанять его вообще без кабинета - и пусть потом сам обустроит себе кабинет, когда понадобится.

Ровно эти два способа создания новой консоли и описывает раздел:

Первый способ - при создании консольного процесса командой CreateProcess (глава 4) установить флаг CREATE_NEW_CONSOLE. Если консольный процесс создаётся из консольного же приложения-родителя, а этот флаг НЕ установлен - новый процесс просто присоединяется к консоли родительского процесса (тот самый вариант "раздели кабинет с соседом", он же поведение по умолчанию).

Второй способ - функция AllocConsole:

```
BOOL AllocConsole(VOID);
```

Возвращает ненулевое значение при успехе, FALSE - при неудаче. Этим способом пользуется процесс, у которого консоли ещё нет (например, он был создан с флагом DETACHED_PROCESS, без консоли вовсе), но она ему понадобилась - как раз "сотрудник без кабинета, который сам заказал себе кабинет изнутри".

В обоих случаях заголовок окна консоли, его параметры и цвет фона/текста задаются полями структуры STARTUPINFO (та же структура, что уже встречалась при создании процесса в главе 4, здесь используются другие её поля):
- lpTitle - заголовок окна консоли;
- dwX, dwY - позиция левого угла окна консоли;
- dwXSize, dwYSize - размеры окна;
- dwXCountChars, dwYCountChars - размеры буфера экрана;
- dwFillAttributes - цвет фона и цвет текста;
- wShowWindow - способ отображения окна при запуске приложения.

Это "бланк заказа мебели" - но сам бланк учитывается только для тех полей, у которых в поле dwFlags той же структуры STARTUPINFO явно поднят соответствующий управляющий флаг: STARTF_USEPOSITION (использовать dwX, dwY), STARTF_USESIZE (dwXSize, dwYSize), STARTF_USECOUNTCHARS (dwXCountChars, dwYCountChars), STARTF_USEFILLATTRIBUTE (dwFillAttributes), STARTF_USESHOWWINDOW (wShowWindow). Без соответствующего флага поле просто игнорируется, даже если в нём что-то записано.

Отдельно книга отмечает: в Windows 98 при создании новой консоли реально используется только поле lpTitle, остальные атрибуты консоли берутся по умолчанию (например чёрный фон и белый текст), сколько бы полей STARTUPINFO ты ни заполнил.

Пример - создание процесса с настроенной консолью (способ 1, CREATE_NEW_CONSOLE)

Родитель (Листинг 10.1) заполняет STARTUPINFO (заголовок, позиция, размер окна, размер буфера, красные буквы на синем фоне) и запускает дочерний процесс с флагом CREATE_NEW_CONSOLE:

```c
#include <windows.h>
#include <iostream.h>

int main()
{
    char lpszAppName1[] = "C:\\ConsoleProcess.exe";
    STARTUPINFO si;
    PROCESS_INFORMATION pi;

    // заполняем поля структуры STARTUPINFO
    ZeroMemory(&si, sizeof(STARTUPINFO));
    si.cb = sizeof(STARTUPINFO);
    si.lpTitle = "This is a new title";
    si.dwX = 200;               // позиция левого угла окна консоли
    si.dwY = 200;
    si.dwXSize = 300;           // размеры окна
    si.dwYSize = 200;
    si.dwXCountChars = 100;     // размер буфера экрана по горизонтали
    si.dwYCountChars = 100;     // размер буфера экрана по вертикали
    // красные буквы на синем фоне
    si.dwFillAttribute = FOREGROUND_RED | FOREGROUND_INTENSITY |
        BACKGROUND_INTENSITY | BACKGROUND_BLUE;
    // используем все параметры, что установили
    si.dwFlags = STARTF_USECOUNTCHARS | STARTF_USEFILLATTRIBUTE |
        STARTF_USEPOSITION | STARTF_USESHOWWINDOW | STARTF_USESIZE;
    si.wShowWindow = SW_SHOWNORMAL;

    // запускаем процесс с новой цветной консолью
    if (!CreateProcess(lpszAppName1, NULL, NULL, NULL, FALSE,
        CREATE_NEW_CONSOLE, NULL, NULL, &si, &pi))
    {
        cout << "The new process is not created." << endl
             << "Check a name of the process." << endl
             << "Press any key to finish." << endl;
        cin.get();
        return 0;
    }
    // закрываем дескрипторы процесса
    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);

    return 0;
}
```

Дочерний процесс (Листинг 10.2) - отдельный exe, который просто печатает сообщение в уже готовую (созданную родителем) консоль:

```c
#include <iostream.h>

int main()
{
    cout << "I am created." << endl;
    cout << "Press any key to finish.";
    cin.get();

    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows/MSVC в этом окружении) - проверено по документации и логике API. Механизм: раз родитель передал CREATE_NEW_CONSOLE, дочерний процесс получает СВОЮ, отдельную консоль с параметрами именно из si, а не консоль родителя - CreateProcess здесь и создаёт процесс, и одновременно (способ 1) создаёт для него новую консоль, за один вызов.

Пример - процесс без консоли, который сам себе её выделяет (способ 2, AllocConsole)

Листинг 10.3 - родитель запускает дочерний процесс с флагом DETACHED_PROCESS (без какой-либо консоли вообще), передав в STARTUPINFO другие параметры окна (200x100, буфер 150x50):

```c
#include <windows.h>
#include <iostream.h>

int main()
{
    char lpszAppName[] = "C:\\ConsoleProcess.exe";

    STARTUPINFO si;
    PROCESS_INFORMATION pi;

    // заполняем поля структуры STARTUPINFO
    ZeroMemory(&si, sizeof(STARTUPINFO));
    si.cb = sizeof(STARTUPINFO);
    si.lpTitle = "This is a new title";
    si.dwX = 200;              // позиция левого угла окна консоли
    si.dwY = 200;
    si.dwXSize = 200;          // размеры окна
    si.dwYSize = 100;
    si.dwXCountChars = 150;    // размер буфера экрана по горизонтали
    si.dwYCountChars = 50;     // размер буфера экрана по вертикали
    // красные буквы на синем фоне
    si.dwFillAttribute = FOREGROUND_RED | FOREGROUND_INTENSITY |
        BACKGROUND_BLUE | BACKGROUND_INTENSITY;
    // используем все параметры, что установили
    si.dwFlags = STARTF_USECOUNTCHARS | STARTF_USEFILLATTRIBUTE |
        STARTF_USEPOSITION | STARTF_USESIZE;
    si.wShowWindow = SW_SHOWNORMAL;

    // запускаем процесс, который сам распределяет консоль
    if (!CreateProcess(lpszAppName, NULL, NULL, NULL, FALSE,
        DETACHED_PROCESS, NULL, NULL, &si, &pi))
    {
        cout << "The new process is not created." << endl
             << "Check a name of the process." << endl
             << "Press any key to finish." << endl;
        cin.get();
        return 0;
    }
    // закрываем дескрипторы процесса
    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);

    return 0;
}
```

Дочерний процесс (Листинг 10.4) сам вызывает AllocConsole, прежде чем что-либо печатать:

```c
#include <windows.h>
#include <conio.h>

int main()
{
    if (!AllocConsole())
    {
        MessageBox(NULL,
            "Console allocation failed",
            "Ошибка Win32 API",
            MB_OK | MB_ICONINFORMATION
        );
        return 0;
    }

    _cputs("I am created.");
    _cputs("\nPress any char to exit.\n");
    _getch();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Разница с предыдущим примером принципиальная: здесь дочерний процесс СТАРТУЕТ вообще без консоли (DETACHED_PROCESS), а параметры STARTUPINFO, которые заботливо заполнил родитель, реально применятся только тогда, когда сам дочерний процесс изнутри вызовет AllocConsole - то есть "заказ мебели" был сделан заранее, но воспользоваться им может только сам новый сотрудник, и то по своей инициативе.

10.2 Освобождение консоли

Приложение освобождает консоль вызовом функции FreeConsole:

```
BOOL FreeConsole(VOID);
```

Возвращает ненулевое значение при успехе, FALSE - при неудаче.

Пример - выделение и освобождение консоли одним процессом

Листинг 10.5: процесс сначала сам распределяет себе консоль (AllocConsole), выводит пару сообщений, а затем сам же её освобождает (FreeConsole):

```c
#include <windows.h>
#include <conio.h>

int main()
{
    // распределяем консоль
    if (!AllocConsole())
    {
        MessageBox(NULL,
            "Console allocation failed", "Ошибка Win32 API",
            MB_OK | MB_ICONINFORMATION
        );
        return 0;
    }

    _cputs("I am created.\n");
    _cputs("Press any char to exit.\n");
    _getch();

    // освобождаем консоль
    if (!FreeConsole())
    {
        _cputs("Free console failed.\n");
    }
    _cputs("Press any key to exit.\n");
    _getch();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Обрати внимание: после FreeConsole процесс формально остаётся без консоли (как если бы он никогда её не запрашивал), но переменные и дескрипторы, полученные ДО освобождения, сами по себе не становятся автоматически недействительными - просто дальнейший вывод через них больше никуда не попадёт, пока не будет выделена новая консоль.

10.3 Стандартные дескрипторы ввода-вывода

При создании новой консоли система создаёт сразу три дескриптора, которые называются STDIN, STDOUT, STDERR - стандартными дескрипторами ввода, вывода и ошибки. STDIN связывается с входным буфером консоли, а STDOUT и STDERR - оба с буфером экрана. Именно эти дескрипторы используются в функциях, предназначенных для работы с консолью (в том числе во всех функциях следующих глав).

Получить значение стандартного дескриптора - функция GetStdHandle:

```
HANDLE GetStdHandle(DWORD dwStdHandle);
```

Параметр dwStdHandle принимает одно из значений: STD_INPUT_HANDLE (дескриптор стандартного ввода), STD_OUTPUT_HANDLE (стандартного вывода), STD_ERROR_HANDLE (стандартной ошибки). При успехе возвращает нужный дескриптор, при неудаче - значение INVALID_HANDLE_VALUE.

Установить значение стандартного дескриптора - функция SetStdHandle:

```
BOOL SetStdHandle(
    DWORD  dwStdHandle,  // тип дескриптора
    HANDLE hHandle       // новое значение дескриптора
);
```

dwStdHandle принимает те же значения, что и в GetStdHandle, hHandle - новое значение для этого стандартного дескриптора. При успехе возвращает ненулевое значение, при неудаче - FALSE.

Обычно SetStdHandle используется для перенаправления потоков стандартного ввода-вывода. В этом случае дескрипторы стандартных потоков ввода-вывода можно определить вызовом функции CreateFile, которая в качестве имени файла (параметр lpNameFile) принимает одно из специальных зарезервированных значений: CONIN$ или CONOUT$ (это не настоящие файлы на диске, а зарезервированные имена, которые CreateFile распознаёт как "открой именно консольный вход/выход"). Для входного потока CONIN$: dwDesiredAccess = GENERIC_READ, dwShareMode = FILE_SHARE_READ (если консоль наследуется), dwCreationDisposition = OPEN_EXISTING. Для выходного потока CONOUT$: dwDesiredAccess = GENERIC_WRITE, dwShareMode = FILE_SHARE_WRITE (если консоль наследуется), dwCreationDisposition = OPEN_EXISTING. В обоих случаях параметры dwFlagsAndAttributes и hTemplateFile игнорируются, а lpSecurityAttributes нужен только для того, чтобы при желании сделать консоль наследуемой (см. главу 4 про наследование дескрипторов). Подробнее перенаправление стандартного ввода-вывода будет рассмотрено в главе 13, про передачу данных между процессами через анонимные каналы. (Так написано в самой книге, и это устаревшая ссылка: по нынешней нумерации перенаправление стандартного ввода-вывода в анонимный канал разобрано в разделе 15.6 главы 15, "Работа с анонимными каналами", - см. lectures/15-anonimnye-kanaly.md. Там оно делается другим способом, чем здесь: не SetStdHandle, а полями hStdInput/hStdOutput/hStdError структуры STARTUPINFO при запуске потомка.)

Частые путаницы и ошибки

Путают "процесс без консоли" (DETACHED_PROCESS) с "процессом, унаследовавшим консоль родителя" (обычный случай без CREATE_NEW_CONSOLE). В первом случае у процесса консоли нет вообще, пока он сам не вызовет AllocConsole. Во втором - процесс сразу пользуется той же самой консолью, что и родитель.

Думают, что поля STARTUPINFO (lpTitle, dwX, dwXSize и т. д.) применяются автоматически, если их просто заполнить. Каждое поле реально учитывается, только если в dwFlags поднят СООТВЕТСТВУЮЩИЙ управляющий флаг (STARTF_USEPOSITION и т. д.) - без флага заполненное поле просто молча игнорируется.

Забывают про особый случай Windows 98: там при создании новой консоли реально работает только lpTitle, все остальные параметры STARTUPINFO не учитываются, какие флаги dwFlags ни поставь.

Путают STDOUT и STDERR по назначению. Оба связаны с одним и тем же буфером экрана консоли (оба реально выводят на тот же самый экран) - разница не в том, КУДА они пишут физически, а в том, для какого РОДА сообщений они предназначены (обычный вывод против сообщений об ошибках), и в том, что их можно перенаправить независимо друг от друга.
