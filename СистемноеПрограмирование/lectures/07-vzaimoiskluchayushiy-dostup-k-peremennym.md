Глава 7. Взаимоисключающий доступ к переменным

Суть

Критическая секция и мьютекс из главы 6 - тяжёлая артиллерия: они годятся для защиты ЛЮБОГО куска кода, но за универсальность платишь скоростью (а у мьютекса - ещё и переключением в режим ядра). Если единственное, что нужно защитить - это одна простая операция над одной переменной (заменить значение, прибавить единицу), таскать для этого целую критическую секцию избыточно. Глава 7 - про специальный, самый лёгкий инструмент именно для таких простых операций: блокирующие функции (interlocked functions).

Пятый механизм синхронизации - атомарные операции - уже упоминался в lectures/06-sinhronizaciya-potokov-v-windows.md (раздел "Атомарные операции", по слайдам преподавателя, на примере InterlockedIncrement и гонки данных на counter++). Эта глава - тот же самый инструмент, но по книге и полностью: не одна функция, а все четыре, каждая для своего вида операции.

Механизм

Представь у входной двери маленький лоток для писем, которым пользуются два соседа по квартире. Один (пусть это producer) кладёт туда письмо и уходит. Другой (consumer) время от времени подходит, забирает письмо и уходит. Если оба физически возьмутся за лоток в один и тот же момент - один кладёт письмо, другой одновременно тянет его - есть риск, что письмо потеряется или лоток окажется в странном промежуточном состоянии (наполовину вынутое письмо, которое видно и как "есть", и как "нет").

Можно поставить вместо лотка настоящую дверь с замком - это критическая секция или мьютекс из главы 6 - и заставлять соседей ждать своей очереди. Но если всё действие - это одно быстрое "положить письмо" или "забрать письмо", городить ради этого целую дверь избыточно: сама эта "дверь" (а тем более переключение в режим ядра ради мьютекса) может стоить дороже по времени, чем само действие, которое она защищает.

Атомарные операции - это как лоток со специальной автоматической защёлкой прямо в самом механизме. Никакой отдельной двери и очереди нет, но сама защёлка (на уровне процессора) гарантирует, что класть и забирать можно только строго по одному разу за раз - потому что вся операция либо выполняется одной процессорной инструкцией, либо несколькими инструкциями, которые процессор гарантированно не даст прервать посередине. Именно поэтому такую операцию называют атомарной (неделимой, от "атом" - то, что нельзя разрезать на части) - её нельзя увидеть выполненной наполовину.

В книге ровно эта картинка воплощена как пример: поток producer кладёт число в общий "контейнер" - переменную n, поток consumer это число забирает. Дальше в главе - четыре конкретные функции Windows под разные виды этой операции: просто заменить значение, заменить значение с условием, увеличить/уменьшить на единицу, изменить на произвольное число.

Общее для всех четырёх функций требование: адрес переменной, с которой работает блокирующая функция, должен быть выровнен на границу слова (в книге - "кратен 32"). На практике об этом можно не беспокоиться: если переменная в программе объявлена с типом long, unsigned long, или их синонимами LONG, ULONG, DWORD (а других типов с этими функциями книга и не использует) - нужное выравнивание получается само собой, компилятор о нём заботится.

Блокирующие функции могут применяться и потоками из РАЗНЫХ процессов - если эти процессы разделяют общую память через механизм отображения файлов в память (глава 30, ещё впереди).

7.2 Замена значения переменной

Функция для взаимоисключающей замены значения переменной:

```
LONG InterlockedExchange(
    LPLONG lpTarget,  // адрес переменной, значение которой заменяется
    LONG lValue        // новое значение переменной
);
```

Заменяет значение переменной по адресу lpTarget на lValue. Возвращает СТАРОЕ значение переменной (то, что было до замены) - это стоит запомнить сразу, потому что у функции инкремента ниже (7.4) логика возврата будет другой.

Листинг 7.1 - пример использования InterlockedExchange:

```c
#include <windows.h>
#include <iostream.h>

volatile long n;

void producer()
{
    long goods = 0;
    for (;;)
    {
        ++goods;                          // производим новое число
        InterlockedExchange((long*)&n, goods);  // помещаем число в контейнер
        Sleep(150);
    }
}

void consumer()
{
    long goods;
    for (;;)
    {
        Sleep(400);
        InterlockedExchange(&goods, n);   // извлекаем число из контейнера
        cout << "Goods are consumed: " << goods << endl;
    }
}

int main()
{
    HANDLE hThread_p, hThread_c;
    DWORD IDThread_p, IDThread_c;

    cout << "Press any key to terminate threads." << endl;
    // создаем потоки
    hThread_p = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)producer,
                              NULL, 0, &IDThread_p);
    if (hThread_p == NULL)
        return GetLastError();
    hThread_c = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)consumer,
                              NULL, 0, &IDThread_c);
    if (hThread_c == NULL)
        return GetLastError();

    cin.get();

    // прерываем выполнение потоков
    TerminateThread(hThread_p, 0);
    TerminateThread(hThread_c, 0);

    // закрываем дескрипторы потоков
    CloseHandle(hThread_c);
    CloseHandle(hThread_p);

    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows/MSVC в этом окружении) - объяснено по документации и логике API. Механизм: producer каждые 150мс увеличивает свою ЛОКАЛЬНУЮ переменную goods и атомарно кладёт её значение в общую n; consumer каждые 400мс атомарно забирает текущее значение n в свою локальную goods и печатает. InterlockedExchange здесь играет роль и "положить", и "забрать" одновременно - для consumer'а это одновременно чтение старого значения n (которое функция вернула бы) и его извлечение через выходной параметр goods; фактическая логика "забрать" в этом коде построена на том, что n сама передаётся как lpTarget, а goods - это то место, куда запишется её старое значение.

Обрати внимание на конец main: потоки останавливают через TerminateThread, а не через штатное завершение. Это тот самый "плохой" способ остановки потока, о котором предупреждает раздел 3.3 - здесь он используется книгой просто как быстрый способ завершить бесконечный цикл демонстрационной программы, а не как рекомендация. К концу главы (раздел 8.6) книга покажет куда более аккуратный способ остановить поток через события и ExitThread.

7.3 Условная замена значения переменной

```
PVOID InterlockedCompareExchange(
    PVOID *Destination,  // адрес переменной, значение которой заменяется
    PVOID Exchange,       // новое значение переменной
    PVOID Comperand       // значение для сравнения
);
```

Заменяет значение переменной по адресу Destination на Exchange, но ТОЛЬКО ПРИ УСЛОВИИ, что текущее значение этой переменной равно Comperand - если оно другое, замены не происходит. Возвращает, как и InterlockedExchange, старое значение переменной (по нему как раз и можно узнать снаружи, произошла замена или нет: если возвращённое значение равно Comperand - заменили, если другое - нет).

Это и есть тот самый "лоток с защёлкой" в чуть более умной версии: положить новое письмо, но только если лоток сейчас пуст (равен условленному "пустому" значению) - иначе не трогать то, что там уже лежит.

Листинг 7.2 - пример использования InterlockedCompareExchange. Отличается от листинга 7.1 только тем, что producer кладёт новое число в контейнер, только если consumer уже освободил его от старого (сравнивает с 0):

```c
#include <windows.h>
#include <iostream.h>

volatile long n;

void producer()
{
    long goods = 0;
    for (;;)
    {
        ++goods;  // производим новое число
        // помещаем число в контейнер, если он пустой
        InterlockedCompareExchange((PVOID*)&n, (PVOID)goods, 0);
        Sleep(150);
    }
}

void consumer()
{
    long goods;
    for (;;)
    {
        Sleep(400);
        goods = n;                         // извлекаем число из контейнера
        InterlockedExchange((LONG*)&n, 0);  // отмечаем, что контейнер пустой
        cout << "Goods are consumed: " << goods << endl;
    }
}

int main()
{
    HANDLE hThread_p, hThread_c;
    DWORD IDThread_p, IDThread_c;

    cout << "Press any key to terminate threads." << endl;
    hThread_p = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)producer,
                              NULL, 0, &IDThread_p);
    if (hThread_p == NULL)
        return GetLastError();
    hThread_c = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)consumer,
                              NULL, 0, &IDThread_c);
    if (hThread_c == NULL)
        return GetLastError();

    cin.get();

    TerminateThread(hThread_p, 0);
    TerminateThread(hThread_c, 0);

    CloseHandle(hThread_c);
    CloseHandle(hThread_p);

    return 0;
}
```

Не скомпилировано по-настоящему - объяснено по документации и логике API. Механизм: если producer работает быстрее, чем consumer успевает забирать, InterlockedCompareExchange просто не даст перезаписать ещё не забранное число - condition (сравнение с 0) не выполнится, и вызов ничего не изменит. Без этой проверки (как в листинге 7.1) более быстрый producer мог бы затереть число, которое consumer ещё не успел прочитать - оно потерялось бы безвозвратно.

7.4 Инкремент и декремент переменной

Отдельная пара функций для самой частой простой операции - изменить значение на единицу:

```
LONG InterlockedIncrement(
    LPLONG lpAddend  // адрес переменной для инкремента
);

LONG InterlockedDecrement(
    LPLONG lpAddend  // адрес переменной для декремента
);
```

Увеличивает (или уменьшает) значение переменной по адресу lpAddend на единицу. Важное отличие от InterlockedExchange/InterlockedCompareExchange: эти две функции возвращают НОВОЕ значение переменной (то, что получилось ПОСЛЕ изменения), а не старое - лёгкая путаница, если не обращать внимания на это отличие.

Листинг 7.3 - пример использования InterlockedIncrement. Отличается от листинга 7.1 тем, что producer меняет число прямо в контейнере, без отдельной локальной переменной:

```c
#include <windows.h>
#include <iostream.h>

volatile long n;

void producer()
{
    for (;;)
    {
        InterlockedIncrement((long*)&n);  /* изменяем число в контейнере */
        Sleep(150);
    }
}

void consumer()
{
    long goods;
    for (;;)
    {
        Sleep(400);
        InterlockedExchange(&goods, n);  // извлекаем число из контейнера
        cout << "Goods are consumed: " << goods << endl;
    }
}

int main()
{
    HANDLE hThread_p, hThread_c;
    DWORD IDThread_p, IDThread_c;

    cout << "Press any key to terminate threads." << endl;
    hThread_p = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)producer,
                              NULL, 0, &IDThread_p);
    if (hThread_p == NULL)
        return GetLastError();
    hThread_c = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)consumer,
                              NULL, 0, &IDThread_c);
    if (hThread_c == NULL)
        return GetLastError();

    cin.get();

    TerminateThread(hThread_p, 0);
    TerminateThread(hThread_c, 0);

    CloseHandle(hThread_c);
    CloseHandle(hThread_p);

    return 0;
}
```

Не скомпилировано по-настоящему - объяснено по документации и логике API. Разница с листингом 7.1 показывает главную выгоду InterlockedIncrement: не нужна отдельная локальная переменная goods у producer'а и отдельный вызов замены - счётчик меняется сразу там, где лежит, одной атомарной операцией. Это ровно та же функция, что уже встречалась в lectures/06 на примере гонки данных с counter++ - там было наглядно видно вживую, к чему приводит обычный ++ вместо InterlockedIncrement на общей переменной у двух потоков.

7.5 Изменение значения переменной

Самая общая из четырёх функций - прибавляет к переменной произвольное число, а не строго единицу:

```
LONG InterlockedExchangeAdd(
    LPLONG lpAddend,  // адрес переменной, значение которой изменяется
    LONG Increment     // прибавляемое значение
);
```

Прибавляет Increment к переменной по адресу lpAddend. Возвращает, как и InterlockedExchange/InterlockedCompareExchange, СТАРОЕ значение переменной (до прибавления) - в этом InterlockedExchangeAdd похожа на первые две функции, а не на Increment/Decrement. InterlockedIncrement и InterlockedDecrement можно считать частными случаями этой функции с Increment, равным +1 или -1 - но у них есть смысл существовать отдельно именно потому, что они возвращают новое, а не старое значение, что для простого счётчика обычно удобнее.

Листинг 7.4 - пример использования InterlockedExchangeAdd. Отличается от листинга 7.3 только тем, что n увеличивается не на 1, а на 10:

```c
#include <windows.h>
#include <iostream.h>

volatile long n;

void producer()
{
    for (;;)
    {
        /* изменяем число в контейнере */
        InterlockedExchangeAdd((long*)&n, 10);
        Sleep(150);
    }
}

void consumer()
{
    long goods;
    for (;;)
    {
        Sleep(400);
        InterlockedExchange(&goods, n);  // извлекаем число из контейнера
        cout << "Goods are consumed: " << goods << endl;
    }
}

int main()
{
    HANDLE hThread_p, hThread_c;
    DWORD IDThread_p, IDThread_c;

    cout << "Press any key to terminate threads." << endl;
    hThread_p = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)producer,
                              NULL, 0, &IDThread_p);
    if (hThread_p == NULL)
        return GetLastError();
    hThread_c = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)consumer,
                              NULL, 0, &IDThread_c);
    if (hThread_c == NULL)
        return GetLastError();

    cin.get();

    TerminateThread(hThread_p, 0);
    TerminateThread(hThread_c, 0);

    CloseHandle(hThread_c);
    CloseHandle(hThread_p);

    return 0;
}
```

Не скомпилировано по-настоящему - объяснено по документации и логике API.

Ключевые функции главы

InterlockedExchange - атомарно заменяет значение переменной на новое, возвращает старое значение.

InterlockedCompareExchange - атомарно заменяет значение переменной на новое, но только если текущее значение равно заданному для сравнения; возвращает старое значение (по нему видно, произошла ли замена).

InterlockedIncrement / InterlockedDecrement - атомарно увеличивают/уменьшают переменную на 1, возвращают НОВОЕ значение (в отличие от остальных функций главы).

InterlockedExchangeAdd - атомарно прибавляет к переменной произвольное число, возвращает старое значение.

Частые путаницы и ошибки

Путают, что возвращают блокирующие функции. InterlockedExchange, InterlockedCompareExchange и InterlockedExchangeAdd возвращают СТАРОЕ значение переменной (до изменения). InterlockedIncrement и InterlockedDecrement - наоборот, НОВОЕ значение (после изменения). Перепутать легко, если считать все пять функций одинаковыми по духу.

Забывают про выравнивание адреса. Все блокирующие функции требуют, чтобы адрес переменной был выровнен на границу слова - на практике об этом не нужно думать отдельно, если переменная объявлена как long/unsigned long/LONG/ULONG/DWORD, но если попытаться применить эти функции к переменной другого размера (например обычному int напрямую без приведения, или short) - есть риск нарушить это требование.

Путают атомарную операцию с критической секцией по области применения. Блокирующие функции защищают только одну простую операцию над одной переменной за раз - они не подходят, если нужно атомарно изменить сразу НЕСКОЛЬКО переменных или выполнить сложную логику между чтением и записью (для этого по-прежнему нужна критическая секция или мьютекс из главы 6).

Считают TerminateThread в примерах этой главы образцом для подражания. Все листинги 7.1-7.4 останавливают потоки через TerminateThread ради простоты демонстрационного кода - глава 3 явно предупреждает, что это аварийный способ, а не обычный (см. lectures/03-potoki-v-windows.md, раздел 3.3). Раздел 8.6 этой же книги показывает более правильный способ - через события и ExitThread.
