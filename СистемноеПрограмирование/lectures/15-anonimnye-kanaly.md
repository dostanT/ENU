Глава 15. Работа с анонимными каналами в Windows

Суть

Анонимный канал - это "труба" внутри операционной системы, по которой процессы на ОДНОМ компьютере передают друг другу байты. У трубы два отверстия: в одно записывают, из другого читают, и у каждого отверстия свой дескриптор (тот самый "номерок" из главы 1). Слово "анонимный" значит "без имени": найти такую трубу по имени нельзя, добраться до неё можно только имея на руках номерок, а номерки раздаёт тот, кто трубу создал, - своим дочерним процессам (наследование дескрипторов, глава 4). Читают и пишут в трубу теми же функциями, что и в файл: ReadFile и WriteFile.

Глава организована так, как сказано в самой книге: сначала определение и все функции (15.1-15.4), потом примеры (15.5), и в последнем разделе - как при помощи канала перенаправить стандартный ввод-вывод (15.6). Картинка на всю главу: родитель прокладывает трубу пневмопочты между своей комнатой и комнатой ребёнка. В телефонной книге этой трубы нет - воспользоваться ею может только тот, кому родитель вручил один из концов.

15.1 Анонимные каналы

Определение книги: анонимным каналом называется объект ядра операционной системы, который обеспечивает передачу данных между процессами, выполняющимися на одном компьютере. Процесс, который создаёт канал, - сервер анонимного канала. Процессы, которые связываются с каналом, - клиенты. Обрати внимание: "сервер" и "клиент" тут означают только "кто создал трубу" и "кто к ней присоединился" - а вовсе не "кто пишет" и "кто читает". Данные могут идти и от клиента к серверу (так в первом примере), и наоборот.

Характеристики анонимных каналов (все пять нужно помнить - это ответ на "карточку" из главы 14):

- не имеют имени;
- полудуплексные (данные идут в одну сторону - это определение из главы 14);
- передача данных потоком (непрерывная последовательность байтов, а не отдельные сообщения);
- синхронный обмен данными (вызывающий ждёт, пока операция не закончится);
- возможность моделировать любую топологию связей (1-1, 1-N, N-1, N-M - за счёт того, что дескрипторы можно раздавать сколь угодно многим процессам).

Про "полудуплексность" книга даёт отдельное пояснение, потому что оно сбивает с толку. Сначала пример. Родитель создал канал и получил два дескриптора: один для записи, другой для чтения. Ребёнку он отдаёт дескриптор записи, себе оставляет дескриптор чтения. Данные потекли от ребёнка к родителю. Но что мешает родителю отдать ребёнку ОБА дескриптора - и тогда ребёнок сможет и писать, и читать? Ничего. Поэтому фраза "по каналу данные идут только в одну сторону" верна лишь для КОНКРЕТНОГО дескриптора: через дескриптор записи можно только записывать, через дескриптор чтения - только читать. А у каждого конца канала свой дескриптор, и его можно передать любому дочернему процессу - поэтому каждый процесс при желании может и писать в канал, и читать из него. (Но канал при этом один и очередь в нём одна - к чему это приводит, показывает пример 15.3-15.4 ниже.)

Отдельное замечание из книги про Windows NT: в этих системах анонимный канал реализован при помощи именованного канала с уникальным именем. Следовательно, функции для работы с именованными каналами (глава 16) могут работать и с анонимными.

Порядок работы с анонимными каналами, которого книга придерживается дальше:

1. создание анонимного канала сервером;
2. соединение клиентов с каналом;
3. обмен данными по каналу;
4. закрытие канала.

Карточка анонимного канала (по образцу из конспекта главы 14): имя - нет; направление - полудуплексное (в одну сторону через каждый дескриптор); передача - потоком байтов; обмен - синхронный; топологии - любые; компьютер - только один и тот же. Про буферизацию книга прямо не говорит, но у канала есть буфер заданного размера (параметр dwSize, см. 15.2), так что по логике это ограниченная вместимость - это мой вывод, а не слова книги.

15.2 Создание анонимных каналов

Представь, что тебе нужно проложить трубу. Что надо решить: куда положить два "номерка" (для записи и для чтения), могут ли эти номерки передаваться детям, и какой вместимости хочешь трубу. Ровно это и спрашивает функция CreatePipe, которую вызывает процесс-сервер:

```
BOOL CreatePipe(
    PHANDLE hReadHandle,                    // дескриптор для чтения из канала
    PHANDLE hWriteHandle,                   // дескриптор для записи в канал
    LPSECURITY_ATTRIBUTES lpPipeAttributes, // атрибуты защиты
    DWORD dwSize                            // размер буфера в байтах
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Что означают параметры:

- hReadHandle и hWriteHandle - адреса двух переменных типа HANDLE, куда функция запишет два новых дескриптора: один для чтения из канала, второй для записи в него. Дескриптор чтения потом передаётся функциям чтения (ReadFile), дескриптор записи - функциям записи (WriteFile). (В прототипе книга называет их hReadHandle и hWriteHandle, а в тексте под ним - hReadPipe и hWritePipe: это разнобой самой книги, не два разных параметра.)
- lpPipeAttributes - атрибуты защиты канала. Здесь важно одно поле - bInheritHandle: TRUE делает оба дескриптора наследуемыми, NULL (или FALSE) - ненаследуемыми. Подробно - в разделе 15.3.
- dwSize - размер буфера ввода-вывода канала в байтах. Это только ПОЖЕЛАНИЕ: Windows сама определяет размер буфера. Можно передать 0 - тогда система выберет размер по умолчанию.

15.3 Соединение клиентов с анонимным каналом

Как присоединить процесс к трубе без адреса? Только вручив ему один из концов. Значит, нужно передать клиенту дескриптор канала, и это упирается в те самые условия наследования из главы 4:

- передаваемый дескриптор должен быть наследуемым;
- клиент должен быть ДОЧЕРНИМ процессом сервера и наследовать его наследуемые дескрипторы, то есть создаваться функцией CreateProcess в процессе-сервере;
- в CreateProcess параметр bInheritHandles должен быть TRUE.

Наследуемость определяется полем bInheritHandle структуры SECURITY_ATTRIBUTES, на которую указывает lpPipeAttributes в CreatePipe. Если поле равно TRUE - дескрипторы канала создаются наследуемыми, иначе - ненаследуемыми.

Если клиенту нужны оба дескриптора - оба должны быть наследуемыми с самого начала. Если же клиенту передаётся только ОДИН, есть два пути:

- либо создать оба дескриптора наследуемыми, а потом тот, который клиенту не нужен, сделать ненаследуемым;
- либо создать оба ненаследуемыми, а потом тот, который нужен клиенту, сделать наследуемым.

Как менять наследуемость у уже существующего дескриптора (см. lectures/04, разделы 4.4-4.5): в Windows 98 создают наследуемый или ненаследуемый ДУБЛИКАТ исходного дескриптора функцией DuplicateHandle и закрывают исходный; в Windows 2000 можно то же самое проще - функцией SetHandleInformation, которая меняет сам флаг наследования.

Но наследование - это только "разрешение". Чтобы клиент реально узнал, под каким числом ему искать унаследованный дескриптор, его нужно ЯВНО передать. Книга перечисляет четыре способа:

- через командную строку;
- через поля hStdInput, hStdOutput и hStdError структуры STARTUPINFO;
- посредством сообщения WM_COPYDATA;
- через файл.

В этой главе используются только первые два - они наиболее естественны для анонимных каналов. Первый показан в примерах 15.1-15.4, второй - в разделе 15.6.

15.4 Обмен данными по анонимному каналу

Для обмена по анонимному каналу используются те же функции, что и для записи/чтения файла. Идея простая: дескриптор канала ведёт себя как дескриптор файла, поэтому WriteFile "пишет в трубу", а ReadFile "забирает из трубы".

Запись:

```
BOOL WriteFile(
    HANDLE hAnonymousPipe,          // дескриптор анонимного канала
    LPCVOID lpBuffer,               // буфер данных
    DWORD dwNumberOfBytesToWrite,   // количество байтов для записи
    LPDWORD lpNumberOfBytesWritten, // количество записанных байтов
    LPOVERLAPPED lpOverlapped       // асинхронный ввод
);
```

Параметры: hAnonymousPipe - дескриптор ЗАПИСИ канала (первым параметром должен быть именно он); lpBuffer - адрес буфера, откуда брать байты; dwNumberOfBytesToWrite - сколько байтов записать; lpNumberOfBytesWritten - адрес переменной, куда функция положит, сколько байтов реально записано; lpOverlapped - для асинхронной операции. Анонимные каналы поддерживают только синхронную передачу, поэтому здесь всегда NULL. Возврат: ненулевое значение при успехе, FALSE при неудаче.

Чтение:

```
BOOL ReadFile(
    HANDLE hAnonymousPipe,          // дескриптор анонимного канала
    LPCVOID lpBuffer,               // буфер данных
    DWORD dwNumberOfBytesToRead,    // количество байт для записи
    LPDWORD lpNumberOfBytesRead,    // количество записанных байтов
    LPOVERLAPPED lpOverlapped       // асинхронный ввод
);
```

Параметры аналогичны: hAnonymousPipe - дескриптор ЧТЕНИЯ канала; lpBuffer - адрес буфера, КУДА положить прочитанное; dwNumberOfBytesToRead - сколько байтов прочитать; lpNumberOfBytesRead - адрес переменной, куда положить, сколько байтов реально прочитано; lpOverlapped - опять NULL. Возврат такой же.

Книга дважды опечаталась в этом месте (в прототипе у ReadFile буфер назван LPCVOID, хотя в него ПИШУТ, а комментарии у двух параметров скопированы с WriteFile; а в тексте написано "прочитанных функцией WriteFile") - смысл понятен: ReadFile читает, и буфер у неё выходной.

Важное правило: обмен идёт строго по назначению дескриптора. Дескриптор записи - только в WriteFile, дескриптор чтения - только в ReadFile. В этом и состоит смысл "передачи только в одном направлении". Но один и тот же процесс может и писать, и читать, если у него на руках оба дескриптора.

После окончания обмена оба дескриптора (записи и чтения) нужно закрыть функцией CloseHandle - как любой дескриптор объекта ядра (глава 1). Пока хоть один дескриптор открыт, система канал не уничтожит: объект ядра живёт, пока живёт хотя бы одна ссылка на него.

15.5 Примеры работы с анонимными каналами

Пример 1 (листинги 15.1 и 15.2) - сервер создаёт канал и дочерний процесс и передаёт ему дескриптор через командную строку. Для определённости клиенту отдаётся дескриптор ЗАПИСИ, а серверу остаётся дескриптор ЧТЕНИЯ: данные пойдут от клиента к серверу. Сначала клиент.

Листинг 15.1 - программа процесса-клиента анонимного канала (собирается в файл Client.exe):

```c
#include <windows.h>
#include <conio.h>

int main(int argc, char *argv[])
{
    HANDLE hWritePipe;

    // преобразуем символьное представление дескриптора в число
    hWritePipe = (HANDLE)atoi(argv[1]);
    // ждем команды о начале записи в анонимный канал
    _cputs("Press any key to start communication.\n");
    _getch();
    // пишем в анонимный канал
    for (int i = 0; i < 10; i++)
    {
        DWORD dwBytesWritten;
        if (!WriteFile(
                hWritePipe,
                &i,
                sizeof(i),
                &dwBytesWritten,
                NULL))
        {
            _cputs("Write to file failed.\n");
            _cputs("Press any key to finish.\n");
            _getch();
            return GetLastError();
        }
        _cprintf("The number %d is written to the pipe.\n", i);
        Sleep(500);
    }
    // закрываем дескриптор канала
    CloseHandle(hWritePipe);

    _cputs("The process finished writing to the pipe.\n");
    _cputs("Press any key to exit.\n");
    _getch();

    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows) - проверено по документации и логике API. Механизм по шагам: клиент получает дескриптор как строку в argv[1] - первом аргументе командной строки; atoi превращает строку в число, а приведение (HANDLE) превращает число обратно в "номерок" (сработает только потому, что клиент унаследовал этот дескриптор - см. 15.3). Дальше клиент ждёт нажатия любой клавиши (_cputs и _getch - функции из conio.h: они пишут на консоль и читают клавишу напрямую, минуя стандартные потоки). В цикле он десять раз записывает в канал число i - целых sizeof(i) байтов, то есть НЕ текст, а само двоичное представление int - печатает сообщение на своей консоли и засыпает на полсекунды. В конце закрывает дескриптор.

Теперь сервер.

Листинг 15.2 - программа процесса-сервера анонимного канала (запускает клиента и передаёт ему дескриптор записи через командную строку):

```c
#include <windows.h>
#include <conio.h>

int main()
{
    char lpszComLine[80];   // для командной строки

    STARTUPINFO si;
    PROCESS_INFORMATION pi;
    HANDLE hWritePipe, hReadPipe, hInheritWritePipe;

    // создаем анонимный канал
    if (!CreatePipe(
            &hReadPipe,    // дескриптор для чтения
            &hWritePipe,   // дескриптор для записи
            NULL,          // атрибуты защиты по умолчанию, в этом случае
                           // дескрипторы hReadPipe и hWritePipe ненаследуемые
            0))            // размер буфера по умолчанию
    {
        _cputs("Create pipe failed.\n");
        _cputs("Press any key to finish.\n");
        _getch();
        return GetLastError();
    }
    // делаем наследуемый дубликат дескриптора hWritePipe
    if (!DuplicateHandle(
            GetCurrentProcess(),     // дескриптор текущего процесса
            hWritePipe,              // исходный дескриптор канала
            GetCurrentProcess(),     // дескриптор текущего процесса
            &hInheritWritePipe,      // новый дескриптор канала
            0,                       // этот параметр игнорируется
            TRUE,                    // новый дескриптор наследуемый
            DUPLICATE_SAME_ACCESS))  // доступ не изменяем
    {
        _cputs("Duplicate handle failed.\n");
        _cputs("Press any key to finish.\n");
        _getch();
        return GetLastError();
    }
    // закрываем ненужный дескриптор
    CloseHandle(hWritePipe);
    // устанавливаем атрибуты нового процесса
    ZeroMemory(&si, sizeof(STARTUPINFO));
    si.cb = sizeof(STARTUPINFO);
    // формируем командную строку
    wsprintf(lpszComLine, "C:\\Client.exe %d", (int)hInheritWritePipe);
    // запускаем новый консольный процесс
    if (!CreateProcess(
            NULL,               // имя процесса
            lpszComLine,        // командная строка
            NULL,               // атрибуты защиты процесса по умолчанию
            NULL,               // атрибуты защиты первичного потока по умолчанию
            TRUE,               // наследуемые дескрипторы текущего процесса
                                // наследуются новым процессом
            CREATE_NEW_CONSOLE, // новая консоль
            NULL,               // используем среду окружения процесса-предка
            NULL,               // текущий диск и каталог, как и в процессе-предке
            &si,                // вид главного окна - по умолчанию
            &pi                 // здесь будут дескрипторы и идентификаторы
                                // нового процесса и его первичного потока
            ))
    {
        _cputs("Create process failed.\n");
        _cputs("Press any key to finish.\n");
        _getch();
        return GetLastError();
    }
    // закрываем дескрипторы нового процесса
    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);
    // закрываем ненужный дескриптор канала
    CloseHandle(hInheritWritePipe);
    // читаем из анонимного канала
    for (int i = 0; i < 10; i++)
    {
        int nData;
        DWORD dwBytesRead;
        if (!ReadFile(
                hReadPipe,
                &nData,
                sizeof(nData),
                &dwBytesRead,
                NULL))
        {
            _cputs("Read from the pipe failed.\n");
            _cputs("Press any key to finish.\n");
            _getch();
            return GetLastError();
        }
        _cprintf("The number %d is read from the pipe.\n", nData);
    }
    // закрываем дескриптор канала
    CloseHandle(hReadPipe);

    _cputs("The process finished reading from the pipe.\n");
    _cputs("Press any key to exit.\n");
    _getch();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Механизм по шагам.

1. CreatePipe(..., NULL, 0) создаёт канал. Атрибуты защиты NULL - значит по умолчанию, а по умолчанию дескрипторы НЕнаследуемые. Размер буфера 0 - выбрать по умолчанию.
2. Клиенту нужен только дескриптор ЗАПИСИ, а он сейчас ненаследуемый. Это ровно второй из двух путей раздела 15.3: создали оба ненаследуемыми, теперь нужный клиенту делаем наследуемым. Способ для Windows 98 - DuplicateHandle (lectures/04, раздел 4.5): копируем дескриптор из текущего процесса в текущий же (GetCurrentProcess() дважды), в новую переменную hInheritWritePipe. Предпоследний аргумент TRUE - новый дескриптор наследуемый. Четвёртый (права доступа, значение 0) игнорируется, потому что последний аргумент DUPLICATE_SAME_ACCESS велит "права оставить те же".
3. Исходный ненаследуемый hWritePipe больше не нужен - закрываем. Теперь на "конец для записи" у сервера есть только наследуемая копия.
4. Формируем командную строку "C:\Client.exe число", где число - значение дескриптора hInheritWritePipe. Путь к Client.exe в книге зашит жёстко: файл должен лежать именно там.
5. CreateProcess с bInheritHandles = TRUE и CREATE_NEW_CONSOLE (у клиента будет своя консоль): клиент наследует наследуемые дескрипторы сервера, в том числе hInheritWritePipe.
6. Дескрипторы процесса и потока клиента (pi.hProcess, pi.hThread) серверу не нужны - закрываем (как всегда после CreateProcess, глава 4). Заодно закрываем свою копию дескриптора записи hInheritWritePipe: сервер писать не собирается, а клиент к этому моменту уже получил свою.
7. Сервер десять раз вызывает ReadFile на hReadPipe. Если данных ещё нет, ReadFile ждёт (обмен синхронный) - поэтому серверу не нужно знать, когда именно клиент начнёт писать.

Ожидаемое поведение (рассуждение по логике API, НЕ проверенный вывод, Windows здесь нет). На консоли клиента сначала появится "Press any key to start communication." и ничего не будет происходить, пока не нажмёшь клавишу. После нажатия каждые ~0.5 секунды будет появляться строка "The number 0 is written to the pipe." (потом 1, 2, ... 9), затем "The process finished writing to the pipe." и "Press any key to exit.". На консоли сервера в те же моменты, когда клиент записывает очередное число, появляются строки "The number 0 is read from the pipe." ... "The number 9 is read from the pipe.", затем "The process finished reading from the pipe." и "Press any key to exit.". До нажатия клавиши в клиенте сервер молча стоит в первом ReadFile.

Пример 2 (листинги 15.3 и 15.4) - двусторонний обмен. Оба дескриптора канала - и записи, и чтения - используются и сервером, и клиентом. Дескрипторы, как и раньше, передаются через командную строку. Сначала клиент.

Листинг 15.3 - процесс-клиент анонимного канала (двусторонний обмен):

```c
#include <windows.h>
#include <conio.h>

int main(int argc, char *argv[])
{
    HANDLE hWritePipe, hReadPipe;
    HANDLE hEnableRead;         // для синхронизации обмена данными
    char lpszEnableRead[] = "EnableRead";

    // открываем событие, разрешающее чтение
    hEnableRead = OpenEvent(EVENT_ALL_ACCESS, FALSE, lpszEnableRead);

    // преобразуем символьное представление дескрипторов в число
    hWritePipe = (HANDLE)atoi(argv[1]);
    hReadPipe = (HANDLE)atoi(argv[2]);
    // ждем команды о начале записи в анонимный канал
    _cputs("Press any key to start communication.\n");
    _getch();
    // пишем в анонимный канал
    for (int i = 0; i < 10; i++)
    {
        DWORD dwBytesWritten;
        if (!WriteFile(
                hWritePipe,
                &i,
                sizeof(i),
                &dwBytesWritten,
                NULL))
        {
            _cputs("Write to file failed.\n");
            _cputs("Press any key to finish.\n");
            _getch();
            return GetLastError();
        }
        _cprintf("The number %d is written to the pipe.\n", i);
    }
    _cputs("The process finished writing to the pipe.\n");

    // ждем разрешения на чтение
    WaitForSingleObject(hEnableRead, INFINITE);
    // читаем ответ из анонимного канала
    for (int j = 0; j < 10; j++)
    {
        int nData;
        DWORD dwBytesRead;
        if (!ReadFile(
                hReadPipe,
                &nData,
                sizeof(nData),
                &dwBytesRead,
                NULL))
        {
            _cputs("Read from the pipe failed.\n");
            _cputs("Press any key to finish.\n");
            _getch();
            return GetLastError();
        }
        _cprintf("The number %d is read from the pipe.\n", nData);
    }
    _cputs("The process finished reading from the pipe.\n");
    _cputs("Press any key to exit.\n");
    _getch();

    // закрываем дескрипторы канала
    CloseHandle(hWritePipe);
    CloseHandle(hReadPipe);
    CloseHandle(hEnableRead);

    return 0;
}
```

Листинг 15.4 - программа процесса-сервера анонимного канала (запускает клиента и передаёт ему оба дескриптора через командную строку):

```c
#include <windows.h>
#include <conio.h>

int main()
{
    char lpszComLine[80];    // для командной строки

    HANDLE hEnableRead;      // для синхронизации обмена данными
    char lpszEnableRead[] = "EnableRead";

    STARTUPINFO si;
    PROCESS_INFORMATION pi;
    HANDLE hWritePipe, hReadPipe;
    SECURITY_ATTRIBUTES sa;

    // создаем событие для синхронизации обмена данными
    hEnableRead = CreateEvent(NULL, FALSE, FALSE, lpszEnableRead);

    // устанавливает атрибуты защиты канала
    sa.nLength = sizeof(SECURITY_ATTRIBUTES);
    sa.lpSecurityDescriptor = NULL;      // защита по умолчанию
    sa.bInheritHandle = TRUE;            // дескрипторы наследуемые

    // создаем анонимный канал
    if (!CreatePipe(
            &hReadPipe,    // дескриптор для чтения
            &hWritePipe,   // дескриптор для записи
            &sa,           // атрибуты защиты по умолчанию, дескрипторы наследуемые
            0))            // размер буфера по умолчанию
    {
        _cputs("Create pipe failed.\n");
        _cputs("Press any key to finish.\n");
        _getch();
        return GetLastError();
    }
    // устанавливаем атрибуты нового процесса
    ZeroMemory(&si, sizeof(STARTUPINFO));
    si.cb = sizeof(STARTUPINFO);
    // формируем командную строку
    wsprintf(lpszComLine, "C:\\Client.exe %d %d",
             (int)hWritePipe, (int)hReadPipe);
    // запускаем новый консольный процесс
    if (!CreateProcess(
            NULL,               // имя процесса
            lpszComLine,        // командная строка
            NULL,               // атрибуты защиты процесса по умолчанию
            NULL,               // атрибуты защиты первичного потока по умолчанию
            TRUE,               // наследуемые дескрипторы текущего процесса
                                // наследуются новым процессом
            CREATE_NEW_CONSOLE, // новая консоль
            NULL,               // используем среду окружения процесса-предка
            NULL,               // текущий диск и каталог, как и в процессе-предке
            &si,                // вид главного окна - по умолчанию
            &pi                 // здесь будут дескрипторы и идентификаторы
                                // нового процесса и его первичного потока
            ))
    {
        _cputs("Create process failed.\n");
        _cputs("Press any key to finish.\n");
        _getch();
        return GetLastError();
    }
    // закрываем дескрипторы нового процесса
    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);
    // читаем из анонимного канала
    for (int i = 0; i < 10; i++)
    {
        int nData;
        DWORD dwBytesRead;
        if (!ReadFile(
                hReadPipe,
                &nData,
                sizeof(nData),
                &dwBytesRead,
                NULL))
        {
            _cputs("Read from the pipe failed.\n");
            _cputs("Press any key to finish.\n");
            _getch();
            return GetLastError();
        }
        _cprintf("The number %d is read from the pipe.\n", nData);
    }
    _cputs("The process finished reading from the pipe.\n");

    // даем сигнал на разрешение чтения клиентом
    SetEvent(hEnableRead);

    // пишем ответ в анонимный канал
    for (int j = 10; j < 20; j++)
    {
        DWORD dwBytesWritten;
        if (!WriteFile(
                hWritePipe,
                &j,
                sizeof(j),
                &dwBytesWritten,
                NULL))
        {
            _cputs("Write to file failed.\n");
            _cputs("Press any key to finish.\n");
            _getch();
            return GetLastError();
        }
        _cprintf("The number %d is written to the pipe.\n", j);
    }
    // закрываем дескрипторы канала
    CloseHandle(hReadPipe);
    CloseHandle(hWritePipe);
    CloseHandle(hEnableRead);

    _cputs("The process finished writing to the pipe.\n");
    _cputs("Press any key to exit.\n");
    _getch();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Механизм по шагам.

Главное, что нужно понять: канал ОДИН. Значит, и очередь байтов в нём ОДНА. Дескриптор записи, который держит клиент, и дескриптор записи, который держит сервер, - это два номерка на один и тот же конец трубы; то же с дескрипторами чтения. Всё, что кто-либо записал, ложится в общую очередь, и заберёт это тот, кто первым вызовет ReadFile. Никакого "канала от клиента к серверу" и отдельного "канала от сервера к клиенту" тут нет, есть одна труба, которой пользуются по очереди.

```
          клиент                                   сервер
   hWritePipe ----\                            /---- hWritePipe
                   >====== ОДИН канал ========<
   hReadPipe  <---/     (одна очередь байтов)   \---- hReadPipe
```

Отсюда и нужна синхронизация - об этом книга говорит прямо после листинга: для двустороннего обмена сервер и клиенты должны синхронизировать доступ к каналу, то есть либо разработать протокол передачи данных, либо использовать объекты синхронизации, которые исключают одновременный неконтролируемый доступ. Здесь работает событие hEnableRead. Ход событий:

1. Сервер ещё до запуска клиента создаёт событие с именем "EnableRead": CreateEvent(NULL, FALSE, FALSE, имя) - второй аргумент FALSE (событие с автосбросом), третий FALSE (в начале несигнальное). Создаёт канал с наследуемыми дескрипторами (заполненная структура sa с bInheritHandle = TRUE, поэтому здесь DuplicateHandle не нужен - наследуемыми сразу оба дескриптора). Запускает клиента, передавая оба числа в командной строке: сначала дескриптор записи, потом чтения (у клиента это argv[1] и argv[2]).
2. Клиент по имени открывает то же событие (OpenEvent - события из главы 6, именованное событие общее для разных процессов). Ждёт нажатия клавиши, потом пишет в канал числа 0-9 и после этого блокируется на WaitForSingleObject(hEnableRead, INFINITE).
3. Сервер читает десять чисел (пока клиент не записал - ждёт), потом вызывает SetEvent(hEnableRead) и пишет в канал числа 10-19.
4. Событие разбудило клиента - он читает десять чисел (10-19).

А теперь вопрос, зачем всё это. Что произошло бы БЕЗ события? Сразу после записи чисел 0-9 клиент пошёл бы в цикл чтения из того же канала - а очередь одна. Клиент мог бы прочитать СВОИ ЖЕ числа раньше, чем до них доберётся сервер. Тогда сервер вечно ждал бы недостающие числа в ReadFile - программа зависла бы. Книга формулирует так: без синхронизации возможно одновременное чтение данных сервером и клиентом, так как они работают параллельно, и это вызовет неправильную работу программы и её зависание. Событие - это "жетон очереди": читать можно только тому, кто получил жетон.

Ожидаемое поведение (рассуждение по логике, НЕ проверенный вывод). Консоль клиента: "Press any key to start communication." - после клавиши десять строк "The number 0 is written to the pipe." ... "The number 9 is written to the pipe." БЕЗ пауз (в этом листинге нет Sleep) - "The process finished writing to the pipe." - затем клиент ждёт события - потом десять строк "The number 10 is read from the pipe." ... "The number 19 is read from the pipe." - "The process finished reading from the pipe." - "Press any key to exit.". Консоль сервера: десять строк "The number 0 is read from the pipe." ... "The number 9 is read from the pipe.", затем "The process finished reading from the pipe.", десять строк "The number 10 is written to the pipe." ... "The number 19 is written to the pipe.", "The process finished writing to the pipe.", "Press any key to exit.".

15.6 Перенаправление стандартного ввода-вывода

Сначала пример из жизни. Есть программа, которая просто печатает "cout << 42;" - про каналы и процессы она ничего не знает. Теперь мы незаметно подменяем ей "экран" трубой: то, что программа "напечатала", уезжает в трубу, а её "клавиатура" - тоже труба. Программа не замечает подмены, а на другом конце трубы другая программа получает то, что первая "напечатала". Это и называется перенаправлением стандартного ввода-вывода, и анонимные каналы для него используются часто.

Чтобы понять, как это работает, книга сначала напоминает про три варианта стандартных функций ввода-вывода в компиляторе Microsoft C++ (каждый описан в своём заголовочном файле):

- stdio.h - стандартная библиотека ввода-вывода языка C. Работает со стандартными файлами: stdin (стандартный ввод), stdout (стандартный вывод), stderr (файл вывода сообщений об ошибках);
- iostream.h - стандартная библиотека ввода-вывода языка C++. Функции и операторы, которые работают со стандартными потоками (в листингах ниже это cin и cout с операторами >> и <<);
- conio.h - консольный ввод-вывод. Отличается от stdio.h тем, что ВСЕГДА работает именно с консолью. Поэтому эти функции (в примерах - _cputs, _cprintf, _getch) можно использовать для общения с пользователем даже тогда, когда стандартный ввод-вывод перенаправлен.

Механизм перенаправления такой. При создании консольного процесса (или при выделении консоли функцией AllocConsole) стандартные файлы и стандартные потоки процесса связываются с дескрипторами, которые заданы в полях hStdInput, hStdOutput и hStdError структуры STARTUPINFO. Значит, если в эти поля положить дескрипторы канала, то функции стандартного ввода-вывода (printf, cout, cin ...) станут писать и читать в канал. Поля учитываются только при поднятом флаге STARTF_USESTDHANDLES в dwFlags - тот же принцип, что в главе 10: поле STARTUPINFO действует, только если поднят соответствующий управляющий флаг (в листинге 15.7 это видно: "использовать стандартные дескрипторы").

Обрати внимание, что это второй из четырёх способов передачи дескрипторов из раздела 15.3, и он удобнее командной строки: ребёнку не нужно ничего сообщать числом. Система сама вешает трубу на "стандартный вход" и "стандартный выход" - то место, где программа и так привыкла искать клавиатуру и экран. Программе-клиенту вообще не надо знать, что рядом канал. Это и есть ответ на обещание из главы 10, где про перенаправление стандартных потоков сказано "подробнее будет в главе 13, про анонимные каналы": в книге тут устаревшая ссылка (по нынешней нумерации это ровно раздел 15.6). Про стандартные дескрипторы и SetStdHandle - lectures/10, раздел 10.3.

Есть и ещё одно отличие от примеров 15.1-15.4. Там числа передавались "сырыми" байтами: WriteFile(&i, sizeof(i)) клал в канал четыре байта самого int. Здесь программы говорят через cout и cin, а это ТЕКСТ: число 3 уезжает в канал как символ "3" и перевод строки, а на другом конце cin >> nData разбирает этот текст обратно в число. Обе стороны обязаны договориться о формате: писать текстом, а читать ReadFile-ом в int (или наоборот) нельзя.

В примере три программы: два клиента, которые обмениваются данными через канал, и сервер, который создаёт канал, запускает обоих клиентов (дескрипторы отдаёт через поля STARTUPINFO) и сразу завершается. Оба клиента запускаются с ОДНОЙ и той же структурой STARTUPINFO, то есть у обоих стандартный ввод - это конец чтения ОДНОГО канала, а стандартный вывод - конец записи ТОГО ЖЕ канала. Канал по-прежнему один и очередь одна - так что снова нужен протокол очерёдности, и его задают два события, ReadFloat и ReadText.

Листинг 15.5 - процесс-клиент, записывающий данные в анонимный канал (собирается в Client1.exe):


Листинг 15.7 - процесс-сервер анонимного канала. Эта программа просто создаёт двух клиентов анонимного канала и прекращает свою работу:

```c
#include <windows.h>
#include <conio.h>

int main()
{
    char lpszComLine1[80] = "C:\\Client1.exe";      // имя первого клиента
    char lpszComLine2[80] = "C:\\Client2.exe";      // имя второго клиента

    STARTUPINFO si;
    PROCESS_INFORMATION pi;
    HANDLE hWritePipe, hReadPipe;
    SECURITY_ATTRIBUTES sa;

    // устанавливает атрибуты защиты канала
    sa.nLength = sizeof(SECURITY_ATTRIBUTES);
    sa.lpSecurityDescriptor = NULL;      // защита по умолчанию
    sa.bInheritHandle = TRUE;            // дескрипторы наследуемые

    // создаем анонимный канал
    if (!CreatePipe(
            &hReadPipe,    // дескриптор для чтения
            &hWritePipe,   // дескриптор для записи
            &sa,           // атрибуты защиты по умолчанию, дескрипторы наследуемые
            0))            // размер буфера по умолчанию
    {
        _cputs("Create pipe failed.\n");
        _cputs("Press any key to finish.\n");
        _getch();
        return GetLastError();
    }
    // устанавливаем атрибуты нового процесса
    ZeroMemory(&si, sizeof(STARTUPINFO));
    si.cb = sizeof(STARTUPINFO);
    // использовать стандартные дескрипторы
    si.dwFlags = STARTF_USESTDHANDLES;
    // устанавливаем стандартные дескрипторы
    si.hStdInput = hReadPipe;
    si.hStdOutput = hWritePipe;
    si.hStdError = hWritePipe;
```

Не скомпилировано по-настоящему (нет Windows) - проверено по документации и логике API. Механизм по шагам.

Сервер (листинг 15.7): создаёт канал с наследуемыми дескрипторами (sa.bInheritHandle = TRUE), заполняет STARTUPINFO: dwFlags = STARTF_USESTDHANDLES ("использовать стандартные дескрипторы"), hStdInput = дескриптор чтения канала, hStdOutput и hStdError = дескриптор записи канала. Дальше дважды подряд вызывает CreateProcess с ОДНОЙ и той же si и bInheritHandles = TRUE - для Client1.exe и Client2.exe. После каждого запуска закрывает дескрипторы процесса и потока (pi.hProcess, pi.hThread), в конце закрывает свои копии дескрипторов канала и завершается. Канал при этом не пропадает: объект ядра живёт, пока на него есть хотя бы один дескриптор, а клиенты свои уже унаследовали (глава 1: подсчёт ссылок на объект).

Клиенты: в них нет ни одного слова про канал. Они просто печатают в cout и читают из cin. А для сообщений пользователю используют _cputs/_cprintf/_getch из conio.h - потому что cout теперь ведёт в канал, а не на экран, и через него пользователю ничего не скажешь.

Оба клиента вызывают CreateEvent с одними и теми же именами ("ReadFloat", "ReadText"), а не OpenEvent. Кто стартовал раньше - создаёт событие, кто позже - получает дескриптор уже существующего события с тем же именем (это поведение CreateEvent для именованных объектов - общее знание, в книге не разбирается). Оба события с автосбросом (второй аргумент FALSE), в начале несигнальные (третий аргумент FALSE).

Ход событий (протокол очерёдности, ведь канал один):

1. Клиент 1 ждёт клавишу. После нажатия он раз в полсекунды пишет в канал целые числа 0-4 (cout << i << endl). Клиент 2 всё это время ждёт данные: cin >> nData блокируется, пока в канале ничего нет.
2. Клиент 2 прочитал пять целых, печатает их на своей консоли, ставит SetEvent(hReadFloat) ("теперь можно читать плавающие числа") и раз в полсекунды пишет 0, 0.1, 0.2, 0.3, 0.4.
3. Клиент 1 всё это время стоял на WaitForSingleObject(hReadFloat). Событие поставлено - он читает пять чисел и печатает их на консоли.
4. Клиент 1 прочитал числа, ставит SetEvent(hReadText) и пишет в канал строку "This is a demo sentence." и признак конца - символ '\0' с переводом строки.
5. Клиент 2 после записи чисел ждал WaitForSingleObject(hReadText). Дождался - читает слова по одному (cin >> lpszInput, пауза полсекунды перед каждым), печатает каждое на консоли, и останавливается, когда прочитанная строка пустая (первый символ '\0' - это как раз признак конца).

Чтобы понять, зачем события, представь, что их нет. Клиент 1 сразу после записи целых пошёл бы читать плавающие - но в очереди пока лежат ЕГО ЖЕ целые числа. Он прочитал бы их (разобрав как плавающие), и клиент 2 остался бы без данных. Событие тут - жетон очереди: тот, кто начинает читать, обязан сначала получить разрешение от того, кто закончил писать.

Про endl: это не просто перевод строки, а ещё и сброс буфера cout (общее знание C++, не из книги). Без сброса написанное могло бы задержаться в буфере программы и не доехать до другого процесса вовремя.

Ожидаемое поведение (рассуждение по логике, НЕ проверенный вывод). На консоли сервера: "The clients are created." и "Press any key to exit.". У клиента 1 всё, что он пишет через cout, в канал, поэтому на экране только сообщения conio: "Press any key to start communication." и после этого (примерно через 2.5 + 2.5 секунды) пять строк "The number 0.0 is read from the pipe." ... "The number 0.4 is read from the pipe.", "The process finished transmission of data.", "Press any key to exit.". У клиента 2 сначала (пока клиент 1 не нажал клавишу) экран пуст, потом пять строк "The number 0 is read from the pipe." ... "The number 4 is read from the pipe.", затем строка "The process read the text: This is a demo sentence. " (слова появляются по одному через полсекунды), и ниже "The process finished transmission of data." и "Press any key to exit.". Выводы "0.0" ... "0.4" получаются из формата %2.1f в _cprintf.

Частые путаницы и ошибки

Путают, кто "сервер", а кто "клиент" канала, с тем, кто пишет и кто читает. Сервер - тот, кто создал канал (вызвал CreatePipe), клиент - тот, кто присоединился (унаследовал дескриптор). Данные могут идти в любую сторону: в листингах 15.1-15.2 - от клиента к серверу.

Думают, что "полудуплексный" значит "процесс может только писать ИЛИ только читать". Ограничение относится к дескриптору: дескриптор записи только пишет, дескриптор чтения только читает. Процесс, у которого на руках оба дескриптора, может и писать, и читать.

Считают, что двусторонний обмен по анонимному каналу - это "два канала в одном". Канал один, очередь в нём одна. Если и сервер, и клиент читают из него, то тот, кто вызовет ReadFile первым, заберёт байты - даже если их писал он сам. Отсюда - обязательный протокол очерёдности (события в листингах 15.4 и 15.5-15.6), иначе читатель заберёт не своё или зависнет. Для двусторонней связи без такой очерёдности естественнее два отдельных канала (мой вывод, не из книги).

Забывают, что "наследуемый дескриптор" - только разрешение. Чтобы клиент реально им воспользовался, нужно все три условия из главы 4: дескриптор наследуемый (bInheritHandle = TRUE или наследуемый дубликат), bInheritHandles = TRUE в CreateProcess, значение дескриптора передано клиенту (командная строка или поля hStdInput/hStdOutput/hStdError). Передать дескриптор неродственному процессу так нельзя: у каждого процесса своя таблица дескрипторов, наследование работает только от родителя к потомкам.

Забывают закрывать ненужные копии дескрипторов. В листинге 15.2 сервер закрывает и исходный ненаследуемый дескриптор записи, и свою наследуемую копию после запуска клиента - они ему больше не нужны. Общее знание (в книге не разбирается): если в системе остаётся открытым хотя бы один дескриптор записи в канал, читатель никогда не получит признак "данных больше не будет" (ReadFile завершается с ошибкой ERROR_BROKEN_PIPE только когда закрыты ВСЕ дескрипторы записи) и может зависнуть, ожидая данных, которых уже не будет.

Смешивают бинарную и текстовую передачу. WriteFile(&i, sizeof(i)) кладёт в канал 4 байта самого числа, cout << i - символы текста. Читающая сторона обязана читать тем же способом (ReadFile в int против cin >> int). Ещё пример: в листинге 15.6 плавающее число 0.3 уезжает в канал как текст "0.3", а не как 4 или 8 байтов.

Пишут сообщения пользователю через cout/printf в программе с перенаправленным выводом. Они уедут в канал, а не на экран. Для общения с консолью в таких программах используют conio.h (_cputs, _cprintf, _getch).

Забывают флаг STARTF_USESTDHANDLES. Без него поля hStdInput/hStdOutput/hStdError в STARTUPINFO игнорируются, и перенаправление не сработает - клиент по-прежнему будет читать клавиатуру и писать на свою консоль.

Ссылка из главы 10 ("подробнее в главе 13") ведёт не туда: перенаправление стандартного ввода-вывода разобрано в разделе 15.6.

Опечатки самой книги в этой главе (чтобы не путаться): в прототипе CreatePipe параметры названы hReadHandle/hWriteHandle, а в тексте - hReadPipe/hWritePipe; в прототипе ReadFile буфер назван LPCVOID (по смыслу он выходной, LPVOID), а комментарии к двум его параметрам скопированы с WriteFile; в тексте "прочитанных функцией WriteFile" вместо ReadFile.

Итог: какие функции и для чего

- CreatePipe - создать анонимный канал, получить два дескриптора (чтения и записи); в lpPipeAttributes решается вопрос наследуемости;
- WriteFile / ReadFile - записать в канал / прочитать из канала (lpOverlapped всегда NULL: анонимные каналы только синхронные);
- CloseHandle - закрыть дескриптор канала;
- DuplicateHandle / SetHandleInformation - изменить наследуемость уже созданного дескриптора (Windows 98 / Windows 2000, глава 4);
- CreateProcess с bInheritHandles = TRUE - создать клиента, который наследует дескрипторы;
- поля hStdInput, hStdOutput, hStdError структуры STARTUPINFO и флаг STARTF_USESTDHANDLES - перенаправить стандартный ввод-вывод клиента в канал;
- CreateEvent / OpenEvent / SetEvent / WaitForSingleObject - события для протокола очерёдности (глава 6).
