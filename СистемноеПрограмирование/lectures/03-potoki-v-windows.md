Глава 3. Потоки в Windows

Суть

Поток - это то, что реально выполняется процессором внутри программы. В главе 2 поток разбирался абстрактно, как понятие операционных систем вообще. Здесь то же самое, но конкретно на Win32 API: какими функциями создать поток, остановить его, поставить на паузу, и что делать, если функция вернула ошибку. Всё, что описано в этой главе, реально пишется на C/C++ и компилируется под Windows.

3.1 Определение потока

Поток в Windows - это объект ядра (то есть сущность, которой управляет сама операционная система, а не твоя программа), которому ОС выделяет процессорное время. У каждого потока есть свой набор ресурсов:
- код исполняемой функции - какую именно функцию поток выполняет
- набор регистров процессора - в них поток хранит свои текущие промежуточные значения, отдельно от других потоков
- стек для работы приложения - память для локальных переменных и вызовов функций твоей программы
- стек для работы операционной системы - отдельный стек, которым пользуется сама ОС, когда обрабатывает системные вызовы этого потока
- маркер доступа - информация о том, что этому потоку разрешено делать с точки зрения безопасности (подробно эта тема будет в отдельной главе про безопасность)

Всё это вместе называется контекстом потока. Плюс у потока есть идентификатор (thread ID) - число, уникальное для всех потоков системы, по которому системные утилиты могут отследить конкретный поток.

Потоки различаются по происхождению:
- системные потоки - их создаёт сама ОС для своих внутренних сервисов
- пользовательские потоки - их создают обычные приложения

И по роли внутри приложения:
- рабочие потоки (working threads) - выполняют фоновую работу
- потоки интерфейса пользователя (user interface threads) - обрабатывают окна и сообщения от них

У любого приложения обязательно есть хотя бы один поток - главный (primary или main), с которого всё начинается. В консольном приложении это поток, который выполняет функцию main. В приложении с окнами - тот, что выполняет WinMain.

Пока поток живёт, он переходит между несколькими состояниями (в книге это рис. 3.1, модель для Windows 2000):
- готов - поток может выполняться, ждёт своей очереди у планировщика
- выбран - планировщик уже выбрал именно этот поток следующим на выполнение, это промежуточный шаг перед стартом
- выполняется - поток реально работает на процессоре прямо сейчас
- ждёт - поток сам остановился и ждёт какого-то события или ресурса
- ждёт ресурс - поток ждал ресурс, а тот, как назло, оказался занят кем-то другим, приходится ждать ещё и освобождения ресурса
- завершён - поток закончил работу

Переходы между ними управляются планировщиком ОС: готов переходит в выбран, когда подходит очередь (планировщик выбрал именно его); выбран переходит в выполняется в момент переключения контекста; выполняется возвращается в готов, если процессор отобрали в пользу другого потока (вытеснение); выполняется переходит в ждёт, если поток сам заблокировался в ожидании чего-то; из ждёт можно попасть обратно в готов, если дождался, либо в ждёт ресурс, если вдобавок оказалось, что нужный ресурс ещё и занят - а оттуда снова в готов, когда ресурс освободится.

3.2 Создание потоков

Поток создаётся функцией CreateThread:

```
HANDLE CreateThread(
    LPSECURITY_ATTRIBUTES lpThreadAttributes,  // атрибуты защиты
    DWORD dwStackSize,                          // размер стека потока в байтах
    LPTHREAD_START_ROUTINE lpStartAddress,      // адрес функции
    LPVOID lpParameter,                         // адрес параметра
    DWORD dwCreationFlags,                      // флаги создания потока
    LPDWORD lpThreadId                          // идентификатор потока
);
```

Если всё прошло успешно, функция возвращает дескриптор (handle) нового потока - это число-ссылка, по которому дальше можно управлять этим потоком: ждать его, останавливать, закрывать. Если не получилось - возвращает NULL.

Разберём параметры по одному, почти в каждом есть нюанс:

lpThreadAttributes - атрибуты защиты создаваемого потока. Пока не разбирали систему безопасности Windows - передавай NULL, тогда ОС сама поставит настройки по умолчанию.

dwStackSize - сколько байт выделить под стек потока. 0 значит взять размер по умолчанию (1 мегабайт). Если указать меньше - Windows всё равно даст минимум 1 мегабайт. Итоговый размер округляется вверх до размера страницы памяти (обычно 4 килобайта) - это связано с тем, как устроена работа с виртуальной памятью, отдельная большая тема дальше в книге.

lpStartAddress - указатель на функцию, которую будет исполнять поток. У функции обязательно должна быть строго определённая сигнатура:

```
DWORD WINAPI имя_функции_потока(LPVOID lpParameters);
```

Почему сигнатура жёстко зафиксирована: эту функцию вызывает не твой код, а сама операционная система, отсюда и название - функция обратного вызова (callback). ОС сама тоже исполняемый модуль и может вызывать только функции с заранее известной, одинаковой для всех сигнатурой. Поэтому у функции потока может быть только один параметр - указатель void*, через который можно передать что угодно, хоть указатель на структуру с кучей полей.

dwCreationFlags - в каком состоянии создать поток. 0 значит поток стартует сразу. CREATE_SUSPENDED значит поток создаётся, но не запускается, стоит на паузе; чтобы его запустить, нужно потом отдельно вызвать ResumeThread (см. 3.4).

lpThreadId - выходной параметр: передаёшь адрес переменной, а Windows сама туда запишет идентификатор нового потока. Этот ID уникален, пока поток жив; после завершения потока тот же номер может достаться другому. В Windows NT/2000 сюда можно передать NULL, если идентификатор не нужен, а в Windows 98 нельзя - там обязательно нужен реальный адрес переменной.

Пример из книги, создание потока, который в фоне прибавляет число к глобальной переменной:

```c
#include <windows.h>
#include <iostream.h>

volatile int n;

DWORD WINAPI Add(LPVOID iNum)
{
    cout << "Thread is started." << endl;
    n += (int)iNum;
    cout << "Thread is finished." << endl;
    return 0;
}

int main()
{
    int inc = 10;
    HANDLE hThread;
    DWORD IDThread;

    cout << "n = " << n << endl;
    // запускаем поток Add
    hThread = CreateThread(NULL, 0, Add, (void*)inc, 0, &IDThread);
    if (hThread == NULL)
        return GetLastError();

    // ждем, пока поток Add закончит работу
    WaitForSingleObject(hThread, INFINITE);
    // закрываем дескриптор потока Add
    CloseHandle(hThread);

    cout << "n = " << n << endl;
    return 0;
}
```

WaitForSingleObject тут блокирует текущий поток, пока не завершится тот, чей дескриптор ей передали (INFINITE значит "жди сколько угодно"). Подробно эта функция разбирается позже, в разделе 6.2 про объекты синхронизации. После того как поток отработал и дескриптор больше не нужен, его закрывают через CloseHandle - иначе дескриптор "утечёт", останется висеть и занимать ресурсы даже после того, как сам поток уже завершился.

Отдельное практическое замечание из книги: чтобы такая программа собралась и корректно отладилась как многопоточная, в Visual C++ 6.0 нужно в настройках проекта (Project - Settings - вкладка C/C++ - категория Code Generation - список Use run-time library) выбрать Debug Multithreaded (или просто Multithreaded для release-сборки). Без этого возможны проблемы из-за того, что библиотека времени выполнения C по умолчанию не рассчитана на то, что её вызывают параллельно из нескольких потоков.

Кроме CreateThread есть ещё один способ - макрокоманда _beginthreadex (описана в заголовочном файле process.h), с теми же параметрами, что и CreateThread. Книга ссылается на Джеффри Рихтера, автора известной книги про программирование под Windows: он рекомендует использовать именно _beginthreadex, а не CreateThread напрямую, потому что она надёжнее - правильно готовит внутренние структуры библиотеки времени выполнения C для этого потока, с которыми у "голого" CreateThread могут быть проблемы. Для завершения такого потока используется парный макрос _endthreadex (см. 3.3).

3.3 Завершение потоков

Есть два принципиально разных способа завершить поток - "по-хорошему" и "по-плохому".

По-хорошему - функция ExitThread:

```
VOID ExitThread(
    DWORD dwExitCode  // код завершения потока
);
```

Её можно вызвать явно, а можно просто выйти из функции потока через return - это одно и то же. При таком завершении система корректно уведомляет все динамические библиотеки (DLL), загруженные в процессе, сообщением DLL_THREAD_DETACH - что поток завершается, и они могут освободить всё, что держали ради этого потока.

Если поток был создан через _beginthreadex, для завершения нужно использовать не ExitThread, а парный _endthreadex. Разница важная: _endthreadex не просто завершает поток, но и освобождает память, которую при создании потока выделила _beginthreadex. Если про это забыть, память утечёт.

По-плохому - один поток может насильно прибить другой функцией TerminateThread:

```
BOOL TerminateThread(
    HANDLE hThread,     // дескриптор потока
    DWORD dwExitThread  // код завершения потока
);
```

Возвращает ненулевое значение при успехе, FALSE при неудаче. Проблема в том, что TerminateThread обрывает поток мгновенно, без всякого уведомления DLL - сообщение DLL_THREAD_DETACH не приходит, и все ресурсы, которые библиотеки держали ради этого потока, не освобождаются. Поэтому TerminateThread - крайняя мера на случай, когда поток завис и другого выхода нет, а не обычный способ остановить поток.

В примере из книги есть важная деталь - ключевое слово volatile перед переменной count:

```c
volatile UINT count;

void thread()
{
    for (;;)
    {
        ++count;
        Sleep(100);  // немного отдохнем
    }
}
```

Зачем нужен volatile: компилятор C/C++ ничего не знает про потоки - для него это просто функции, а обычный код вызывается строго синхронно (вызвал функцию - дождался, пока вернёт управление). Поэтому компилятор без всякого злого умысла может "соптимизировать" код и держать значение переменной не в оперативной памяти, а в регистре процессора. Если так сделать с переменной, к которой параллельно обращаются несколько потоков, каждый поток может работать со своей отдельной копией значения в своём регистре и не видеть изменений, которые сделал другой поток. volatile - это указание компилятору: не оптимизируй, всегда читай и пиши эту переменную напрямую в память, потому что её могут менять "снаружи", в обход обычной логики этого куска кода.

3.4 Приостановка и возобновление потоков

У каждого потока есть счётчик приостановок. Пока этот счётчик больше нуля, поток не выполняется - находится в подвешенном состоянии. Максимальное значение счётчика - константа MAXIMUM_SUSPEND_COUNT.

Поставить поток на паузу - функция SuspendThread:

```
DWORD SuspendThread(
    HANDLE hThread  // дескриптор потока
);
```

Она увеличивает счётчик приостановок на 1 и возвращает предыдущее значение счётчика. При ошибке возвращает -1. Поток может приостановить и сам себя, если передаст сюда свой псевдодескриптор (см. 3.5).

Снять с паузы - функция ResumeThread:

```
DWORD ResumeThread(
    HANDLE hThread  // дескриптор потока
);
```

Она уменьшает счётчик приостановок на 1, если он был больше нуля. Если после уменьшения счётчик дошёл до 0, поток реально возобновляет выполнение. Если счётчик и так был 0, функция ничего не делает. Возвращает предыдущее значение счётчика либо -1 при ошибке.

Важный момент: раз это именно счётчик, а не переключатель "пауза/не пауза" - если поток приостановили дважды подряд (счётчик стал 2), одного ResumeThread не хватит, поток реально заработает только после второго вызова ResumeThread, когда счётчик дойдёт до 0.

Ещё один способ временно притормозить поток - Sleep:

```
VOID Sleep(
    DWORD dwMilliseconds  // миллисекунды
);
```

Это не то же самое, что SuspendThread. Sleep - это когда сам поток добровольно говорит "я подожду столько-то миллисекунд", а не кто-то снаружи ставит его на паузу. Если передать 0, поток просто уступает очередь на процессор другим потокам, которые готовы выполняться, и сам сразу же возвращается в очередь. Если передать INFINITE, поток засыпает навсегда, и если это был единственный поток приложения - всё приложение зависает.

3.5 Псевдодескрипторы потоков

Иногда потоку нужен свой собственный дескриптор - например, чтобы изменить свой же приоритет или вызвать для себя SuspendThread. Для этого есть функция:

```
HANDLE GetCurrentThread(VOID);
```

Она возвращает не настоящий дескриптор, а псевдодескриптор текущего потока. Отличия от настоящего дескриптора:
- псевдодескриптор годится только для того, чтобы поток обращался сам к себе - передать его другому процессу или потоку и получить от этого пользу нельзя
- его нельзя унаследовать другим процессам, в отличие от обычного дескриптора
- его не нужно закрывать через CloseHandle после использования, он не занимает отдельный ресурс, который надо освобождать

Если всё же нужен настоящий дескриптор этого потока, например чтобы передать его другому процессу, из псевдодескриптора его можно получить функцией DuplicateHandle. Дублирование дескрипторов подробно разбирается в главе 4.

3.6 Обработка ошибок в Windows

Почти все функции Win32 API возвращают код результата, по которому видно, получилось или нет: обычно это FALSE, NULL или -1 при неудаче. Но кроме этого возвращаемого значения, при ошибке функция ещё и запоминает код последней ошибки (last-error code) - причём отдельно для каждого потока: если у тебя несколько потоков одновременно ловят ошибки, они друг другу не мешают, у каждого свой код.

Забрать код последней ошибки:

```
DWORD GetLastError(VOID);
```

Установить его вручную, редко нужно, но иногда полезно:

```
VOID SetLastError(
    DWORD dwErrCode  // код ошибки
);
```

Сам по себе код ошибки - просто число, по нему не сразу понятно, что случилось. Чтобы превратить его в текст, есть функция FormatMessage:

```
DWORD FormatMessage(
    DWORD dwFlags,        // режимы форматирования
    LPCVOID lpSource,     // источник сообщения
    DWORD dwMessageId,    // идентификатор сообщения
    DWORD dwLanguageId,   // идентификатор языка
    LPTSTR lpBuffer,      // буфер для сообщения
    DWORD nSize,          // максимальный размер буфера
    va_list *Arguments    // список значений для вставки в сообщение
);
```

На практике для простого случая "покажи текст ошибки" не нужно разбираться во всех этих параметрах - используется готовый шаблон вызова, как в примере ниже: просим Windows сама выделить буфер под текст (флаг FORMAT_MESSAGE_ALLOCATE_BUFFER), взять текст из системных сообщений (FORMAT_MESSAGE_FROM_SYSTEM), передаём код последней ошибки через GetLastError(), просим язык по умолчанию, а после использования обязательно освобождаем буфер функцией LocalFree - раз Windows сама его выделила, освобождать нужно особым способом, не обычным delete или free.

```c
void ErrorMessageBox()
{
    LPVOID lpMsgBuf;

    FormatMessage(
        FORMAT_MESSAGE_ALLOCATE_BUFFER |
        FORMAT_MESSAGE_FROM_SYSTEM |
        FORMAT_MESSAGE_IGNORE_INSERTS,
        NULL,
        GetLastError(),
        MAKELANGID(LANG_NEUTRAL, SUBLANG_DEFAULT),  // язык по умолчанию
        (LPTSTR) &lpMsgBuf,
        0,
        NULL
    );
    // Показать ошибку в MessageBox.
    MessageBox(
        NULL,
        (LPCTSTR)lpMsgBuf,
        "Ошибка Win32 API",
        MB_OK | MB_ICONINFORMATION
    );
    // Освободить буфер.
    LocalFree(lpMsgBuf);
}
```

Дальше книга показывает, как вывести такое же сообщение об ошибке не в окошко (MessageBox), а прямо на консоль, да ещё и по-русски. Тут всплывает отдельная проблема: чтобы русский текст нормально отображался именно в консольном окне Windows, буквы нужно перекодировать функцией CharToOem:

```
BOOL CharToOem(
    LPCTSTR lpszSrc,  // строка для перекодировки
    LPSTR lpszDst      // перекодированная строка
);
```

Дело в том, что у Windows исторически два разных набора кодировок для кириллицы: один для обычных окон и программ (кодировка Microsoft, она же ANSI), другой для консоли и старого оборудования (кодировка OEM, аббревиатура расшифровывается как Original Equipment Manufacturer - "производитель оборудования"). Без перекодировки русский текст в консоли превращается в нечитаемую кашу из символов. CharToOem как раз переводит строку из одной кодировки в другую.

Собрав FormatMessage, CharToOem и вывод на консоль вместе, в книге получается готовая функция CoutErrorMessage - удобный многоразовый кусок кода для любого консольного проекта на Win32 API:

```c
void CoutErrorMessage()
{
    char prefix[] = "Ошибка Win32 API: ";
    LPVOID lpMsgBuf;

    CharToOem(prefix, prefix);  // перекодируем заголовок

    FormatMessage(
        FORMAT_MESSAGE_ALLOCATE_BUFFER |
        FORMAT_MESSAGE_FROM_SYSTEM |
        FORMAT_MESSAGE_IGNORE_INSERTS,
        NULL,
        GetLastError(),
        MAKELANGID(LANG_NEUTRAL, SUBLANG_DEFAULT),  // язык по умолчанию
        (LPTSTR) &lpMsgBuf,
        0,
        NULL
    );
    // перекодируем русские буквы
    CharToOem((char*)lpMsgBuf, (char*)lpMsgBuf);
    // выводим сообщение об ошибке на консоль
    cout << prefix << (char*)lpMsgBuf << endl;
    // освобождаем буфер
    LocalFree(lpMsgBuf);
}
```

Отдельно книга упоминает приём для отладчика: если во время отладки в окне watch (просмотр переменных) написать в поле "имя переменной" текст @err,hr, отладчик сам покажет текст последней ошибки, без необходимости руками звать FormatMessage.

Частые ошибки и путаницы

- Путают CreateThread и _beginthreadex. Если в потоке используются функции стандартной библиотеки C (например strtok, как в примере из книги, или вообще что угодно с внутренним состоянием) - надёжнее _beginthreadex/_endthreadex, а не голый CreateThread/ExitThread.
- Забывают закрыть дескриптор потока после CreateThread через CloseHandle. Дескриптор - отдельный ресурс, он не закрывается сам по себе, даже когда поток уже завершился.
- Используют TerminateThread как обычный способ остановить поток. Это аварийная функция: она не уведомляет DLL о завершении потока, и ресурсы, которые эти библиотеки держали, повиснут. Нормальный способ - дать потоку самому дойти до return или ExitThread.
- Забывают volatile у переменных, к которым обращаются несколько потоков одновременно. Без этого компилятор может закэшировать значение переменной в регистре процессора, и один поток не увидит изменений, сделанных другим.
- Путают счётчик приостановок с логическим флагом. SuspendThread можно вызвать несколько раз подряд, и тогда потребуется столько же вызовов ResumeThread, чтобы поток реально заработал - это именно счётчик, а не переключатель "вкл/выкл".
- Путают псевдодескриптор с настоящим. Псевдодескриптор от GetCurrentThread работает только "для себя" - его нельзя передать в другой процесс и рассчитывать, что он там будет ссылаться на тот же поток. Для этого нужен реальный дескриптор через DuplicateHandle.
- Забывают, что код последней ошибки свой у каждого потока. Если поток A вызвал функцию с ошибкой, а поток B в этот момент позвал GetLastError, он получит код своей последней ошибки, а не ошибки потока A.
