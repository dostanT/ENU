Глава 16. Работа с именованными каналами в Windows

Суть

Именованный канал - это "телефонная линия с номером". У линии есть имя (например, \\.\pipe\demo_pipe), и позвонить по нему может ЛЮБОЙ процесс, который это имя знает и у которого есть права, - не только дочерний, как у анонимного канала из главы 15. Причём звонить можно и с другого компьютера локальной сети. Канал может быть двусторонним, передавать данные либо сплошным потоком байтов, либо отдельными сообщениями, работать синхронно или асинхронно.

Цена за такую гибкость - больше действий. Сервер не просто создаёт трубу, а создаёт "экземпляры" канала (по одному на каждого клиента), поднимает трубку и ждёт звонка, потом обслуживает клиента и отсоединяется. Клиент ищет свободный экземпляр и открывает его почти как обычный файл. Структура главы по самой книге: сначала характеристики и функции передачи данных (16.1-16.5), потом примеры (листинги 16.1-16.5), потом служебные функции для работы с каналами (16.6-16.9, листинги 16.6-16.11).

16.1 Именованные каналы

Определение книги: именованным каналом называется объект ядра операционной системы, который обеспечивает передачу данных между процессами, выполняющимися на компьютерах в одной локальной сети. Процесс, который создаёт канал, - сервер именованного канала. Процессы, которые связываются с ним, - клиенты.

Характеристики (ответ на "карточку" из главы 14):

- имеют имя, по которому клиенты связываются с каналом;
- бывают и полудуплексные, и дуплексные;
- передача данных может идти и потоком, и сообщениями;
- обмен может быть и синхронным, и асинхронным;
- возможность моделировать любую топологию связей.

Сравни с анонимным каналом (глава 15): у того имени нет, направление только одно (полудуплекс), передача только потоком, обмен только синхронный, работает на одном компьютере, а доступ есть только у родителя и потомков. Именованный канал снимает почти все эти ограничения. В Windows NT анонимный канал вообще реализован как именованный с уникальным именем - поэтому функции этой главы работают и с анонимными.

Порядок работы с именованными каналами, которого книга дальше придерживается (в самой книге в этом списке первый пункт закончен двоеточием - это опечатка):

1. создание именованного канала сервером;
2. соединение сервера с экземпляром именованного канала;
3. соединение клиента с экземпляром именованного канала;
4. обмен данными по именованному каналу;
5. отсоединение сервера от экземпляра именованного канала;
6. закрытие именованного канала клиентом и сервером.

Слово "экземпляр" здесь ключевое, и пока оно непонятно. Картинка из жизни: колл-центр с одним городским номером. Номер (имя канала) один, а операторов (экземпляров) может быть несколько; каждый оператор в каждый момент разговаривает только с одним звонящим. Если у центра один оператор, второй звонящий будет ждать. Так и здесь: имя одно, а экземпляров канала столько, сколько клиентов сервер хочет обслуживать одновременно, и каждый экземпляр обслуживает одного клиента. Об этом ещё раз в разделе 16.2.

Схема жизни одного экземпляра (по шагам 1-6 выше, с функциями):

```
сервер:  CreateNamedPipe          создал экземпляр, он свободен
сервер:  ConnectNamedPipe         поднял трубку, ждёт клиента
клиент:  WaitNamedPipe            (по желанию) ждёт, пока найдётся свободный экземпляр
клиент:  CreateFile               открыл экземпляр - связь установлена
обе:     ReadFile / WriteFile     обмен данными
сервер:  DisconnectNamedPipe      положил трубку - экземпляр свободен для следующего клиента
обе:     CloseHandle              закрыли дескрипторы
```

16.2 Создание именованных каналов

Пример из жизни: открываешь колл-центр. Нужно решить: какой номер телефона, кто кому звонит (только принимаем звонки, только делаем или и то, и другое), говорят сплошным потоком или отдельными репликами-сообщениями, ждут ли на линии, сколько операторов, какой размер блокнотов для записей, сколько ждать ответа и кому вообще можно звонить. Ровно эти решения и задаёт функция CreateNamedPipe, которую вызывает процесс-сервер:

```
HANDLE CreateNamedPipe(
    LPCTSTR lpName,                          // имя канала
    DWORD   dwOpenMode,                      // атрибуты канала
    DWORD   dwPipeMode,                      // режим передачи данных
    DWORD   nMaxInstances,                   // максимальное количество экземпляров канала
    DWORD   nOutBufferSize,                  // размер выходного буфера
    DWORD   nInBufferSize,                   // размер входного буфера
    DWORD   nDefaultTimeOut,                 // время ожидания связи с клиентом
    LPSECURITY_ATTRIBUTES lpPipeAttributes   // атрибуты безопасности
);
```

Возврат. При успехе - дескриптор именованного канала (точнее, экземпляра). При неудаче книга называет два значения: INVALID_HANDLE_VALUE (неудача вообще) и ERROR_INVALID_PARAMETR - когда nMaxInstances больше, чем PIPE_UNLIMITED_INSTANCES (в книге слово написано с опечаткой, правильно ERROR_INVALID_PARAMETER). Общее знание, не из книги: на самом деле функция возвращает только INVALID_HANDLE_VALUE, а код ERROR_INVALID_PARAMETER можно получить потом через GetLastError.

Параметры.

lpName - имя канала. Строка вида:

```
\\.\pipe\pipe_name
```

Здесь "." означает локальную машину (новый именованный канал всегда создаётся на локальной машине), слово pipe фиксированное, а pipe_name - имя канала, которое придумывает пользователь; оно нечувствительно к регистру. В коде на C надо не забыть удвоить обратные косые черты: "\\\\.\\pipe\\demo_pipe" (как в листингах).

dwOpenMode - флаги, которые определяют направление передачи данных, буферизацию, синхронизацию и права доступа. Направление:

- PIPE_ACCESS_DUPLEX - чтение и запись в канал (двусторонний);
- PIPE_ACCESS_INBOUND - клиент пишет, а сервер читает;
- PIPE_ACCESS_OUTBOUND - сервер пишет, а клиент читает.

Кроме того, каждый из этих флагов позволяет использовать дескриптор канала для синхронизации (то есть ждать на нём функциями ожидания из главы 6). Флаг направления должен совпадать для всех экземпляров одного и того же канала.

Буферизация и синхронизация:

- FILE_FLAG_WRITE_THROUGH - запрещает буферизацию при передаче данных по сети;
- FILE_FLAG_OVERLAPPED - разрешает асинхронную передачу данных по каналу.

Эти два флага могут быть разными у разных экземпляров одного канала.

Про права доступа книга здесь коротко (подробно - разделы 36.7 и 41.3, часть XI про безопасность): три флага направления определяют специфические права доступа, которые включают родовые права. PIPE_ACCESS_DUPLEX включает GENERIC_READ, GENERIC_WRITE и SYNCHRONIZE; PIPE_ACCESS_INBOUND - GENERIC_READ и SYNCHRONIZE; PIPE_ACCESS_OUTBOUND - GENERIC_WRITE и SYNCHRONIZE. Смысл в том, что выбор направления заодно решает, что сервер вообще может делать со своим концом канала: у сервера, читающего клиента (INBOUND), есть право чтения, у сервера, пишущего клиенту (OUTBOUND), - право записи.

dwPipeMode - флаги, задающие способ передачи данных. Способ записи и чтения:

- PIPE_TYPE_BYTE - запись данных потоком;
- PIPE_TYPE_MESSAGE - запись данных сообщениями;
- PIPE_READMODE_BYTE - чтение данных потоком;
- PIPE_READMODE_MESSAGE - чтение данных сообщениями.

(В тексте книги последние два флага напечатаны как PYPE_READMODE_... - опечатка, правильно PIPE_READMODE_...) По умолчанию данные передаются потоком. Флаги, определяющие способ чтения и записи, должны совпадать для всех экземпляров одного канала. Способ ожидания:

- PIPE_WAIT - синхронная связь с каналом и обмен данными (вызвал - ждёшь результата);
- PIPE_NOWAIT - асинхронная связь с каналом и обмен данными (так в книге; функции не ждут, а сразу возвращают управление).

Эти два флага могут быть разными для каждого экземпляра.

Запомни разницу между "типом" и "режимом чтения": PIPE_TYPE_* говорит, как данные ПИШУТСЯ в канал, а PIPE_READMODE_* - как они ЧИТАЮТСЯ. Это две отдельные настройки.

nMaxInstances - максимальное число экземпляров канала, от 1 до PIPE_UNLIMITED_INSTANCES (последнее значит "сколько угодно, пока хватает ресурсов системы"). Каждый экземпляр предназначен для обмена данными между сервером и ОТДЕЛЬНЫМ клиентом.

nOutBufferSize и nInBufferSize - размеры выходного и входного буферов канала. Как и с dwSize у анонимного канала - это только пожелание, окончательный размер выбирает система (в листингах везде 0 - "по умолчанию").

nDefaultTimeOut - время ожидания клиентом связи с сервером. Оно используется, когда клиент вызывает WaitNamedPipe (16.4) со значением nTimeOut равным NMPWAIT_USE_DEFAULT_WAIT.

lpPipeAttributes - атрибуты безопасности: кто вообще имеет право связываться с каналом. NULL - защита по умолчанию (канал принадлежит только пользователю, который его создал; последствия - в примерах 16.3-16.5).

Как сделать канал для нескольких клиентов. Для связи сервера с несколькими клиентами по одному имени сервер должен создать несколько экземпляров этого канала. Каждый экземпляр создаётся своим вызовом CreateNamedPipe (с тем же lpName), который возвращает дескриптор именно этого экземпляра. При этом поток, создающий экземпляр, должен иметь право доступа FILE_CREATE_PIPE_INSTANCE к каналу; по умолчанию это право есть у владельца канала, то есть у того процесса, который канал создал.

16.3 Соединение сервера с клиентом

Создать канал - ещё не значит быть на связи. Как в колл-центре: поставили телефон, но пока не подняли трубку, разговора нет. Сервер должен дождаться, пока клиент присоединится к экземпляру. Для этого вызывается ConnectNamedPipe:

```
BOOL ConnectNamedPipe(
    HANDLE       hNamedPipe,     // дескриптор канала
    LPOVERLAPPED lpOverlapped    // асинхронная связь
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Параметры: hNamedPipe - дескриптор экземпляра, полученный от CreateNamedPipe; lpOverlapped - структура для асинхронной связи, а при синхронной связи (как в листингах этой главы) NULL. Сервер вызывает эту функцию для КАЖДОГО свободного экземпляра. При синхронной связи функция не возвращает управление, пока клиент не присоединится.

После окончания обмена сервер может разорвать связь с клиентом функцией DisconnectNamedPipe:

```
BOOL DisconnectNamedPipe(
    HANDLE hNamedPipe    // дескриптор канала
);
```

Возвращает ненулевое значение при успехе, FALSE при неудаче. Эта функция разрывает связь сервера с клиентом: после неё клиент уже не может обмениваться данными по этому каналу, и ЛЮБАЯ его операция с каналом вызовет ошибку. Зато после разрыва сервер снова может вызвать ConnectNamedPipe и установить связь по этому же экземпляру с ДРУГИМ клиентом - это и есть способ переиспользовать экземпляр по очереди для разных клиентов.

16.4 Соединение клиентов с именованным каналом

Клиент не знает, свободна ли линия. Поэтому, прежде чем "звонить", он проверяет, доступен ли какой-либо экземпляр канала для соединения. Для этого служит WaitNamedPipe:

```
BOOL WaitNamedPipe(
    LPCTSTR lpNamedPipeName,    // указатель на имя канала
    DWORD   nTimeOut            // интервал ожидания
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Параметры.

lpNamedPipeName - имя канала. Здесь уже нужен формат с именем компьютера:

```
\\server_name\pipe\pipe_name
```

server_name - имя компьютера, на котором работает сервер канала, слово pipe фиксированное, pipe_name - имя канала (то самое, которое сервер задал в CreateNamedPipe). Заметь разницу с серверной стороной: там "." (локальная машина), тут имя машины, где живёт сервер.

nTimeOut - сколько ждать связи, в миллисекундах, либо одно из специальных значений: NMPWAIT_USE_DEFAULT_WAIT (ждать столько, сколько указано в nDefaultTimeOut при создании канала) или NMPWAIT_WAIT_FOREVER (ждать бесконечно).

Два замечания книги про WaitNamedPipe.

- Если не существует НИ ОДНОГО экземпляра канала с таким именем, функция сразу завершается неудачей, независимо от заданного времени ожидания. Ждать имеет смысл, только если канал уже создан, но все экземпляры заняты.
- Если клиент соединяется с каналом ДО того, как сервер вызвал ConnectNamedPipe, то WaitNamedPipe возвращает FALSE, а GetLastError вернёт ERROR_PIPE_CONNECTED. Поэтому, по книге, WaitNamedPipe нужно вызывать только ПОСЛЕ того, как сервер связался с каналом функцией ConnectNamedPipe. (Общее знание, не из книги: в документации Windows код ERROR_PIPE_CONNECTED описан как результат ConnectNamedPipe на стороне сервера - "клиент уже подключился раньше, чем сервер вызвал функцию" - и означает, что связь на самом деле хорошая. Если писать сервер по-настоящему, этот код стоит считать успехом.)

Когда свободный экземпляр найден, клиент устанавливает связь функцией CreateFile - той самой, что открывает обычные файлы. Идея: именованный канал ведёт себя как файл с особым именем, поэтому "открыть канал" - это "открыть файл по имени \\server\pipe\name".

```
HANDLE CreateFile(
    LPCTSTR lpFileName,                        // указатель на имя канала
    DWORD   dwDesiredAccess,                   // чтение или запись в канал
    DWORD   dwShareMode,                       // режим совместного использования
    LPSECURITY_ATTRIBUTES lpSecurityAttributes, // атрибуты безопасности
    DWORD   dwCreationDisposition,             // флаг открытия канала
    DWORD   dwFlagsAndAttributes,              // флаги и атрибуты
    HANDLE  hTemplateFile                      // дополнительные атрибуты
);
```

При успехе возвращает дескриптор именованного канала, при неудаче - INVALID_HANDLE_VALUE. Что нужно передавать, когда CreateFile открывает именно канал:

lpFileName - имя канала в том же формате, что и в WaitNamedPipe. Важная деталь про режим: если клиент работает на той же машине, что и сервер, и открывает канал по имени \\.\pipe\pipe_name, то файловая система именованных каналов (Named Pipe File System, NPFS) открывает канал в режиме передачи данных ПОТОКОМ. Чтобы открыть канал в режиме передачи СООБЩЕНИЯМИ, имя нужно задавать в виде \\server_name\pipe\pipe_name. (То же напоминание будет в разделе 16.7 - для транзакций.)

dwDesiredAccess - что клиент хочет делать. Книга называет три значения по отдельности: 0 (только получить атрибуты канала), GENERIC_READ (читать) и GENERIC_WRITE (писать); в листингах 16.4-16.11 при этом передаётся комбинация GENERIC_READ | GENERIC_WRITE (клиенту нужно и писать, и читать). Функция завершится неудачей, если запрошенный доступ не соответствует dwOpenMode, заданному сервером в CreateNamedPipe: например, если сервер создал канал с PIPE_ACCESS_INBOUND (сервер читает), клиент может открыть его только на запись. Стандартные права доступа тоже можно указать здесь - см. разделы 36.7 и 41.3.

dwShareMode - режим совместного использования: 0 запрещает делить канал с другими, либо любая комбинация FILE_SHARE_READ (разрешает совместное чтение из канала) и FILE_SHARE_WRITE (разрешает совместную запись).

lpSecurityAttributes - атрибуты безопасности, пока NULL.

dwCreationDisposition - для канала ВСЕГДА OPEN_EXISTING, потому что клиент открывает только уже существующий канал (создавать его - дело сервера).

dwFlagsAndAttributes - можно 0 (флаги и атрибуты по умолчанию); подробности - глава 24, про файлы. hTemplateFile - NULL.

Замечания книги про CreateFile в применении к каналам.

- WaitNamedPipe могла завершиться успешно, а CreateFile после неё - неудачей. Причины: между двумя вызовами сервер закрыл канал, либо другой клиент успел занять экземпляр. От второй ситуации защищаются на стороне сервера: создавать НОВЫЙ экземпляр после каждого успешного ConnectNamedPipe или сразу создать несколько экземпляров.
- Если заранее известно, что сервер уже вызвал ConnectNamedPipe, CreateFile можно вызывать без предварительного WaitNamedPipe (именно так сделан клиент в листинге 16.2).

Ещё один момент про связь сервера с клиентом. Что если сервер вызвал ConnectNamedPipe, а клиента нет вообще? Тогда серверное приложение блокируется (ждёт неизвестно чего). Чтобы иметь возможность справиться с этой ситуацией, ConnectNamedPipe нужно вызывать в отдельном потоке серверного приложения. Тогда для разблокировки можно из ДРУГОГО потока этого же приложения вызвать функции клиента (то есть "самому позвонить в свою же линию" - и ConnectNamedPipe вернётся).

16.5 Обмен данными по именованному каналу

Как и с анонимным каналом, данные передаются функциями ReadFile и WriteFile - дескриптор канала ведёт себя как дескриптор файла. Единственное отличие: у именованного канала разрешён АСИНХРОННЫЙ обмен, поэтому параметр lpOverlapped в ReadFile/WriteFile здесь может быть не только NULL. Он работает при условии, что в CreateNamedPipe в dwOpenMode был установлен флаг FILE_FLAG_OVERLAPPED. За одну операцию WriteFile в канал можно записать максимум 65 535 байтов. Подробно ReadFile и WriteFile разбираются в главе 24 (файлы); для асинхронного обмена по каналу можно использовать и функции ReadFileEx/WriteFileEx (тоже глава 24). После окончания обмена дескрипторы экземпляров закрываются функцией CloseHandle. Прототипы ReadFile/WriteFile - в конспекте главы 15 (раздел 15.4).

Дальше - примеры. Пять листингов идут парами "сервер + клиент", и у них один и тот же порядок запуска: СНАЧАЛА сервер (он создаёт канал и ждёт), ПОТОМ клиент (он пытается открыть уже существующий канал).

Пример 1 (листинги 16.1 и 16.2): сервер создаёт канал, ждёт клиента, читает от него десять чисел и печатает их на консоль. Клиент связывается с каналом и записывает десять чисел.

Листинг 16.1 - процесс-сервер именованного канала:

```c
#include <windows.h>
#include <iostream.h>

int main()
{
    HANDLE hNamedPipe;

    // создаем именованный канал для чтения
    hNamedPipe = CreateNamedPipe(
        "\\\\.\\pipe\\demo_pipe",      // имя канала
        PIPE_ACCESS_INBOUND,           // читаем из канала
        PIPE_TYPE_MESSAGE | PIPE_WAIT, // синхронная передача сообщений
        1,           // максимальное количество экземпляров канала
        0,           // размер выходного буфера по умолчанию
        0,           // размер входного буфера по умолчанию
        INFINITE,    // клиент ждет связь бесконечно долго
        NULL         // защита по умолчанию
        );
    // проверяем на успешное создание
    if (hNamedPipe == INVALID_HANDLE_VALUE)
    {
        cerr << "Create named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // ждем, пока клиент свяжется с каналом
    cout << "The server is waiting for connection with a client." << endl;
    if (!ConnectNamedPipe(
            hNamedPipe,     // дескриптор канала
            NULL            // связь синхронная
            ))
    {
        cerr << "The connection failed." << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // читаем данные из канала
    for (int i = 0; i < 10; i++)
    {
        int nData;
        DWORD dwBytesRead;
        if (!ReadFile(
                hNamedPipe,     // дескриптор канала
                &nData,         // адрес буфера для ввода данных
                sizeof(nData),  // число читаемых байтов
                &dwBytesRead,   // число прочитанных байтов
                NULL            // передача данных синхронная
                ))
        {
            cerr << "Read file failed." << endl
                << "The last error code: " << GetLastError() << endl;
            CloseHandle(hNamedPipe);
            cout << "Press any key to exit.";
            cin.get();

            return 0;
        }
        // выводим прочитанные данные на консоль
        cout << "The number " << nData << " was read by the server" << endl;
    }
    // закрываем дескриптор канала
    CloseHandle(hNamedPipe);
    // завершаем процесс
    cout << "The data are read by the server." << endl;
    cout << "Press any key to exit.";
    cin.get();

    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows) - проверено по документации и логике API. Механизм по шагам.

Сервер. CreateNamedPipe делает экземпляр канала "\\.\pipe\demo_pipe": PIPE_ACCESS_INBOUND (сервер только ЧИТАЕТ, клиент только пишет), PIPE_TYPE_MESSAGE | PIPE_WAIT (запись сообщениями, все вызовы ждут результата), максимум один экземпляр, буферы по умолчанию, ожидание клиента INFINITE, защита по умолчанию. Если вернулся INVALID_HANDLE_VALUE - печатает код ошибки в cerr и выходит. Потом ConnectNamedPipe(hNamedPipe, NULL) - синхронная связь, сервер здесь замирает, пока клиент не присоединится (перед этим он успел напечатать "The server is waiting for connection with a client."). Дальше десять раз ReadFile на четыре байта (sizeof(int)) - каждый вызов ждёт, пока клиент запишет очередное число. В конце CloseHandle. DisconnectNamedPipe в примере не нужен: сервер сразу завершается.

Клиент. CreateFile открывает канал по имени "\\.\pipe\demo_pipe" (точка = этот же компьютер) на запись (GENERIC_WRITE) - совпадает с PIPE_ACCESS_INBOUND у сервера; FILE_SHARE_READ, OPEN_EXISTING, 0 и NULL, как рассказано в 16.4. WaitNamedPipe здесь не вызывается: клиент запускается после сервера, когда тот уже стоит в ConnectNamedPipe (второе замечание раздела 16.4). Десять раз WriteFile записывает целое число (4 байта), печатает сообщение и засыпает на секунду. Сервер получает каждое число сразу - поэтому его строки идут с такими же паузами.

Ожидаемое поведение (рассуждение по логике, НЕ проверенный вывод). Сервер: "The server is waiting for connection with a client." - пауза, пока не запущен клиент - потом строки "The number 0 was read by the server" ... "The number 9 was read by the server" по одной в секунду - "The data are read by the server." - "Press any key to exit.". Клиент: строки "The number 0 is written to the named pipe." ... "The number 9 is written to the named pipe." по одной в секунду - "The data are written by the client." - "Press any key to exit.". Если клиента запустить раньше сервера, CreateFile не найдёт канала - клиент напечатает "Connection with the named pipe failed." и код ошибки (в этой ветке кода клиента нет cin.get(), поэтому окно может закрыться сразу - мелкая недоработка самого листинга).

Пример 2 (листинги 16.3 и 16.4): двусторонний обмен сообщениями. Сервер создаёт канал, ждёт клиента, принимает ОДНО сообщение, печатает его и посылает клиенту ответное сообщение (текст вводится с клавиатуры). Клиент вводит имя компьютера с сервером, связывается с каналом, отправляет одно сообщение и печатает ответ.

Листинг 16.3 - сервер именованного канала, отвечающий на сообщение от клиента:

```c
#include <windows.h>
#include <iostream.h>
#include <string.h>

int main()
{
    HANDLE hNamedPipe;
    DWORD dwBytesRead;      // для количества прочитанных байтов
    DWORD dwBytesWrite;     // для количества записанных байтов
    char pchMessage[80];    // для сообщения
    int nMessageLength;     // длина сообщения

    // создаем именованный канал для чтения и записи
    hNamedPipe = CreateNamedPipe(

        PIPE_TYPE_MESSAGE | PIPE_WAIT,  // синхронная передача сообщений
        1,           // максимальное количество экземпляров канала
        0,           // размер выходного буфера по умолчанию
        0,           // размер входного буфера по умолчанию
        INFINITE,    // клиент ждет связь бесконечно долго
        NULL         // безопасность по умолчанию
        );
    // проверяем на успешное создание
    if (hNamedPipe == INVALID_HANDLE_VALUE)
    {
        cerr << "Create named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // ждем, пока клиент свяжется с каналом
    cout << "The server is waiting for connection with a client." << endl;
    if (!ConnectNamedPipe(
            hNamedPipe,     // дескриптор канала
            NULL            // связь синхронная
            ))
    {
        cerr << "Connect named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }
    // читаем сообщение от клиента
    if (!ReadFile(
            hNamedPipe,           // дескриптор канала
            pchMessage,           // адрес буфера для ввода данных
            sizeof(pchMessage),   // количество читаемых байтов
            &dwBytesRead,         // количество прочитанных байтов
            NULL))                // передача данных синхронная
    {
        cerr << "Data reading from the named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // выводим полученное от клиента сообщение на консоль
    cout << "The server received the message from a client: "
        << endl << '\t' << pchMessage << endl;

    // вводим строку
    cout << "Input a string: ";
    cin.getline(pchMessage, 80);
    // определяем длину строки
    nMessageLength = strlen(pchMessage) + 1;

    // отвечаем клиенту
    if (!WriteFile(
            hNamedPipe,       // дескриптор канала
            pchMessage,       // адрес буфера для вывода данных
            nMessageLength,   // количество записываемых байтов
            &dwBytesWrite,    // количество записанных байтов
            NULL              // передача данных синхронная
            ))
    {
        cerr << "Write file failed." << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // выводим посланное клиенту сообщение на консоль
    cout << "The server sent the message to a client: "
        << endl << '\t' << pchMessage << endl;

    // закрываем дескриптор канала
    CloseHandle(hNamedPipe);
    // завершаем процесс
    cout << "Press any key to exit.";
    cin.get();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Механизм по шагам.

Отличия от первого примера. Сервер создаёт канал PIPE_ACCESS_DUPLEX (можно и читать, и писать), поэтому клиент открывает его на GENERIC_READ | GENERIC_WRITE. Сервер сначала ЧИТАЕТ (ждёт сообщение клиента), потом ПИШЕТ (отвечает) - очерёдность задана самим кодом, поэтому дополнительных событий, как в анонимном канале главы 15, не нужно: канал двусторонний, а протокол "сначала клиент, потом сервер" зашит в порядок вызовов.

Клиент теперь формирует имя канала не жёстко, а из имени компьютера, введённого пользователем: wsprintf подставляет его вместо %s в шаблон "\\\\%s\\pipe\\demo_pipe" (в памяти получается \\имя_компьютера\pipe\demo_pipe). Это как раз формат с именем машины из 16.4: так клиент может быть на другом компьютере локальной сети, и такой формат открывает канал в режиме передачи сообщениями.

Тонкости кода. После cin >> machineName в буфере ввода остаётся символ перевода строки; поэтому перед cin.getline стоит cin.get() - он "съедает" этот символ, иначе getline сразу вернул бы пустую строку. Длина сообщения считается как strlen(...) + 1: лишний байт - это завершающий нулевой символ строки, чтобы получатель получил корректную строку С. Читают обе стороны в буфер на 80 байтов (sizeof(pchMessage)) - сообщение помещается целиком. Флаг PIPE_READMODE_MESSAGE ни в одном примере не задан, то есть чтение здесь идёт в режиме потока (по умолчанию); работает это потому, что запись сообщения происходит одним вызовом WriteFile и буфер чтения не меньше сообщения (мой вывод по логике, не слова книги).

Важное замечание книги. Если клиент и сервер работают на РАЗНЫХ компьютерах, то вход как на компьютер сервера, так и на компьютер клиента должен выполняться под одинаковыми именами (логинами) и паролями. Причина: по умолчанию атрибуты безопасности именованного канала устанавливаются так, что он принадлежит только пользователю, создавшему этот канал (lpPipeAttributes = NULL). Следующий пример сервера как раз задаёт атрибуты безопасности так, чтобы разрешить доступ любому пользователю.

Ожидаемое поведение (рассуждение по логике, НЕ проверенный вывод). Сервер: "The server is waiting for connection with a client." - после того как клиент отправил сообщение: "The server received the message from a client:" и с новой строки с отступом (\t) полученный текст - "Input a string: " (оператор вводит ответ) - "The server sent the message to a client:" и ответ с отступом - "Press any key to exit.". Клиент: "Enter a name of the server machine: " (вводится имя компьютера сервера) - "Input a string: " (вводится сообщение) - "The client sent the message to a server:" и текст - после ответа сервера "The client received the message from a server:" и текст ответа - "Press any key to exit.". Клиент в этот момент блокирован в ReadFile, пока оператор сервера не введёт ответ.

Пример 3 (листинг 16.5): сервер, создающий общедоступный именованный канал. Клиент - тот же, что в листинге 16.4. Разница только в том, как сервер задаёт защиту канала: он создаёт дескриптор безопасности, который разрешает доступ всем пользователям.

Листинг 16.5 - сервер, создающий общедоступный именованный канал:

```c
#include <windows.h>
#include <iostream.h>
#include <string.h>

int main()
{
    HANDLE hNamedPipe;
    SECURITY_ATTRIBUTES sa;     // атрибуты безопасности
    SECURITY_DESCRIPTOR sd;     // дескриптор безопасности
    DWORD dwBytesRead;          // для количества прочитанных байтов
    DWORD dwBytesWrite;         // для количества записанных байтов
    char pchMessage[80];        // для сообщения
    int nMessageLength;         // длина сообщения

    // инициализация атрибутов безопасности
    sa.nLength = sizeof(sa);
    sa.bInheritHandle = FALSE;  // дескриптор канала ненаследуемый
    // инициализируем дескриптор безопасности
    InitializeSecurityDescriptor(&sd, SECURITY_DESCRIPTOR_REVISION);
    // разрешаем доступ к именованному каналу всем пользователям
    SetSecurityDescriptorDacl(&sd, TRUE, NULL, FALSE);
    sa.lpSecurityDescriptor = &sd;

    // создаем именованный канал для чтения и записи
    hNamedPipe = CreateNamedPipe(
        "\\\\.\\pipe\\demo_pipe",       // имя канала
        PIPE_ACCESS_DUPLEX,             // читаем из канала и пишем в канал
        PIPE_TYPE_MESSAGE | PIPE_WAIT,  // синхронная передача сообщений
        1,           // максимальное количество экземпляров канала
        0,           // размер выходного буфера по умолчанию
        0,           // размер входного буфера по умолчанию
        INFINITE,    // клиент ждет связь бесконечно долго
        &sa          // доступ для всех пользователей
        );
    // проверяем на успешное создание
    if (hNamedPipe == INVALID_HANDLE_VALUE)
    {
        cerr << "Create named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // ждем, пока клиент свяжется с каналом
    cout << "The server is waiting for connection with a client." << endl;
    if (!ConnectNamedPipe(
            hNamedPipe,   // дескриптор канала
            NULL          // связь синхронная
            ))
    {
        cerr << "Connect named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }
    // читаем сообщение от клиента
    if (!ReadFile(
            hNamedPipe,             // дескриптор канала
            pchMessage,             // адрес буфера для ввода данных
            sizeof(pchMessage),     // количество читаемых байтов
            &dwBytesRead,           // количество прочитанных байтов
            NULL))                  // передача данных синхронная
    {
        cerr << "Data reading from the named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // выводим полученное от клиента сообщение на консоль
    cout << "The server received the message from a client: "
        << endl << '\t' << pchMessage << endl;

    // вводим строку
    cout << "Input a string: ";
    cin.getline(pchMessage, 80);
    // определяем длину строки
    nMessageLength = strlen(pchMessage) + 1;

    // отвечаем клиенту
    if (!WriteFile(
            hNamedPipe,         // дескриптор канала
            pchMessage,         // адрес буфера для вывода данных
            nMessageLength,     // количество записываемых байтов
            &dwBytesWrite,      // количество записанных байтов
            NULL                // передача данных синхронная
            ))
    {
        cerr << "Write file failed." << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // выводим посланное клиенту сообщение на консоль
    cout << "The server sent the message to a client: "
        << endl << '\t' << pchMessage << endl;

    // закрываем дескриптор канала
    CloseHandle(hNamedPipe);
    // завершаем процесс
    cout << "Press any key to exit.";
    cin.get();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Механизм по шагам: от листинга 16.3 этот сервер отличается только блоком "инициализация атрибутов безопасности" и последним параметром CreateNamedPipe (теперь &sa вместо NULL). В структуре SECURITY_ATTRIBUTES заполняются размер (nLength), признак наследования (bInheritHandle = FALSE - дескриптор канала ненаследуемый) и указатель на дескриптор безопасности. Дескриптор безопасности sd сначала инициализируется (InitializeSecurityDescriptor с константой версии SECURITY_DESCRIPTOR_REVISION), потом в него функцией SetSecurityDescriptorDacl записывается список прав доступа DACL, который по комментарию книги "разрешает доступ к именованному каналу всем пользователям". Смысл: пустой список прав (NULL на месте самого списка) означает "ограничений нет" - каждый может открыть этот канал; в отличие от защиты по умолчанию, при которой канал принадлежит только создавшему пользователю. Подробно параметры этих функций разбираются в части XI книги (безопасность в Windows, главы 35-45); здесь важна идея. Остальная часть кода - как в листинге 16.3: сервер ждёт клиента, читает сообщение, показывает его, отвечает.

В заключение раздела книга отмечает: для создания именованных каналов и связи с ними пользователь должен иметь соответствующие полномочия.

16.6 Копирование данных из именованного канала

Картинка из жизни: почтовый ящик. ReadFile - это "достать письмо и забрать его": письмо из ящика пропадает. А иногда хочется просто ЗАГЛЯНУТЬ - есть ли что-то и что именно, - не вынимая письма. Так же в главе 13 работали PeekConsoleInput (посмотреть) и ReadConsoleInput (забрать) - lectures/13. Для именованных каналов "заглянуть, не удаляя" делает функция PeekNamedPipe:

```
BOOL PeekNamedPipe(
    HANDLE  hNamedPipe,                // дескриптор канала
    LPVOID  lpBuffer,                  // буфер данных
    DWORD   nBufferSize,               // размер буфера данных
    LPDWORD lpBytesRead,               // количество прочитанных байтов
    LPDWORD lpTotalBytesAvail,         // количество доступных байтов
    LPDWORD lpBytesLeftThisMessage     // количество непрочитанных байтов
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Важное отличие от ReadFile: если данных в канале нет, функция НЕ ждёт, а немедленно возвращает управление и записывает нули в переменные, на которые указывают lpBytesRead, lpTotalBytesAvail и lpBytesLeftThisMessage. Параметры:

- hNamedPipe - дескриптор канала; канал должен быть открыт в режиме чтения;
- lpBuffer - область памяти, в которую функция копирует данные из канала. Если здесь NULL, данные вообще не читаются (можно узнать только количество);
- nBufferSize - размер области памяти, на которую указывает lpBuffer;
- lpBytesRead - адрес DWORD, куда функция запишет, сколько байтов скопировала. Если данные не читаются - можно NULL;
- lpTotalBytesAvail - адрес DWORD, куда функция запишет, сколько байтов сейчас лежит в канале и доступно для чтения. Если данные не читаются - можно NULL;
- lpBytesLeftThisMessage - адрес DWORD, куда функция запишет, сколько байтов текущего сообщения осталось непрочитанными (не влезло в буфер). Если данные не читаются - можно NULL.

Поведение зависит от способа передачи. Если данные идут ПОТОКОМ, функция читает ровно столько байтов, какова длина буфера. Если СООБЩЕНИЯМИ, то читает целиком сообщение, если оно влезает в буфер; иначе читается часть сообщения, а число оставшихся байтов возвращается через lpBytesLeftThisMessage.

Листинг 16.6 - клиент, который использует PeekNamedPipe. Сервер для этого листинга (и для 16.7-16.11) книга отдельно не приводит - все клиенты просто подключаются к каналу demo_pipe.

```c
#include <windows.h>
#include <iostream.h>
#include <string.h>

int main()
{
    char machineName[80];
    char pipeName[80];
    HANDLE hNamedPipe;
    DWORD dwBytesRead;              // для количества прочитанных байтов
    DWORD dwTotalBytesAvail;        // количество байтов в канале
    DWORD dwBytesLeftThisMessage;   // количество непрочитанных байтов
    char pchMessage[80];            // для сообщения

    // вводим имя машины в сети, на которой работает сервер
    cout << "Enter a name of the server machine: ";
    cin >> machineName;
    cin.get();
    // подставляем имя машины в имя канала
    wsprintf(pipeName, "\\\\%s\\pipe\\demo_pipe", machineName);

    // связываемся с именованным каналом
    hNamedPipe = CreateFile(
        pipeName,                             // имя канала
        GENERIC_READ | GENERIC_WRITE,         // читаем и записываем в канал
        FILE_SHARE_READ | FILE_SHARE_WRITE,   // разрешаем чтение и запись
        NULL,                                 // безопасность по умолчанию
        OPEN_EXISTING,                        // открываем существующий канал
        FILE_ATTRIBUTE_NORMAL,                // атрибуты по умолчанию
        NULL);                                // дополнительных атрибутов нет

    // проверяем связь с каналом
    if (hNamedPipe == INVALID_HANDLE_VALUE)
    {
        cerr << "Connection with the named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // ждем команду на копирование сообщения из канала
    cout << "Press any key to peek a message." << endl;
    cin.get();

    // копируем информацию из именованного канала
    if (!PeekNamedPipe(
            hNamedPipe,               // дескриптор канала
            pchMessage,               // данные
            sizeof(pchMessage),       // размер данных
            &dwBytesRead,             // количество записанных байтов
            &dwTotalBytesAvail,       // количество байтов в канале
            &dwBytesLeftThisMessage   // количество непрочитанных байтов
            ))
    {
        // ошибка чтения сообщения
        cerr << "Peek named pipe failed: " << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }
    // выводим полученное сообщение на консоль
    if (dwTotalBytesAvail)
        cout << "The peeked message: "
            << endl << '\t' << pchMessage << endl;
    else
        cout << "There is no mesage." << endl;

    // теперь читаем сообщение из именованного канала
    if (!ReadFile(
            hNamedPipe,            // дескриптор канала
            pchMessage,            // данные
            sizeof(pchMessage),    // размер данных
            &dwBytesRead,          // количество записанных байтов
            NULL))                 // синхронное чтение
    {
        // ошибка чтения
        cerr << "Read file failed: " << endl
            << "The last error code: " << GetLastError() << endl;
        CloseHandle(hNamedPipe);
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }
    // выводим полученное сообщение на консоль
    cout << "The client received the message from a server: "
        << endl << '\t' << pchMessage << endl;
    // закрываем дескриптор канала
    CloseHandle(hNamedPipe);
    // завершаем процесс
    cout << "Press any key to exit." << endl;
    cin.get();

    return 0;
}
```

Не скомпилировано по-настоящему (нет Windows) - проверено по документации и логике API. Механизм по шагам: клиент по имени компьютера подключается к каналу и ждёт нажатия клавиши - за это время сервер должен успеть что-то записать. Потом PeekNamedPipe копирует в pchMessage то, что лежит в канале, НЕ удаляя. Если dwTotalBytesAvail не ноль (в канале что-то было) - печатает "The peeked message:" и текст, иначе "There is no mesage." (в тексте книги опечатка "mesage"). После этого сразу ReadFile читает то же самое сообщение уже по-настоящему и печатает "The client received the message from a server:". Раз сообщение появилось на экране дважды - и при "подсмотре", и при чтении, - это и есть демонстрация того, что Peek не удаляет данные.

Ожидаемое поведение (рассуждение по логике, НЕ проверенный вывод), при условии что сервер уже успел отправить сообщение: "Press any key to peek a message." - после клавиши "The peeked message:" и текст с отступом - "The client received the message from a server:" и тот же текст - "Press any key to exit.". Важная ловушка (мой вывод по логике кода, не из книги): клиент сначала подсматривает, а потом читает - то есть ждёт сообщение от сервера. Если запустить его с сервером из листинга 16.3, который сам сначала ЖДЁТ сообщение от клиента в ReadFile, получится взаимная блокировка - оба ждут друг друга (глава 8): Peek вернёт "There is no mesage.", а ReadFile клиента зависнет.

16.7 Передача транзакций по именованному каналу

Часто общение выглядит так: клиент задал один вопрос - сервер дал один ответ. Записать вопрос, потом прочитать ответ - это два вызова (WriteFile + ReadFile). Функция TransactNamedPipe склеивает их в ОДНУ операцию, которая называется транзакцией. Она нужна для обмена сообщениями по сети и может использоваться только если сервер при создании канала установил флаг PIPE_TYPE_MESSAGE.

```
BOOL TransactNamedPipe(
    HANDLE       hNamedPipe,       // дескриптор именованного канала
    LPVOID       lpInBuffer,       // буфер для записи в канал
    DWORD        dwInBufferSize,   // длина буфера для записи
    LPVOID       lpOutBuffer,      // буфер для чтения из канала
    DWORD        dwOutBufferSize,  // длина буфера для чтения
    LPDWORD      lpBytesRead,      // количество прочитанных байтов
    LPOVERLAPPED lpOverlapped      // асинхронный доступ к каналу
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Параметры:

- hNamedPipe - дескриптор УЖЕ ОТКРЫТОГО канала (клиент получил его от CreateFile);
- lpInBuffer - буфер, из которого данные записываются в канал (вопрос);
- dwInBufferSize - длина передаваемого сообщения в байтах;
- lpOutBuffer - буфер, в который читаются данные из канала (ответ);
- dwOutBufferSize - длина буфера, в который читается сообщение;
- lpBytesRead - адрес DWORD, куда функция запишет, сколько байтов прочитано. При асинхронном доступе можно NULL;
- lpOverlapped - для асинхронного доступа (указатель на структуру OVERLAPPED); пока NULL, то есть синхронная передача (асинхронная - глава 27).

Листинг 16.7 - клиент, передающий транзакцию через TransactNamedPipe. Раньше здесь были бы две функции - WriteFile и ReadFile. Дальше клиент печатает то, что отправил, и то, что получил.

Ожидаемое поведение (рассуждение по логике, НЕ проверенный вывод), при сервере, который читает одно сообщение и отвечает (подходит сервер из 16.3 или 16.5 - мой вывод, книга сервер здесь не называет): "Enter a name of the server machine: " (полное имя компьютера, НЕ точка) - "Input a string: " - после ответа оператора сервера: "The sent message:" и текст, "The received message:" и ответ - "Press any key to exit.".

Функция CallNamedPipe делает ещё больше: она ВООБЩЕ вся транзакция целиком. Порядок такой: сначала она сама связывается с каналом по его имени (канал при этом должен быть открыт в режиме передачи сообщениями), потом передаёт единственное сообщение и получает сообщение в ответ, а после этого разрывает связь с каналом. То есть вместо CreateFile + WriteFile + ReadFile + CloseHandle - один вызов. Картинка из жизни: TransactNamedPipe - это "задать вопрос и сразу выслушать ответ", когда ты уже дозвонился; CallNamedPipe - "позвонить, задать один вопрос, выслушать ответ и повесить трубку" одним движением.

```
BOOL CallNamedPipe(
    LPCTSTR lpNamedPipeName,   // имя именованного канала
    LPVOID  lpInBuffer,        // буфер для записи данных в канал
    DWORD   dwInBufferSize,    // размер буфера для записи данных
    LPVOID  lpOutBuffer,       // буфер для чтения данных из канала
    DWORD   dwOutBufferSize,   // размер буфера для чтения данных
    LPDWORD lpBytesRead,       // количество прочитанных байтов
    DWORD   dwTimeOut          // интервал ожидания
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Параметры: lpNamedPipeName - строка с именем канала (формат \\имя_компьютера\pipe\имя); lpInBuffer и dwInBufferSize - буфер с записываемым сообщением и его длина в байтах; lpOutBuffer и dwOutBufferSize - буфер, в который читается ответ, и его длина; lpBytesRead - адрес DWORD, куда функция положит число прочитанных байтов; dwTimeOut - сколько миллисекунд ждать связи с каналом, либо специальное значение:

- NMPWAIT_NOWAIT - если нет свободного экземпляра канала, функция немедленно возвращает управление;
- NMPWAIT_WAIT_FOREVER - ждать связи с экземпляром бесконечно долго;
- NMPWAIT_USE_DEFAULT_WAIT - интервал ожидания берётся из значения, заданного при создании канала (nDefaultTimeOut в CreateNamedPipe).

Листинг 16.8 - клиент, передающий транзакцию через CallNamedPipe (тот же результат, что в 16.7, но клиент не открывает канал сам):

```c
    cout << "The sent message: "
        << endl << '\t' << pchInBuffer << endl;
    // выводим полученное сообщение на консоль
    cout << "The received message: "
        << endl << '\t' << pchOutBuffer << endl;
    // завершаем процесс
    cout << "Press any key to exit.";
    cin.get();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Механизм по шагам: в программе нет ни CreateFile, ни WaitNamedPipe, ни CloseHandle - CallNamedPipe делает всё сама и ждёт свободный экземпляр бесконечно долго (NMPWAIT_WAIT_FOREVER). Ожидаемое поведение то же, что у листинга 16.7 (рассуждение по логике, НЕ проверенный вывод): просьба ввести имя компьютера и строку, потом "The sent message:" и "The received message:" с текстами.

16.8 Определение и изменение состояния именованного канала

Пример из жизни: у линии связи есть "пульт настроек" - можно посмотреть текущие настройки (GetNamedPipeHandleState) и изменить некоторые (SetNamedPipeHandleState). Сначала чтение состояния:

```
BOOL GetNamedPipeHandleState(
    HANDLE  hNamedPipe,               // дескриптор именованного канала
    LPDWORD lpState,                  // состояние канала
    LPDWORD lpCurrentInstances,       // количество экземпляров канала
    LPDWORD lpMaxCollectionCount,     // максимальное количество байтов
    LPDWORD lpCollectionDataTimeout,  // интервал ожидания
    LPTSTR  lpUserName,               // имя клиента именованного канала
    DWORD   dwMaxUserNameSize         // длина буфера для имени клиента
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Параметры (каждый, кроме дескриптора, можно заменить на NULL, если эта информация не нужна):

- hNamedPipe - дескриптор канала; канал должен быть открыт в режиме чтения;
- lpState - адрес DWORD, куда функция запишет любую комбинацию значений: PIPE_NOWAIT (канал не блокирован) и PIPE_READMODE_MESSAGE (канал открыт в режиме передачи данных сообщениями). Если PIPE_NOWAIT не установлен - канал БЛОКИРОВАН (вызовы ждут). Если PIPE_READMODE_MESSAGE не установлен - канал открыт в режиме передачи данных ПОТОКОМ;
- lpCurrentInstances - адрес DWORD, куда функция запишет количество созданных экземпляров канала;
- lpMaxCollectionCount - адрес DWORD, куда функция запишет максимальное число байтов, которые клиент должен записать в канал, прежде чем данные будут переданы серверу. Это параметр про передачу по СЕТИ: клиентская сторона не отправляет каждый записанный байт отдельно (моё простое прочтение: сеть сначала копит записанное). Этот параметр ДОЛЖЕН быть NULL, если функцию вызывает сервер канала или если клиент и сервер на одном компьютере и клиент связывается с сервером, используя "." вместо имени сервера;
- lpCollectionDataTimeout - адрес DWORD, куда функция запишет количество миллисекунд, которые могут пройти, прежде чем данные будут переданы по сети. Те же условия NULL, что у предыдущего параметра;
- lpUserName - массив символов, куда функция запишет имя владельца именованного канала. По книге имя владельца можно получить только если доступ к каналу открыт всем пользователям (как в листинге 16.5);
- dwMaxUserNameSize - размер этого массива.

Листинг 16.9 - клиент, определяющий состояние канала:

```c
#include <windows.h>
#include <iostream.h>
#include <string.h>

int main()
{
    char machineName[80];
    char pipeName[80];
    HANDLE hNamedPipe;

    DWORD dwState;                  // состояние канала
    DWORD dwCurInstances;           // количество экземпляров канала
    DWORD dwMaxCollectionCount;     // размер буфера клиента канала
    DWORD dwCollectDataTimeout;     // задержка перед передачей данных
    TCHAR chUserName[255];          // имя владельца именованного канала

    // вводим имя машины в сети, на которой работает сервер
    cout << "Enter a name of the server machine: ";
    cin >> machineName;
    cin.get();
    // подставляем имя машины в имя канала
    wsprintf(pipeName, "\\\\%s\\pipe\\demo_pipe", machineName);

    // связываемся с именованным каналом
    hNamedPipe = CreateFile(
        pipeName,                             // имя канала
        GENERIC_READ | GENERIC_WRITE,         // читаем и записываем в канал
        FILE_SHARE_READ | FILE_SHARE_WRITE,   // разрешаем чтение и запись
                                              // в канал
        NULL,                                 // безопасность по умолчанию
        OPEN_EXISTING,                        // открываем существующий канал
        FILE_ATTRIBUTE_NORMAL,                // атрибуты по умолчанию
        NULL);                                // дополнительных атрибутов нет

    // проверяем связь с каналом
    if (hNamedPipe == INVALID_HANDLE_VALUE)
    {
        cerr << "Connection with the named pipe failed." << endl
            << "The last error code: " << GetLastError() << endl;
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // определяем состояние канала
    if (!GetNamedPipeHandleState(
            hNamedPipe,             // дескриптор именованного канала
            &dwState,               // состояние именованного канала
            &dwCurInstances,        // количество экземпляров канала
            &dwMaxCollectionCount,  // размер буфера клиента канала
            &dwCollectDataTimeout,  // макс. задержка перед передачей данных
            chUserName,             // имя пользователя канала
            255))                   // максимальная длина имени
    {
        cerr << "Get named pipe handle state failed." << endl
            << "The last error code: " << GetLastError() << endl;
        cout << "Press any key to exit.";
        cin.get();

        return 0;
    }

    // выводим состояние канала на консоль
    cout << "State: ";
    switch (dwState)
    {
    case (PIPE_NOWAIT):
        cout << "PIPE_NOWAIT" << endl;
        break;
    case (PIPE_READMODE_MESSAGE):
        cout << "PIPE_READMODE_MESSAGE" << endl;
        break;
    case (PIPE_NOWAIT | PIPE_READMODE_MESSAGE):
        cout << "PIPE_NOWAIT and PIPE_READMODE_MESSAGE" << endl;
        break;
    default:
        cout << "Unknown state." << endl;
        break;
    }

    cout << "Current instances: " << dwCurInstances << endl
        << "Max collection count: " << dwMaxCollectionCount << endl
        << "Collection data timeout: " << dwCollectDataTimeout << endl
        << "User name: " << chUserName << endl;

    // закрываем дескриптор канала
    CloseHandle(hNamedPipe);
    // завершаем процесс
    cout << "Press any key to exit.";
    cin.get();

    return 0;
}
```

Не скомпилировано по-настоящему - проверено по документации и логике API. Механизм по шагам: клиент подключается по имени компьютера, вызывает GetNamedPipeHandleState со всеми шестью параметрами и печатает результат. switch по dwState перебирает три комбинации флагов из книги. Ловушка по логике самого кода: у обычного канала - блокирующего и с чтением потоком (значение по умолчанию) - ОБА флага сброшены, dwState равно 0, и ни один case не подходит; сработает default и напечатает "Unknown state." - хотя канал вполне обычный, а не "неизвестного" состояния (мой вывод, не слова книги). Остальное: количество экземпляров, значения из lpMaxCollectionCount/lpCollectionDataTimeout и имя владельца - то, что вернула система; сами значения по книге не определить, они зависят от системы (для серверов этой главы с nMaxInstances = 1 счётчик экземпляров по логике равен 1).

Теперь изменение состояния:

```
BOOL SetNamedPipeHandleState(
    HANDLE  hNamedPipe,                // дескриптор именованного канала
    LPDWORD lpMode,                    // новый режим передачи данных
    LPDWORD lpMaxCollectionCount,      // максимальное количество байтов
    LPDWORD lpCollectionDataTimeout    // интервал ожидания
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Параметры:

- hNamedPipe - дескриптор канала; канал должен быть открыт в режиме ЗАПИСИ;
- lpMode - адрес DWORD с новыми режимами работы. Можно менять режим передачи данных (PIPE_READMODE_BYTE - потоком; PIPE_READMODE_MESSAGE - сообщениями) и режим ожидания (PIPE_WAIT - блокировать приложение до завершения функций ConnectNamedPipe, WriteFile и ReadFile; PIPE_NOWAIT - эти функции не блокируют приложение). Книга отмечает: режимы ожидания не влияют на асинхронные (overlapped) операции, а предназначены только для работы менеджера локальной сети. Можно любую комбинацию флагов или один флаг; если режимы не меняются - NULL;
- lpMaxCollectionCount - адрес DWORD с новым максимальным числом байтов, которые клиент может записать, прежде чем они будут переданы серверу. Игнорируется, если клиент открыл канал в режиме FILE_FLAG_WRITE_THROUGH. NULL, если не меняем;
- lpCollectionDataTimeout - адрес DWORD с новым числом миллисекунд, которые могут пройти, прежде чем данные будут переданы по сети. Так же игнорируется при FILE_FLAG_WRITE_THROUGH; NULL, если не меняем.

16.9 Получение информации об именованном канале

Пример из жизни: "паспорт" линии. Не настройки, которые можно менять, а то, что задано при создании и остаётся навсегда: чей это конец трубы (клиента или сервера), как передаются данные (потоком или сообщениями), какие размеры буферов и сколько экземпляров разрешено. Для этого - GetNamedPipeInfo:

```
BOOL GetNamedPipeInfo(
    HANDLE  hNamedPipe,         // дескриптор именованного канала
    LPDWORD lpFlags,            // тип канала
    LPDWORD lpOutBufferSize,    // размер выходного буфера
    LPDWORD lpInBufferSize,     // размер входного буфера
    LPDWORD lpMaxInstances      // макс. количество экземпляров канала
);
```

При успехе возвращает ненулевое значение, при неудаче - FALSE. Параметры:

- hNamedPipe - дескриптор канала; канал должен быть открыт в режиме чтения;
- lpFlags - адрес DWORD, в который записывается тип канала: информация о способе передачи данных и о том, кому принадлежит дескриптор. Константы: PIPE_CLIENT_END - дескриптор клиента; PIPE_SERVER_END - дескриптор сервера; PIPE_TYPE_BYTE - передача потоком; PIPE_TYPE_MESSAGE - передача сообщениями. Если значение lpFlags - NULL, то, по словам книги, функция рассматривает тот конец канала, который соединён с клиентом и по которому данные передаются потоком (формулировка в книге запутанная - опираться стоит на константы выше);
- lpOutBufferSize - адрес DWORD, куда функция положит размер выходного буфера. Не нужен - NULL;
- lpInBufferSize - адрес DWORD, куда функция положит размер входного буфера. Не нужен - NULL;
- lpMaxInstances - адрес DWORD, куда функция положит максимально допустимое число экземпляров. Если там PIPE_UNLIMITED_INSTANCES, число экземпляров ограничено только системными ресурсами. Не нужно - NULL.

Частые путаницы и ошибки

Путают имя канала на стороне сервера и на стороне клиента. Сервер в CreateNamedPipe пишет \\.\pipe\name (точка - "эта машина": канал всегда создаётся на локальной машине). Клиент в WaitNamedPipe/CreateFile/CallNamedPipe пишет \\имя_компьютера_сервера\pipe\name. Если клиент на той же машине и тоже написал "\\.\", канал откроется в режиме потока, а не сообщений - для TransactNamedPipe/CallNamedPipe это ошибка (раздел 16.7).

Путают "канал" и "экземпляр канала". Имя у канала одно, а экземпляров может быть много (nMaxInstances). Каждый экземпляр обслуживает одного клиента одновременно. Чтобы сервер обслуживал нескольких клиентов сразу, он вызывает CreateNamedPipe несколько раз с одним и тем же именем и получает по дескриптору на каждый экземпляр.

Ждут от WaitNamedPipe того, чего она не делает. Она ждёт освобождения СУЩЕСТВУЮЩЕГО экземпляра; если ни одного экземпляра с таким именем нет, она сразу завершается неудачей независимо от времени ожидания. К тому же успех WaitNamedPipe не гарантирует успех следующего CreateFile: между вызовами экземпляр мог занять другой клиент. Защита - на стороне сервера: создавать новый экземпляр после каждого успешного ConnectNamedPipe.

Забывают, что ConnectNamedPipe блокирует сервер, если клиента нет. Чтобы сервер мог что-то делать ещё, ConnectNamedPipe вызывают в отдельном потоке.

Путают PIPE_TYPE_* и PIPE_READMODE_*. Первые определяют, как данные ПИШУТСЯ в канал, вторые - как ЧИТАЮТСЯ. Это две отдельные настройки, и в примерах главы PIPE_READMODE_MESSAGE ни разу не задан. К тому же "по сообщениям" зависит и от имени, которым клиент открыл канал (\\.\pipe\... - поток; \\сервер\pipe\... - сообщения).

Путают, какие флаги должны совпадать у всех экземпляров одного канала. Должны совпадать: флаг направления (PIPE_ACCESS_*) и флаги способа чтения и записи (PIPE_TYPE_*, PIPE_READMODE_*). Могут различаться: FILE_FLAG_WRITE_THROUGH, FILE_FLAG_OVERLAPPED, PIPE_WAIT/PIPE_NOWAIT.

Путают направление "с чьей стороны". PIPE_ACCESS_INBOUND - "вход" с точки зрения СЕРВЕРА: сервер читает, клиент пишет. Клиент обязан открыть такой канал на GENERIC_WRITE (иначе CreateFile закончится неудачей). PIPE_ACCESS_OUTBOUND - наоборот: сервер пишет, клиент читает, открывает на GENERIC_READ.

Не учитывают защиту по умолчанию. По умолчанию канал принадлежит только создавшему его пользователю. Между компьютерами клиент и сервер должны работать под одинаковыми логинами и паролями, либо сервер должен создать канал с открытыми правами (листинг 16.5).

Считают, что PeekNamedPipe ведёт себя как ReadFile. Peek НЕ удаляет данные из канала и НЕ ждёт: на пустом канале сразу возвращается с нулями в счётчиках. ReadFile данные забирает и, если их нет, ждёт (при синхронном режиме).

Забывают правила NULL у GetNamedPipeHandleState/SetNamedPipeHandleState: lpMaxCollectionCount и lpCollectionDataTimeout должны быть NULL, если функцию вызывает сервер или если клиент связывается с сервером на том же компьютере через ".". А при FILE_FLAG_WRITE_THROUGH эти параметры в Set игнорируются.

Путают "неизвестное состояние" с нулевым. В switch листинга 16.9 обычный канал (блокирующий, чтение потоком) даёт dwState = 0 и попадает в default - "Unknown state." (см. разбор выше).

Общее знание, не из книги: код ERROR_PIPE_CONNECTED в документации Windows относится к ConnectNamedPipe на стороне сервера (клиент подключился раньше вызова) и означает, что связь уже хорошая. Книга приписывает его WaitNamedPipe; практический совет книги остаётся в силе - вызывать WaitNamedPipe только после того, как сервер связался с каналом функцией ConnectNamedPipe.

Опечатки самой книги в этой главе (чтобы не путаться): ERROR_INVALID_PARAMETR вместо ERROR_INVALID_PARAMETER (16.2); PYPE_READMODE_BYTE/PYPE_READMODE_MESSAGE вместо PIPE_READMODE_... (16.2); список порядка работы в 16.1 начинается пунктом, оканчивающимся двоеточием, а не точкой с запятой; "mesage" в листинге 16.6; перепутанные комментарии у трёх переменных в листинге 16.11; перенос строки внутри "//"-комментария в листинге 16.10.

Итог: какие функции и для чего

- CreateNamedPipe - сервер создаёт экземпляр канала (имя, направление, способ передачи, число экземпляров, буферы, таймаут, защита);
- ConnectNamedPipe - сервер ждёт клиента на свободном экземпляре;
- DisconnectNamedPipe - сервер разрывает связь с клиентом (экземпляр можно переиспользовать);
- WaitNamedPipe - клиент ждёт, пока освободится экземпляр (сервер уже вызвал ConnectNamedPipe);
- CreateFile - клиент открывает экземпляр (OPEN_EXISTING) и получает дескриптор;
- ReadFile / WriteFile - обмен данными (lpOverlapped для асинхронного режима, не больше 65 535 байтов за один WriteFile);
- PeekNamedPipe - "подсмотреть" данные, не удаляя их из канала;
- TransactNamedPipe - записать и прочитать одной операцией через уже открытый дескриптор;
- CallNamedPipe - подключиться + записать + прочитать + разорвать связь одним вызовом;
- GetNamedPipeHandleState / SetNamedPipeHandleState - узнать / изменить изменяемые характеристики;
- GetNamedPipeInfo - узнать неизменяемые характеристики;
- CloseHandle - закрыть дескриптор.
