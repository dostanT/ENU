Глава 9. Структура консольного приложения

Суть

Консольное приложение - это программа, которая общается с пользователем через текстовое окно (консоль), а не через графические окна с кнопками. Эта глава - фундамент для всей части III книги: что вообще такое консоль изнутри (из каких двух частей она состоит), какие бывают события ввода и как они устроены как структуры данных, и что такое буфер экрана на уровне отдельной ячейки. Без этой главы дальнейшие функции (главы 10-13) будут просто набором вызовов без понимания, с чем они работают.

9.1 Структура консоли

Представь звонок в call-центр по обычному телефону против полноценной видеоконференции. По телефону ты слышишь только голос собеседника и говоришь сам - больше ничего, даже если в комнате у собеседника происходит что-то ещё (кто-то зашёл, что-то упало) - ты об этом не узнаешь. На видеоконференции ты видишь ВСЁ: не только голос, но и то, кто вошёл в кадр, кто взял слово, изменился ли размер окна трансляции.

Ровно то же самое различие книга описывает для консоли: она обеспечивает два уровня ввода-вывода текстовой информации - высокий и низкий. Функции высокого уровня - это "телефонный звонок": ввод-вывод только символов, всё остальное (события мыши, изменение размера окна) полностью игнорируется. Функции низкого уровня - это "видеоконференция": обрабатывают вообще все события, связанные с консольным приложением, не только нажатия клавиш.

Консоль - это интерфейс, который приложение использует для ввода-вывода текстовой информации. Приложение, которое пользуется консолью для общения с пользователем, называется консольным приложением. Такие приложения нужны в основном в системном программировании: для разработки различных сервисов и для обработки неустранимых ошибок, возникающих при работе графического приложения (даже у оконной программы иногда есть смысл открыть консоль, чтобы напечатать диагностику).

Из чего состоит консоль - ровно из двух частей:
- один входной буфер - содержит очередь записей о событиях ввода (каждое событие ввода описывается отдельной записью, все записи стоят в очереди в порядке поступления);
- один или несколько буферов экрана - каждый буфер экрана содержит информацию для вывода в окно приложения и представляет собой двумерный массив, хранящий и сами символы, и данные об их цвете.

То, что буферов экрана может быть НЕСКОЛЬКО, а входной буфер всегда ровно один - не случайность, а важная асимметрия: несколько заранее подготовленных "картинок" вывода имеют смысл (можно переключаться между ними мгновенно, см. главу 12), а вот несколько независимых очередей ввода не имели бы смысла - откуда, в какую именно очередь должно попасть очередное нажатие клавиши?

9.2 Входной буфер консоли

Входной буфер содержит очередь записей, которые описывают события ввода. События ввода делятся на пять категорий: ввод с клавиатуры, ввод с мыши, изменение размеров окна, изменение фокуса ввода, события, связанные с меню. Два последних (фокус и меню) обрабатываются самой системой и должны игнорироваться приложением - то есть реально твою программу интересуют только первые три.

Каждому событию ввода в очереди соответствует запись типа INPUT_RECORD:

```c
typedef struct _INPUT_RECORD {
    WORD EventType;
    union {
        KEY_EVENT_RECORD          KeyEvent;
        MOUSE_EVENT_RECORD        MouseEvent;
        WINDOW_BUFFER_SIZE_RECORD WindowBufferSizeEvent;
        MENU_EVENT_RECORD         MenuEvent;
        FOCUS_EVENT_RECORD        FocusEvent;
    } Event;
} INPUT_RECORD;
```

Представь это как универсальный бланк на ресепшене: сверху бланка одна галочка "тип визита" (EventType), а ниже - несколько разных секций бланка (для клиента, для курьера, для собеседования), но заполнена всегда только ОДНА секция - именно та, что соответствует отмеченной галочке. Ровно так работает union в C: все пять вариантов записи (KeyEvent, MouseEvent и так далее) делят одну и ту же область памяти, и в любой момент осмысленна ровно ОДНА из них - та, на которую указывает поле EventType. Значения EventType: KEY_EVENT (ввод с клавиатуры), MOUSE_EVENT (ввод с мыши), WINDOW_BUFFER_SIZE_EVENT (изменение размеров окна), MENU_EVENT (меню), FOCUS_EVENT (фокус ввода).

Запись для ввода с клавиатуры:

```c
typedef struct _KEY_EVENT_RECORD {
    BOOL  bKeyDown;
    WORD  wRepeatCount;
    WORD  wVirtualKeyCode;
    WORD  wVirtualScanCode;
    union {
        WCHAR UnicodeChar;
        CHAR  AsciiChar;
    } uChar;
    DWORD dwControlKeyState;
} KEY_EVENT_RECORD;
```


Поля: bKeyDown - TRUE, если клавиша нажата, FALSE - если отпущена. wRepeatCount - счётчик повторов при удержании клавиши. wVirtualKeyCode - код клавиши, не зависящий от типа клавиатуры (один и тот же код для клавиши "A" на любой раскладке/клавиатуре). wVirtualScanCode - код клавиши, который генерирует именно эта клавиатура (у разных производителей может отличаться для одной и той же клавиши). uChar - объединение, содержащее сам символ (в Unicode или ASCII). dwControlKeyState - комбинация флагов состояния управляющих клавиш: CAPSLOCK_ON, ENHANCED_KEY (дополнительные клавиши - самый правый блок клавиатуры, обычно под индикаторами), LEFT_ALT_PRESSED, LEFT_CTRL_PRESSED, NUMLOCK_ON, RIGHT_ALT_PRESSED, RIGHT_CTRL_PRESSED, SCROLLLOCK_ON, SHIFT_PRESSED.

Отдельно стоит запомнить: автономное нажатие клавиши Alt (без другой клавиши следом) имеет специальный смысл для самой системы (открывает фокус на меню окна) и поэтому вообще не передаётся приложению для обработки - ты не увидишь такое событие в очереди, даже если технически пользователь клавишу нажал.

Запись для ввода с мыши:

```c
typedef struct _MOUSE_EVENT_RECORD {
    COORD dwMousePosition;
    DWORD dwButtonState;
    DWORD dwControlKeyState;
    DWORD dwEventFlags;
} MOUSE_EVENT_RECORD;
```

dwMousePosition - координаты курсора относительно буфера экрана. dwButtonState - флаги нажатых кнопок мыши (FROM_LEFT_1ST_BUTTON_PRESSED, RIGHTMOST_BUTTON_PRESSED, FROM_LEFT_2ND/3RD/4TH_BUTTON_PRESSED - нумерация кнопок идёт от самой левой). dwControlKeyState - те же флаги управляющих клавиш, что и в KEY_EVENT_RECORD. dwEventFlags - тип события мыши: 0 (кнопка нажата или отпущена), DOUBLE_CLICK (второе нажатие подряд, первое отмечается просто 0), MOUSE_MOVED (сдвиг мыши), MOUSE_WHEELED (прокрутка колеса - доступно только начиная с Windows 2000).

Запись об изменении размера окна - самая простая из всех:

```c
typedef struct _WINDOW_BUFFER_SIZE_RECORD {
    COORD dwSize;
} WINDOW_BUFFER_SIZE_RECORD;
```

dwSize - новый размер буфера экрана в символах (не окна, а именно буфера - подробно разница между окном и буфером экрана разбирается в главах 11-12).

9.3 Буфер экрана

Буфер экрана - двумерный массив, элементы которого - записи типа CHAR_INFO:

```c
typedef struct _CHAR_INFO {
    union {
        WCHAR UnicodeChar;
        CHAR  AsciiChar;
    } Char;
    WORD Attributes;
} CHAR_INFO, *PCHAR_INFO;
```

Объединение Char содержит сам символ (в Unicode или ASCII), а поле Attributes определяет цвет фона и цвет текста, которыми этот символ выводится на экран дисплея. Значение 0 означает фон чёрный, текст белый (значения по умолчанию), а любая другая комбинация собирается из флагов: BACKGROUND_BLUE, BACKGROUND_GREEN, BACKGROUND_RED, BACKGROUND_INTENSITY (для фона) и FOREGROUND_BLUE, FOREGROUND_GREEN, FOREGROUND_RED, FOREGROUND_INTENSITY (для текста).

Представь три прожектора - красный, зелёный, синий - направленных на одну и ту же точку сцены (это и есть цветовая модель RGB, уже знакомая по обычным мониторам). Каждый прожектор можно включить или выключить независимо - получается 8 разных комбинаций света (2 в кубе, по числу прожекторов), это и есть 8 базовых цветов и для фона, и для текста отдельно. Флаг INTENSITY - это как добавить ещё один, более мощный набор тех же трёх прожекторов поверх обычного: та же комбинация цветов, но ярче. Белый цвет - это все три прожектора вместе, чёрный - все три выключены (побитовое отрицание белого).

Отдельно книга отмечает практическое поведение, никак не связанное с этими флагами напрямую: если окно консольного приложения имеет фокус ввода, фон и текст выводятся на экран яркими цветами (ровно как задают константы выше), а если окно фокус ввода потеряло - и фон, и текст система автоматически выводит приглушёнными цветами, независимо от того, что реально записано в Attributes. Это делает сама система, а не флаг, который ты сам выставляешь.

Частые путаницы и ошибки

Путают уровень (высокий/низкий) консольного ввода-вывода со сложностью кода. Дело не в том, что низкоуровневые функции "сложнее написать" - дело в том, ЧТО ИМЕННО они видят: высокий уровень видит только символы, низкий - вообще любое событие консоли (клавиатура, мышь, изменение размера).

Путают структуру INPUT_RECORD с "структурой из пяти разных полей сразу". На самом деле в памяти в любой момент реально хранится только ОДНА из пяти возможных записей (Event - это union, а не struct) - какая именно, определяет поле EventType.

Путают wVirtualKeyCode и wVirtualScanCode. Первый код не зависит от конкретной клавиатуры (device-independent) - одна и та же клавиша всегда даёт один и тот же код на любом оборудовании. Второй код генерируется именно этой клавиатурой и может отличаться у разных производителей для формально той же клавиши.

Думают, что нажатие Alt всегда попадает в очередь входного буфера как обычное событие клавиатуры. Автономное (без другой клавиши) нажатие Alt перехватывается самой системой и вообще не передаётся приложению.

Путают Attributes буфера экрана с реальным отображаемым цветом. То, что реально видно на экране, зависит ещё и от того, есть ли у окна фокус ввода - без фокуса система приглушает цвета независимо от значения Attributes.
