Глава 14. Передача данных

Суть

Раньше (главы 5-8) потоки договаривались друг с другом ВНУТРИ одного процесса: у них была общая память и общие переменные, и вся сложность сводилась к тому, чтобы не наступать друг другу на ноги (синхронизация). Теперь нужно научить общаться потоки из РАЗНЫХ процессов. А у разных процессов адресные пространства разные (глава 2: процесс - это как раз "своё адресное пространство + свои потоки"), общих переменных у них нет. Значит, между ними нужен посредник, которым владеет не сам процесс, а операционная система.

Эта глава - чистая теория, без единой функции Win32. Она вводит словарь, на котором построены главы 15-17 (анонимные каналы, именованные каналы, почтовые ящики). Каждый из этих механизмов потом описывается одними и теми же вопросами: есть ли у канала имя, в какую сторону идут данные, идут они потоком байтов или сообщениями, ждёт ли отправитель получателя, сколько данных канал может держать внутри. Ответы на эти вопросы и есть содержание главы, поэтому в конце собрана "карточка", которую удобно заполнять для каждого нового канала.

14.1 Способы передачи данных между процессами

Начнём с картинки из жизни. Двое соседей живут в разных квартирах и хотят обмениваться записками. Положить записку "в общую тумбочку" нельзя - тумбочки у каждого свои. Нужно что-то, что принадлежит не им, а дому: например, почтальон, который забирает записку у одного, относит в общую комнату для писем, а второй почтальон оттуда доставляет её в ящик второго соседа. Ровно так устроена передача данных между процессами.

Теперь то же самое словами книги. Под обменом данными между параллельными процессами понимается пересылка данных от одного потока к другому, при условии что эти потоки выполняются в контекстах разных процессов. Поток, который посылает данные, называется отправителем. Поток, который получает данные, - адресатом (или получателем).

Если бы потоки были в одном процессе, для обмена хватило бы глобальных переменных и средств синхронизации из глав 5-8. Между процессами общих переменных нет, поэтому создаётся канал передачи данных. Вот из чего он состоит (рис. 14.1 книги):

- B1 - входной буфер (буфер здесь - просто кусок памяти, в котором данные ждут своей очереди);
- B2 - выходной буфер;
- K1 и K2 - два потока ядра операционной системы (это потоки, которые работают внутри самой ОС и таскают байты; не путай с потоками T1 и T2 - те принадлежат пользовательским программам);
- M - общая память, до которой дотягиваются только эти два потока ядра;
- T1 и T2 - пользовательские потоки: отправитель и получатель.

```
  T1 -> [B1] -> (K1) -> [ M ] -> (K2) -> [B2] -> T2
  |      \_________ канал передачи данных _________/      |
  отправитель                                     получатель
```

На рисунке в книге пунктирной рамкой "канал передачи данных" обведены B1, K1, M, K2 и B2; потоки T1 и T2 остаются снаружи - они только пользуются каналом. Пользовательские потоки работают своими руками только с буферами B1 и B2, и только вызывая специальные функции ядра ОС. Путь данных по шагам:

1. T1 записывает данные в буфер B1 (функцией ядра ОС).
2. K1 читает данные из B1 и записывает их в общую память M.
3. K2 читает данные из M и записывает их в буфер B2.
4. T2 читает данные из B2.

В картинке с соседями: T1 - сосед, который отдаёт записку; B1 - ящик у его двери; K1 - первый почтальон; M - комната для писем; K2 - второй почтальон; B2 - ящик у двери второго соседа; T2 - сам второй сосед. Вывод, который делает книга: в любом случае обмен данными между процессами организуется только через цепочку взаимодействующих потоков, которые обмениваются данными через общую - и доступную только им - память.

Эта же схема годится и для передачи данных по сети. Тогда общая память M превращается в передающую среду (провод, радиоэфир), устройство которой аналогично устройству канала передачи данных.

Как сделать такой канал самому, программно? Нужно заменить потоки ядра и общую память M ФАЙЛОМ. Получается простейший канал между потоками из разных процессов: один процесс пишет в общий файл, другой из него читает. Иногда операционная система упрощает доступ к такому общему файлу, чтобы ускорить обмен. Например, Windows умеет отображать (проецировать) файл на адресное пространство процесса - тогда файл выглядит как обычный кусок памяти (в оглавлении книги это отдельная глава 30, "Отображение файлов в память"; здесь только упоминание).

Теперь про то, как именно данные пересылаются. Различают два способа:

- передача потоком - данные идут непрерывной последовательностью байтов. Общая память M в этом случае может вообще отсутствовать: один поток ядра перекладывает байты прямо из буфера B1 в буфер B2;
- передача сообщением - данные идут группами байтов, и каждая группа - самостоятельная единица, которая называется сообщением.

Картинка из жизни: поток - это труба с водой. Воду льёшь с одного конца, она вытекает с другого, и по воде нельзя понять, где закончилась "одна порция" и началась следующая. Сообщения - это письма: каждое письмо отдельное, у него есть начало и конец, и получатель достаёт их по одному. Для программиста разница практическая: из потока читаешь "сколько-то байтов" и сам решаешь, как их разрезать на смысловые куски; сообщение приходит целиком, как его отправили.

14.2 Связи между процессами

Прежде чем что-то передавать, между процессами нужно установить связь - как перед разговором по телефону нужно сначала набрать номер и дождаться ответа. Связь может устанавливаться на физическом (аппаратном) уровне или на логическом (программном). Нас дальше интересует программная.

Первое свойство связи - направление передачи данных:

- полудуплексная связь: данные идут только в ОДНОМ направлении;
- дуплексная связь: данные идут в обоих направлениях.

Обрати внимание: это определение именно КНИГИ. В сетевой терминологии (общее знание, не из книги) слова обычно значат другое: "симплекс" - только в одну сторону, "полудуплекс" - в обе стороны, но по очереди (как рация: сказал "приём" - и теперь говорит другой), "дуплекс" - в обе стороны одновременно (как телефон). На экзамене по этому предмету используй определение книги: полудуплексная = в одну сторону.

Второе свойство - топология. Топология связи - это конфигурация связей между процессами-отправителями и процессами-адресатами: кто с кем соединён. Дальше книга рассматривает только полудуплексные связи. Бывают четыре вида (рис. 14.2 книги; на рисунке процессы - кружки, стрелки - связи, а прямоугольник посередине - средство передачи данных, то есть канал):

```
а) 1 -> 1      O ---> [канал] ---> O

б) 1 -> N      O ---> [канал] ---> O
                              +--> O
                              +--> O

в) N -> 1      O --+
               O --+-> [канал] ---> O
               O --+

г) N -> M      O --+             +--> O
               O --+-> [канал] --+--> O
               O --+             +--> O
```

- 1 -> 1: связаны только два процесса (личный разговор двух людей);
- 1 -> N: один процесс связан с N процессами (один говорит, N слушают - как объявление по вокзальному радио);
- N -> 1: каждый из N процессов связан с одним процессом (N клиентов шлют запросы в одно окошко обслуживания);
- N -> M: каждый из N процессов связан с каждым из M процессов (общий чат, где пишут и читают многие).

Книга делает важное замечание про названия. Для каналов передачи данных, которые обеспечивают разные виды связей, используются специальные термины, причём в разных системах они могут отличаться, а один и тот же канал часто поддерживает сразу несколько видов связей. Поэтому в главах 15-17 нужно смотреть не на слово, а на то, какие топологии канал реально умеет.

Порядок работы при проектировании такой системы: сначала выбирают топологию и направления передачи данных по связям, и только потом в программах реализуют эти связи специальными функциями ОС, которые предназначены для установки связи. Сами эти функции и функции для обмена данными предоставляет система передачи данных - она обычно является частью ядра ОС.

14.3 Передача сообщений

Представь обычное письмо. На конверте написано, кому оно, от кого, какого оно типа (обычное, заказное), а внутри лежит само письмо. Сообщение в компьютере устроено так же.

Концептуально обмен сообщениями между процессами выполняется двумя функциями:

```
send     - послать сообщение
receive  - получить сообщение
```

(Это не настоящие функции Win32, а обобщённые названия операций - в главах 15-17 им соответствуют WriteFile/ReadFile и другие.)

Само сообщение состоит из двух частей:

- заголовок - служебная информация: тип сообщения, имя адресата, имя отправителя, длина сообщения (контрольная информация - чтобы получатель мог проверить, что пришло всё);
- тело - собственно то, что хотели передать.

При передаче сообщений процессы можно адресовать двумя способами.

Прямая адресация. В функциях send и receive явно указываются процессы - кто отправитель и кто адресат:

```
send(Process P, сообщение);        // послать сообщение процессу P
receive(Process Q, сообщение);     // получить сообщение от процесса Q
```

Это как позвонить конкретному человеку на его личный номер.

Косвенная адресация. Вместо процессов указывается имя связи, по которой идёт сообщение:

```
send(Connection S, сообщение);       // послать сообщение по связи S
receive(Connection R, сообщение);    // получить сообщение по связи R
```

Это как бросить письмо в почтовый ящик с номером: отправитель не знает, кто именно его заберёт, ему важно только "в какой ящик".

Дальше - про то, как два подхода сочетаются. Адресация процессов бывает симметричной и асимметричной:

- симметричная: и отправитель, и получатель используют только прямую адресацию, либо оба только косвенную;
- асимметричная: используется и прямая, и косвенная адресация вместе.

Асимметричная адресация нужна в системах "клиент-сервер". Клиенты знают адрес сервера и шлют ему сообщения по прямой адресации:

```
send(Process Сервер, сообщение);
```

А сервер не знает, кто именно ему напишет. Он "слушает" канал связи и принимает сообщения от всех клиентов по косвенной адресации:

```
receive(Connection S, сообщение);
```

Эту функцию часто так и называют - listen ("слушать"). Картинка из жизни: справочная служба. Все знают её номер телефона (прямая адресация), но справочная не знает заранее, кто позвонит, - она просто снимает трубку на общей линии (косвенная адресация).

В конце раздела книга даёт важное определение. Набор правил, по которым устанавливаются связи и передаются данные между процессами, называется протоколом. С точки зрения программирования эти правила включают набор функций для передачи данных И порядок их использования: у вызовов есть определённая последовательность. Например, нельзя начинать передачу данных, не установив связь между отправителем и адресатом. Картинка из жизни - протокол телефонного разговора: набрал номер, дождался ответа, поздоровался, поговорил, попрощался, положил трубку. Поменяй порядок - и разговор не получится. В главе 15 такой протокол придётся придумывать самим (см. синхронизацию событием в примере двустороннего обмена).

14.4 Синхронный и асинхронный обмен

Два способа отправить письмо: вручить лично и дождаться, пока получатель распишется, - или бросить в ящик и пойти по своим делам. И два способа получить: стоять у ящика и ждать, пока письмо придёт, - или заглянуть, увидеть, что пусто, и заняться другим делом. Ровно это и есть синхронный и асинхронный обмен.

Определения книги, по четырём случаям:

- Отправление синхронное: поток-отправитель, вызвав send, БЛОКИРУЕТСЯ (замирает) до тех пор, пока сообщение не получит адресат. Иначе отправление асинхронное (отправил - и сразу пошёл дальше).
- Получение синхронное: поток-адресат, вызвав receive, блокируется, пока не получит сообщение. Иначе получение асинхронное (проверил - сообщения нет - пошёл дальше).
- Обмен сообщениями синхронный, если отправитель передаёт синхронно И адресат принимает синхронно. Во всех остальных случаях обмен асинхронный.

Про передачу потоком: предполагается, что она ВСЕГДА синхронная, потому что в этом случае между отправителем и адресатом устанавливается непосредственная связь (как разговор по прямому проводу: вы оба должны быть на линии одновременно, промежуточного хранилища с порциями-письмами тут нет).

Рандеву (rendezvous, по-французски "встреча") - так называется синхронный обмен в случае прямой адресации процессов. Отправитель и получатель как бы встречаются в одной точке: пока оба не пришли, никто не идёт дальше. Такой механизм обмена сообщениями используется в языке программирования Ада.

Дальше - мостик к главам 5-6. Раз синхронный обмен заставляет одного ждать другого, его можно использовать и для решения задач СИНХРОНИЗАЦИИ процессов: "жду, пока ты пришлёшь сообщение" - это то же самое, что "жду события" из главы 5. И здесь важная деталь про Windows: синхронизация процессов, выполняющихся на РАЗНЫХ компьютерах в локальной сети, может осуществляться только при помощи механизма синхронного обмена данными (то есть события, мьютексы и семафоры из главы 6 через границу компьютера не работают - об этом книга говорит прямо).

14.5 Буферизация

Представь, что отправитель кладёт письма не в руки получателю, а на полку. Сколько писем помещается на полку - это и есть буферизация. Книга называет буфером ВМЕСТИМОСТЬ СВЯЗИ - количество сообщений, которые могут одновременно пересылаться по этой связи. Различаются три типа:

- нулевая вместимость (нет буфера): полки нет, письмо можно только вручить из рук в руки. Поэтому возможен ТОЛЬКО синхронный обмен: отправитель обязан дождаться получателя;
- ограниченная вместимость (ограниченный буфер): полка на N писем. Пока есть свободное место - кладёшь и уходишь. Если полка полна, отправитель должен ждать, пока получатель заберёт хотя бы одно сообщение;
- неограниченная вместимость (неограниченный буфер): бездонная полка, отправитель никогда не ждёт при отправке (в реальности память конечна, так что это идеализация - общее соображение, не из книги).

Как видно, типы буферизации тесно связаны с синхронизацией передачи данных, и поэтому их тоже нужно учитывать при разработке систем с обменом данными между процессами. Связь с прошлым материалом (моя аналогия, не из книги): ограниченный буфер - это ровно задача "производитель/потребитель" из главы 6, где считающий семафор не даёт положить в контейнер больше N штук и не даёт забрать из пустого (lectures/06, раздел про семафоры).

Карточка для описания любого канала

Когда в главах 15-17 появится очередной канал, заполняй для него эту карточку - она сразу расставит всё по местам:

1. Есть ли у канала имя? (безымянный доступен только тем, кому передали дескриптор; именованный - любому, кто знает имя)
2. Направление: полудуплексный (в одну сторону) или дуплексный (в обе)?
3. Как передаются данные: потоком байтов или сообщениями?
4. Обмен синхронный или асинхронный?
5. Какая буферизация (нулевая / ограниченная / неограниченная)?
6. Какие топологии связей поддерживает (1-1, 1-N, N-1, N-M)?
7. Работает только на одном компьютере или по сети?
8. Какая адресация: прямая, косвенная, асимметричная (клиент-сервер)?

Частые путаницы и ошибки

Путают два смысла слова "поток". В этой главе (как и во всей книге) слово "поток" встречается в двух совершенно разных значениях. "Передача данных потоком" - поток БАЙТОВ, непрерывная последовательность данных. "Потоки ядра", "пользовательские потоки" - потоки ВЫПОЛНЕНИЯ (threads), те самые из глав 2-3. Это разные понятия, которые просто называются одинаково.

Путают два смысла слова "буфер". В разделе 14.1 буфер (B1, B2) - это кусок памяти, в котором данные ждут своей очереди. В разделе 14.5 буфер - это вместимость связи, количество сообщений, которое она может держать. Оба смысла связаны (второй - это "сколько влезает в первый"), но в задаче нужно понимать, о каком речь.

Путают направление и топологию. Полудуплексная связь - про направление ("в одну сторону"), а не про то, сколько процессов участвует. Одна полудуплексная связь спокойно может быть N -> 1 или N -> M.

Путают прямую и косвенную адресацию с синхронным и асинхронным обменом. Это две независимые оси. Адресация отвечает на вопрос "КОГО я указываю" (процесс или связь), синхронность - на вопрос "жду ли я". Рандеву - единственное место, где они встречаются: синхронный обмен ПЛЮС прямая адресация.

Думают, что асинхронный обмен - это "без буфера". Наоборот: нулевая вместимость связи допускает ТОЛЬКО синхронный обмен. Чтобы отправитель мог не ждать, сообщению нужно куда-то лечь, то есть нужен буфер.

Считают обмен синхронным, если синхронна только одна сторона. Обмен синхронный только тогда, когда синхронны и отправление, и получение. Если отправитель ждёт, а получатель нет (или наоборот) - обмен асинхронный.

Путают полудуплекс книги с полудуплексом из сетей (см. раздел 14.2): в книге это "только в одну сторону", в сетевой терминологии - "в обе, но по очереди".

Забывают, что события/мьютексы/семафоры не связывают компьютеры. Если процессы на разных машинах, синхронизироваться они могут только через синхронный обмен данными (раздел 14.4).
