# 03. Архитектура

## Общая картина

```
Браузер (HTML-страницы, формы)
        |  HTTP
Spring Boot-приложение (Java 25)
  Controller  ->  Service  ->  Repository  ->  Entity
  (страницы,      (бизнес-     (Spring Data    (классы,
   формы)          правила)     JPA)            связанные с таблицами)
        |  JDBC (драйвер mssql-jdbc)
Microsoft SQL Server 2025 Express (.\SQLEXPRESS, база FitnessCRM)
  таблицы, ограничения, индексы, представления, триггеры, процедуры
```

Это те же 4 уровня, что ты нарисовал в лабе 2 ИСРП («архитектура снизу вверх»):
- Уровень 1, данные — таблицы SQL Server (клиенты, абонементы, тарифы и акции, платежи, филиалы и остальное).
- Уровень 2, бизнес-логика — классы-сервисы и доменные классы в Java плюс то, что обязана гарантировать сама база (ограничения, триггеры, критичные операции).
- Уровень 3, API — контроллеры Spring MVC (адреса и формы). Отдельного REST-слоя пока нет.
- Уровень 4, клиенты — браузер сотрудника и страница «киоск» (роль «терминала на ресепшн»). Мобильное приложение и публичный сайт из лабы не делаем.
- Отдельно, внешняя система — платёжный шлюз; у нас это страница-эмулятор.

## Где живёт логика (главное правило проекта; предложение — ты решаешь в неделю 2)

Правило, которое должно выполняться независимо от того, кто и откуда обращается к данным, живёт в базе:
- один активный абонемент вида у клиента (уникальный индекс с условием);
- вместимость занятия и отсутствие пересечений (триггер или проверка в транзакции);
- допустимые значения (`CHECK`), связи (внешние ключи), уникальность кодов и ключей идемпотентности;
- журнал изменений (триггер).

Всё, что про предметную область и удобство, живёт в Java:
- расчёт цены и скидки (интерфейс и реализации: процентная, суммовая, комбинированная);
- проверки операций и понятные сообщения об ошибках (иерархия собственных исключений);
- страницы, формы, форматирование, навигация, фоновые задачи;
- отчёты, где важна читаемость кода (Stream API), и экспорт файлов.

Критичные атомарные операции (продать абонемент, вернуть, записаться на занятие, списать по ФИФО) — спорное место. Два варианта, выбираешь один (или разные для разных операций):
- а) Java-метод с `@Transactional`: вся логика в одном языке, проще отлаживать и тестировать, лучше для курса ООП на Java;
- б) хранимая процедура T-SQL, которую Java лишь вызывает: проще для курса БД («бизнес-логика через объектные методы» из списка СРС), работает одинаково для любого клиента.
Мой совет: продажа и возврат — процедурами (витрина для курса БД), расчёт цены, проверки и всё остальное — в Java; сравнение двух подходов потом можно описать как СРС 13 («ORM и прямой вызов»).

## Слои приложения и структура пакетов

Пакеты по функциям (а не «все контроллеры в одной куче»), корень `com.fitlife.fitnesscrm`:
- `common` — общие настройки, форматирование денег и дат, базовые классы, собственные исключения, обработчик ошибок.
- `security` — настройка Spring Security, загрузка пользователей из `staff`, роли.
- `branches`, `staff`, `clients`, `memberships`, `payments`, `schedule`, `bookings`, `trainers`, `visits`, `inventory`, `marketing`, `reports`, `notifications`, `kiosk` — по пакету на функцию. Внутри каждого: `...Controller`, `...Service`, `...Repository`, сущности (`Entity`), объекты для форм (`...Form` или `...Dto`).
- Шаблоны страниц — `src/main/resources/templates/<функция>/...html`.

Правила зависимостей:
- Контроллер вызывает только сервисы, не репозитории напрямую.
- Сервис знает про репозитории и доменные классы, но ничего не знает про HTTP и HTML.
- Сущность (`Entity`) не уходит в шаблон «как есть», если у неё есть лишние данные (хэш пароля, например): для страницы собираем форму или DTO.
- Транзакции открывает сервис (`@Transactional`), не контроллер.

## Java: что учесть именно в этом проекте

- Java 25, Spring Boot 4.1.1: примеры из интернета на Spring Boot 2 и 3 могут отличаться (пакеты, имена стартеров). Если пример не работает — сначала проверь версию, а потом свой код.
- Деньги — `BigDecimal`, не `double`. Время — `java.time` (`Instant`, `LocalDate`, `ZonedDateTime`), не `Date`.
- Тексты ошибок для пользователя — по-русски, в одном месте; исключения не глотаются (никаких пустых `catch`).
- Lombok: если подключил, понимай, что генерируется (геттеры, сеттеры, конструкторы); для сущностей JPA осторожно с `@Data` (`equals` и `hashCode` по всем полям ломают связи). Для курса ООП на Java геттеры и сеттеры лучше хотя бы раз написать руками.
- Именование: классы — `UpperCamelCase`, методы и поля — `lowerCamelCase`, константы — `UPPER_SNAKE_CASE`; имена таблиц и колонок — `snake_case` (в Spring Boot это сопоставляется автоматически).
- Статусы и роли — `enum` в Java; в базе — те же строки с ограничением `CHECK` (расхождение в одной букве превращается в ошибку чтения).

## Spring Data JPA и SQL Server: как договариваемся

- Схему создаёшь ты, T-SQL-скриптами в `db/`; Hibernate лишь проверяет (`ddl-auto=validate`). Так схема — предмет курса БД, а не побочный продукт Java.
- Сложные отчёты — запросы или представления; в Java их читаем через `JdbcTemplate` или `@Query` (это же материал лекции про JDBC и DAO).
- Связи между сущностями (`@ManyToOne`, `@OneToMany`) используем осознанно: следи за ленивой загрузкой и проблемой «N+1» (один запрос на список и ещё по запросу на каждую строку).
- Типы: `datetime2` в базе — `Instant` или `LocalDateTime` в Java; `decimal(12,2)` — `BigDecimal`; `uniqueidentifier` — `UUID`; текст — `nvarchar` (русские буквы).

## Безопасность

- Вход — форма Spring Security; пароли в `staff` хранятся только как BCrypt-хэши.
- Права проверяются на сервере: правила по адресам плюс `@PreAuthorize` на методах сервисов; кнопку «спрятать» мало.
- Фильтр по филиалу — в сервисах (текущий сотрудник известен из сессии). Для курса БД можно дополнительно показать защиту на стороне базы (роли и права SQL Server, представления по ролям); решаем в неделю 2.
- Защита форм от подделки (CSRF) включена по умолчанию: не отключай «чтобы заработало», а разберись, как передаётся токен в Thymeleaf-форме.
- Пароль к базе — в переменной окружения `FITNESSCRM_DB_PASSWORD`, в `application.properties` только `${FITNESSCRM_DB_PASSWORD}`. Файлы с настоящими паролями — в `.gitignore`. Приложение подключается логином `fitnesscrm_app` с правами только на свою базу, не `sa`.
- Персональные данные — по минимуму (ФИО, телефон, e-mail, дата рождения). Данные банковских карт не храним вообще (как и в лабе 2).
- Перед показом: убедиться, что ни одна проверка прав не отключена «на время отладки», а в репозитории нет паролей.

## Соглашения по БД

- Имена: `snake_case`; таблицы во множественном числе (`clients`); внешние ключи вида `client_id`.
- Идентификаторы: `bigint IDENTITY` или `uniqueidentifier`; человекочитаемые коды (`FIZ_01_00001`, `STD_3`) — отдельная колонка `code` с ограничением уникальности, генерируется в базе или в сервисе (решение фиксируем в неделю 2).
- Время: `datetime2` (UTC), даты без времени — `date`.
- Деньги: `decimal(12,2)`, валюта одна (KZT).
- Статусы: текст с `CHECK` или таблица-справочник (в SQL Server нет типа `enum`) — выбор фиксируем в неделю 2.
- Скрипты: `db/migrations/NNNN_описание.sql` (применяются по порядку), `db/seed/` (данные для разработки), `db/tests/` (SQL-тесты: печатают «ожидал» и «получил»). Уже применённый файл не переписываем: исправление — новый скрипт.
- Процедуры и функции: `usp_` и глагол с существительным (`usp_SellMembership`, `usp_RefundMembership`).

## Ловушки (собраны заранее)

- SQL Server Express: по умолчанию принимает только Windows-аутентификацию и не слушает TCP; Spring по паролю подключиться не сможет, пока не включишь смешанный режим и TCP/IP (неделя 1). После включения нужно перезапустить службу.
- Ошибка подключения «The driver could not establish a secure connection» — часто из-за шифрования и сертификата: для учебной базы добавляем `encrypt=true;trustServerCertificate=true` в адрес (на настоящем сервере так делать не надо).
- `datetime2` и `date` — разные вещи; часовые пояса ловят на границах суток и последнего дня срока.
- Деньги в `double` — источник копеечных ошибок.
- Проблема «N+1»: список из 100 клиентов и по запросу на каждого — лучше одно соединение или представление.
- Express: нет агента SQL Server, лимиты на размер базы и память; задачи по расписанию делаем в Spring (`@Scheduled`).
- В репозитории не должно быть паролей: если пароль один раз попал в коммит, строка в `.gitignore` не поможет, нужно менять пароль и чистить историю.
- IntelliJ и Maven: если после правки `pom.xml` IDE ругается на настройки Java, нажми «Reload All Maven Projects»; не выбирай версию Spring Boot со словом SNAPSHOT (так уже было 05.10.2026: из-за неё модуль получил «JVM target 5»).
