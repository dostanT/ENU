# 04. База данных (черновик схемы под SQL Server)

Это заготовка для проектирования, а не готовая схема: SQL пишешь ты, я объясняю и делаю ревью. Предметная область и список таблиц перенесены из прежнего плана; поменялась техника: теперь Microsoft SQL Server (T-SQL), а не PostgreSQL. Всё, что ниже названо «проверено», я запускал; остальное — гипотезы и предложения, которые ты подтверждаешь или меняешь. На 05.10.2026 на SQL Server проверено только одно утверждение (уникальный индекс с условием, см. ниже); остальное — по документации, помечу «проверено», когда прогоню на твоих скриптах.

## Решения, которые нужно принять в неделях 1–2

- Сотрудники и вход. Одна таблица `staff` (сотрудник): логин (уникальный), хэш пароля (BCrypt), ФИО, роль, филиал, признак активности. Роль и филиал лежат рядом с сотрудником. Альтернатива: отдельные таблицы пользователей и сотрудников — гибче, но сложнее.
- Роли. В Java — `enum Role`, в базе — текст с ограничением `CHECK` (или таблица-справочник ролей). Значения совпадают до буквы: `DIRECTOR`, `MANAGER`, `RECEPTION`, `COACH`, `STOREKEEPER`, `ACCOUNTANT`, `MARKETER`, `ADMIN` (имена предлагаю, ты можешь выбрать другие, но в одном месте). Роли «user» из старого приложения здесь нет: решаем, нужна ли «клиентская» роль для киоска.
- Статусы (абонемент, запись, заказ): в SQL Server нет типа `enum`. Мой совет: `nvarchar` с `CHECK` для стабильных наборов, таблицы-справочники для тех, что меняются (виды абонементов, категории товаров).
- Идентификаторы: `bigint IDENTITY` (проще) или `uniqueidentifier`. Для кодов вида `FIZ_01_00001`: объект `SEQUENCE` или счётчик на филиал и тип; пропуски номеров допустимы. Решай сам, но фиксируй.
- Удаление. Бизнес-сущности не удаляем физически, а переводим в статус или снимаем флаг `is_active`; физическое удаление — только тестовых данных.
- Снимок цены. В абонементе сохраняем цену на момент продажи (`price_paid`): иначе смена тарифа испортит историю. Это не нарушение нормальных форм, а осознанный снимок.

## Сущности по модулям (черновик)

Основа (M0):
- `branches` — филиалы: код 01–03, название, адрес.
- `staff` — сотрудники: логин, хэш пароля, ФИО, роль, филиал, активность.
- `membership_types` — виды абонементов: код `STD_3`, вид (UNLIM, STD, BASE), срок в месяцах (1, 3, 6, 12), базовая цена, разрешённые услуги (тренажёрный зал, групповые, бассейн, сауна: либо связанная таблица, либо JSON-колонка), активность.

Клиенты и абонементы (M1):
- `clients` — клиенты: код `FIZ_01_00001`, тип (FIZ, KRP), ФИО, телефон, e-mail, дата рождения, филиал регистрации, дата создания.
- `promotions` — акции: название, вид скидки (процент или сумма), значение, период, виды абонементов и филиалы, к которым применима.
- `memberships` — абонементы клиентов: клиент, вид, филиал, статус, даты покупки, начала и окончания, конец периода охлаждения, токен QR, цена на момент продажи, применённая акция.
- `membership_freezes` — заморозки: абонемент, период, причина.
- `payments` — платежи: клиент, абонемент (может быть пуст для разовых покупок), сумма, способ, статус (ответ эмулятора шлюза), номер квитанции, время, ключ идемпотентности.
- `refunds` — возвраты: платёж, сумма, причина, время.
- `ledger_entries` — проводки: время, счёт дебета, счёт кредита, сумма, аналитика (клиент, абонемент, филиал), источник (платёж, возврат, признание выручки).

Расписание и тренировки (M2, M3, M4):
- `rooms` — залы: филиал, название, вместимость.
- `class_types` — виды занятий: название, категория.
- `class_sessions` — занятия: вид, зал, тренер, начало и конец, вместимость, статус.
- `bookings` — записи на занятия: занятие, клиент, абонемент, статус, время.
- `trainers` — тренеры как подтип сотрудника: код `TREN_GROUP_###` или `TREN_PERS_###`, специализация.
- `personal_sessions` — персональные сессии: тренер, клиент, время, статус, заметки.
- `visits` — посещения: клиент, абонемент или разовая покупка, филиал, время входа и выхода, источник (турникет или ручная отметка), результат.

Склад и закупки (M5):
- `suppliers` — поставщики двух видов (спортпит, инвентарь).
- `goods` — товары: код (категория SPIT или INV плюс номер), название, цена продажи, единица.
- `purchase_orders`, `purchase_order_lines` — заказы поставщикам и их строки.
- `stock_lots` — партии на складе: товар, филиал, дата прихода, количество пришло и осталось, цена закупки (для ФИФО).
- `shop_sales`, `shop_sale_lines` — продажи в клубном магазине.

Уведомления и аудит (M8, сквозное):
- `notifications` — уведомления: вид (истекает абонемент, подтверждение записи), клиент, данные, статус.
- `audit_log` — журнал изменений: таблица, строка, действие, кто, когда, что изменилось.

Проводки. В лабе 2 заданы: при оплате дебет «Расчётный счёт/эквайринг», кредит «Авансы полученные»; при возврате наоборот. Признание выручки по учётной политике логично продолжается проводкой «дебет Авансы полученные, кредит Выручка» по мере срока абонемента — это моё продолжение, в твоих лабах его нет (уточни у себя, нужно ли оно в документах).

## Бизнес-правила -> механизмы SQL Server

В SQL Server не всё, что есть в PostgreSQL: нет ограничения исключения для интервалов, нет типа `enum`, нет массивов и диапазонных типов. Ниже, чем это заменяем (подтверждается на практике, пока это план):
- Один активный (или замороженный) абонемент одного вида у клиента: уникальный индекс с условием (filtered index: `CREATE UNIQUE INDEX ... ON ... (client_id, type_id) WHERE status IN (...)`). Проверено 05.10.2026 на SQL Server 2025 Express во временной базе: вторая открытая запись того же вида отклоняется («Cannot insert duplicate key row ... unique index»), а истёкшая запись того же вида и активная другого вида проходят. Ловушка: индекс с условием требует `SET QUOTED_IDENTIFIER ON`; в `sqlcmd` это флаг `-I` (в SSMS и в драйвере JDBC включено по умолчанию), без него `CREATE INDEX` падает с ошибкой 1934.
- Занятия не пересекаются в одном зале: триггер или проверка внутри транзакции с блокировкой зала. Условие пересечения: начало A < конец B и начало B < конец A.
- Мест не больше вместимости: операция записи с блокировкой строки занятия (`UPDLOCK`, `HOLDLOCK`) и проверкой числа записей.
- Возврат только в период охлаждения и без посещений: операция возврата проверяет оба условия.
- Продажа атомарна (оплата, активация, проводка): одна транзакция (процедура или `@Transactional`) плюс уникальный ключ идемпотентности у платежа.
- Заморозка продлевает срок: операция и таблица заморозок; пересечение заморозок одного абонемента запрещается триггером.
- Признание выручки равномерно по сроку: представление с долей выручки по месяцам.
- Списание по ФИФО: операция берёт товар из самых старых партий.
- Коды сущностей: генерируются в одном месте (база или сервис).
- Журнал изменений: триггеры (в SQL Server есть и готовый механизм «темпоральных таблиц» с историей строк, его можно сравнить с триггерами для курса БД).

## Объектно-реляционные приёмы для курса БД

Не тащим всё подряд: каждый приём должен решать задачу проекта, а не «для галочки». Что в SQL Server реально есть (по документации, не проверено выполнением):
- Типы данных пользователя и ограничения: свои типы на базе стандартных (например, телефон), `CHECK` на форматы.
- JSON: список разрешённых услуг у вида абонемента или гибкие правила акции как JSON-колонка (`ISJSON`, `JSON_VALUE`, `OPENJSON`).
- Подтипы: тренер как подтип сотрудника. Две реализации для сравнения (СРС «наследование и полиморфизм»): одна таблица с колонкой типа и две таблицы со связью один к одному; то же в JPA (`@Inheritance`, SINGLE_TABLE или JOINED). Типового наследования таблиц, как `INHERITS` в PostgreSQL, в SQL Server нет.
- Функции и процедуры как «методы объектов» — `usp_SellMembership`, `usp_RefundMembership`, `usp_CheckIn`, `usp_BookClass` (СРС «бизнес-логика через объектные методы»).
- Триггеры — аудит и служебные статусы (СРС «триггеры»).
- Представления: реестры и отчёты; вертикальная и горизонтальная фильтрация данных по ролям; индексированные представления для тяжёлых отчётов.
- Индексы: кластерные и некластерные, с условием, покрывающие; секционирование визитов по месяцам — как исследование производительности (доступность в Express проверить по документации).
- Мини-проект «объектно-реляционная модель БД для CRM» из списка СРС — это и есть твоя схема; документ описания схемы в конце проекта закрывает его.

## Матрица доступа (гипотеза для недели 2)

Ты уточняешь матрицу, я проверяю её тестами. «Свой филиал» значит: строки, где филиал равен филиалу сотрудника.
- Директор сети: чтение всего по всем филиалам; запись справочников, цен, акций, сотрудников.
- Менеджер по продажам: клиенты, абонементы и платежи по сети (чтение и запись через операции продажи); акции — чтение.
- Ресепшн: свой филиал — клиенты (чтение и запись), продажа, заморозка и возврат абонементов, посещения, запись на занятия, платежи своего филиала (создание и чтение). Не видит выручку сети и финансовые отчёты.
- Тренер: свои занятия и персональные сессии; клиентов — только минимум полей у тех, кто записан к нему; отметка посещаемости.
- Кладовщик: товары, заказы и остатки своего филиала.
- Бухгалтер: платежи, проводки и отчёты по сети — чтение; запись проводок только через операции.
- Маркетолог: акции — запись; статистика — только обезличенные представления (без персональных данных).
- Администратор (IT): сотрудники и справочники; финансовых данных не видит (решение подтверди).
Принцип: доступ по умолчанию закрыт; права открывают ровно то, что записано выше; для всех записей о деньгах прямая запись из страниц закрыта, работает только операция продажи или возврата.

## Представления и отчёты

- Реестры: платежей, абонементов, возвратов (таблица 2 из лабы 2).
- «Скоро истекают», «сейчас в клубе», загрузка залов, посещаемость по дням и филиалам.
- Выручка по филиалам: полученная и признанная; остаток «Авансов полученных»; задолженности.
- Нагрузка тренеров; остатки и «мало на складе»; эффективность акций.
- Удержание клиентов: кто не продлил абонемент после окончания — главная бизнес-цель FitLife.

## Данные и «наследство»

- Для разработки — вымышленные данные (`db/seed/`): 3 филиала, по сотруднику на роль, десятки клиентов, все виды абонементов, пара акций, залы и расписание на несколько недель, склад с двумя партиями. Загрузка — вставка запросами или импорт CSV (`BULK INSERT`).
- Документ «План переноса данных» (СРС о миграции): как настоящие данные FitLife (Excel с расписанием и посещаемостью, журналы турникетов, бумажные журналы записи, справочники 1С) попадут в новую БД: соответствие полей, порядок загрузки, проверки, риски. Данные 1С не трогаем (вне границ проекта), но справочник клиентов можно сопоставлять.

## Нормальные формы

К неделе 10 по каждой таблице записывается короткая проверка 1НФ, 2НФ и 3НФ и оправданные исключения (снимок цены, `price_paid`; JSON-колонка с услугами). Это материал для описания схемы и для лекции о нормализации.
