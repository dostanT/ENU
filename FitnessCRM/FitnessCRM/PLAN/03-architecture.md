# 03. Архитектура

## Общая картина

```
macOS-приложение (SwiftUI)
  Presentation  ->  Domain  <-  Data
                                  |
                        supabase-swift (SDK)
                                  |
   Supabase:  Auth | PostgREST (таблицы и RPC) | Realtime
                                  |
   PostgreSQL:  таблицы, ограничения, RLS, функции, представления, триггеры
```

Это те же 4 уровня, что ты нарисовал в лабе 2 ИСРП («архитектура снизу вверх»):
- Уровень 1, данные — таблицы PostgreSQL (клиенты, абонементы, тарифы и акции, платежи, филиалы и остальное).
- Уровень 2, бизнес-логика — функции БД (правила из таблицы операций: можно ли активировать, как считается цена, когда возможен возврат) и use case'ы в Swift.
- Уровень 3, API — то, что Supabase создаёт сам: PostgREST для таблиц и вызов функций (RPC). Отдельный сервер не пишем.
- Уровень 4, клиенты — macOS-приложение для сотрудников и режим «киоск» (роль «терминала на ресепшн»). Сайт и мобильное приложение из лабы не делаем.
- Отдельно, внешняя система — платёжный шлюз; у нас это экран-эмулятор.

Где живёт логика (главное правило проекта):
- Правило, которое должно выполняться независимо от того, кто и откуда обращается к данным (один активный абонемент вида, вместимость занятия, условия возврата, списание по ФИФО, суммы), живёт в БД: ограничения, функции, транзакции.
- Всё, что про показ и удобство (экраны, форматирование, навигация, локальные подсказки), живёт в Swift.
- Use case'ы в Swift — тонкая прослойка: вызвать нужную операцию, превратить ответ БД в доменную сущность, перевести ошибку в понятное сообщение.

## Слои приложения (уже заложены в проекте)

В Xcode-проекте есть папки `Domain`, `Data`, `Presentation`, `Utils`. Держим их так:
- `Domain`: сущности (структуры Swift без зависимостей от Supabase и SwiftUI), протоколы репозиториев (`Domain/Protocols`), use case'ы (`Domain/UseCases`).
- `Data`: реализации репозиториев поверх `supabase-swift` (`Data/Repository`, `Data/Sources`), объекты передачи данных (`Codable`) и их преобразование в доменные сущности.
- `Presentation`: экраны SwiftUI и ViewModel; по одной папке на функцию (Clients, Memberships, Schedule, Visits, Payments, Inventory, Marketing, Reports, Kiosk), плюс `Root` для входа и навигации.
- `Utils`: конфигурация (ключи), форматирование денег и дат, общие расширения.

Правило зависимостей: Presentation зависит от Domain, Data зависит от Domain, Domain не знает ни о SwiftUI, ни о Supabase. Сейчас в проекте есть `SupabaseRepository` (пустой протокол) и `SupabaseManager` (создаёт клиент): пусть клиент создаётся в одном месте, а репозитории по агрегатам (клиенты, абонементы, расписание и т. д.) получают его через инициализатор.

## Swift: что учесть именно в этом проекте

- В настройках проекта включено `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` и `SWIFT_APPROACHABLE_CONCURRENCY = YES`. То есть типы по умолчанию «живут» на главном акторе. Чистые доменные типы и мапперы имеет смысл помечать `nonisolated` и `Sendable`, а сетевые вызовы делать `async`; предупреждения о конкурентности при работе с SDK читай внимательно.
- macOS-интерфейс: `NavigationSplitView` для бокового меню, `Table` для списков, панели инструментов, горячие клавиши, минимальный размер окна.
- Графики — Swift Charts. QR — CoreImage. Экспорт CSV — стандартный диалог сохранения файла.
- Деньги — `Decimal`, не `Double`.
- Единая модель ошибок приложения с понятными русскими сообщениями; ошибки Supabase переводятся в неё в слое `Data`.
- Решение, как сопоставлять имена snake_case из БД и camelCase в Swift (`CodingKeys` или стратегия декодера), принимаем один раз и одинаково для всех сущностей.

## Supabase: что используем и как

- Auth: вход по e-mail и паролю; сессию хранит SDK. Роль сотрудника читаем из таблицы сотрудников в БД, а не доверяем тому, что прислал клиент.
- Данные: простые чтения и записи — через PostgREST (`from(...)`); всё, что нужно сделать атомарно или что сложнее одного запроса, — функция БД и вызов через RPC.
- Realtime: занятость занятий и список уведомлений (подписка на изменения таблицы); подписку закрываем при уходе с экрана.
- Storage и Edge Functions не используем: TypeScript в проекте не нужен, эмуляции делаем в приложении и БД.

Шпаргалка «Firebase -> Supabase» (ты работал с Firebase):
- Коллекция и документ (Firestore) — таблица и строка (Postgres). Вложенные документы заменяются связями и соединениями (JOIN).
- Правила безопасности (Rules) — политики RLS, написанные на SQL.
- Firebase Auth — Supabase Auth; в политиках текущий пользователь доступен как `auth.uid()`.
- Cloud Functions — функции БД (RPC) там, где нужна транзакция рядом с данными.
- Слушатели (snapshot listeners) — Realtime.
- Индексы Firestore — обычные индексы Postgres, создаются SQL-командой.
- Привычка «денормализовать, чтобы читать быстрее» — здесь наоборот: сначала нормальные формы (3НФ), а ускоряем индексами и представлениями.
- Главное отличие в безопасности: доступ к данным решается политиками на самих таблицах, а ключ в приложении публичный.

## Безопасность

- В приложении только publishable-ключ (он публичный по замыслу). Ключи `secret` и `service_role` никогда не кладём в приложение, репозиторий и чат.
- RLS включаем на каждой таблице сразу при создании: без RLS таблица доступна любому, у кого есть ключ; с включённой RLS и без политик доступа нет вообще.
- Политики проверяем скриптами от лица каждой роли (`db/tests/`), не «на глаз».
- Функции с `SECURITY DEFINER` — только когда без них нельзя, с явно заданным `search_path`; по умолчанию функции выполняются с правами вызывающего.
- Персональные данные — по минимуму (ФИО, телефон, e-mail, дата рождения). Данные банковских карт не храним вообще (как и в лабе 2).
- Перед показом: убедиться, что ни одна политика не отключена «на время отладки».

## Соглашения по БД

- Имена: `snake_case`; таблицы во множественном числе (`clients`); внешние ключи вида `client_id`.
- Идентификаторы: `uuid`; человекочитаемые коды (`FIZ_01_00001`, `STD_3`) — отдельная колонка `code` с ограничением уникальности, генерируется в БД.
- Время: `timestamptz` (UTC), даты без времени — `date`.
- Деньги: `numeric(12,2)`, валюта одна (KZT).
- Статусы: перечисление (`enum`) или `text` с `CHECK` — выбор фиксируем в неделю 2.
- Миграции: `db/migrations/NNNN_описание.sql`, применяются по порядку (через SQL Editor или `psql`). Уже применённый файл не переписываем: исправление — новая миграция.
- Данные для разработки: `db/seed/`; SQL-тесты: `db/tests/` (скрипт печатает «ожидал» и «получил»).
- Функции: глагол и существительное (`sell_membership`, `refund_membership`, `check_in`).

## Тестирование

- SQL: скрипты в `db/tests/`; я прогоняю их локально, ты — в Supabase.

## Ловушки (собраны заранее)

- Песочница macOS: без Outgoing Connections (Client) сеть не работает.
- «Пустой ответ вместо ошибки»: когда RLS отрезает строки, запрос не падает, а возвращает пусто. Если данных «нет» — сначала проверь политики и роль пользователя.
- `date` и `timestamptz` — разные вещи; часовые пояса ловят на границах суток и последнего дня срока.
- Деньги в `Double` — источник копеечных ошибок.
- Много мелких запросов из Swift (N+1): лучше одно соединение или представление в БД.
- Бесплатный тариф Supabase: неактивный проект может «засыпать», есть лимиты — проверяй перед показом.
- Секреты в git: проверяй историю коммитов перед публикацией на GitHub.
- Синхронизируемая папка Xcode: посторонние файлы попадают в цель сборки (см. открытый вопрос в README). Проверено на сборке: `SUPABASE.xcconfig` и все файлы `PLAN` лежат внутри `.app` (Contents/Resources). Лечится снятием Target Membership у этих файлов (как уже сделано для `Info.plist`).
- Файл `.xcconfig`: два слэша `//` начинают комментарий, поэтому `https://...` обрезается до `https:` (проверено: `SupabaseURL = https:` в собранном приложении). Пиши `https:/$()/<ref>.supabase.co`. И это должен быть адрес API проекта (`https://<ref>.supabase.co`), а не адрес страницы проекта в дашборде (`supabase.com/dashboard/project/...`).
- Секретные файлы, которые уже попали в git: строка в `.gitignore` не помогает, если файл уже отслеживается (`git ls-files` покажет). Нужно `git rm --cached <файл>`. Для publishable-ключа это гигиена, а не авария; для `secret` и `service_role` это была бы авария.
