# FitnessCRM — план на 3 месяца

Период: 24.09.2026 — 24.12.2026 (13 недель, ровно 3 месяца). Версия: черновик 1 от 24.09.2026. Это живой документ: каждую неделю он обновляется по новым лабам, лекциям и заданиям.

## Что мы делаем

FitnessCRM — macOS-приложение на SwiftUI для сотрудников сети фитнес-клубов «FitLife» (3 филиала, 120 сотрудников, 40 рабочих мест — это компания из твоих лабораторных ИСРП). Данные, вход и безопасность — в Supabase (PostgreSQL). Проект показывается на двух предметах: «Инструментальные средства разработки программ» (ИСРП) и «Объектно-реляционные СУБД» (БД).

Как читать термины: FitLife — сеть клубов (заказчик из лаб ИСРП), FitnessCRM — программа, которую мы для неё делаем, сотрудники клуба — пользователи, ты — исполнитель (роли «заказчик / исполнитель / пользователь» из лекции 2 ИСРП).

## Договорённости (результат допроса 24.09.2026)

1. Стек: macOS + SwiftUI, бэкенд Supabase (PostgreSQL, Auth, RLS, Realtime), SDK `supabase-swift`. Java в проекте нет.
2. Предметы: только ИСРП и БД. «ООП на Java», «Системное программирование» и «Теория информации» в проект не входят.
3. Код: весь Swift и весь SQL пишешь ты. Мои роли (все четыре, как ты выбрал):
   - веду PLAN и каждую неделю обновляю его по твоим новым лабам, лекциям и заданиям;
   - перед каждым этапом объясняю «что и зачем» простым языком, без готового кода;
   - ревью твоего кода и SQL: нахожу ошибки и объясняю, но не переписываю за тебя;
   - готовлю тексты для ИСРП (ТЗ, требования, описания процессов).
   Диаграммы рисуешь ты в draw.io, по своим решениям.
4. Объём: всё, что описано в ИСРП по FitLife (6 бизнес-процессов и 7 функциональных требований), плюс то, что добавят новые лабы ИСРП. Подробно — в `01-scope.md`.
5. Внешний мир эмулируется: платёжный шлюз, турникеты, уведомления клиентам (список в приложении), самообслуживание клиентов (режим «киоск» в этом же приложении).
6. Роли и филиалы: 3 филиала, роли из оргструктуры FitLife, доступ ограничивается RLS-политиками в БД.
7. БД: для проекта достаточно PostgreSQL (Supabase). Лабы по БД решаются на материале проекта — тоже в PostgreSQL, и я запускаю их по-настоящему, а не только «по документации».
8. Лабы ИСРП — на материале FitLife (как уже сделаны лабы 1–3).
9. Срок: ровно 3 месяца, до 24.12.2026; 15+ часов в неделю. У каждого преподавателя свои сроки — они заносятся в журнал (`07-journal.md`).
10. Твой уровень: Swift и SwiftUI — уверенно; Firebase — работал; Supabase осваиваем в первую неделю.
11. Диаграммы: draw.io.

## Допущения (я так понял, но ты этого прямо не говорил — поправь, если не так)

- Язык интерфейса — русский; названия таблиц, колонок и кода — английские.
- Валюта — тенге (KZT). Деньги хранятся в `numeric`, а не в `float`. Время хранится в UTC (`timestamptz`), показывается по часовому поясу клуба (Asia/Almaty).
- Корпоративные клиенты (тип KRP из справочника клиентов) — только тип клиента: «CRM для корпоративных клиентов» в ИСРП вынесена за границы проекта.
- Один проект Supabase (без отдельных dev и prod). Перед каждым показом — резервная копия данных.
- Git — локальный репозиторий; GitHub по желанию.
- Реальных SMS, e-mail, платежей и турникетов нет.

## Как мы работаем

Ритм недели (недели считаем от четверга, как и сам старт проекта):
1. Первый день недели, 15–20 минут: ты присылаешь, что пришло нового (лабы, задания, сроки). Я разбираю, заношу в журнал и обновляю дорожную карту: что берём в проект.
2. В течение недели: перед каждым этапом я объясняю «что и зачем», ты пишешь код и SQL. Когда кусок готов — присылаешь файлы на ревью.
3. Последний день недели: демо-сценарий недели (критерий готовности из `02-roadmap.md`), галочки в чекбоксах, три строки «что сломалось / чему научился».

Definition of Done (когда задача считается сделанной):
- БД: миграция лежит в репозитории, RLS-политики написаны и проверены скриптом, seed-данные есть.
- Swift: репозиторий, use case и экран; есть состояния «загрузка / пусто / ошибка»; ошибки не глотаются.
- Сценарий недели проходит вручную от начала до конца.
- ИСРП-артефакт (диаграмма или текст) обновлён.
- Сделан git-коммит с понятным сообщением.

Как я проверяю твою работу (честно про границы):
- SQL: запускаю в локальной временной базе PostgreSQL (со своей заглушкой схемы `auth`) — проверка настоящая. Что зависит от самого Supabase (Auth, Realtime, pg_cron, лимиты тарифа), проверить не могу: объясню по документации и помечу «не проверено выполнением».
- Swift: читаю код и собираю проект по-настоящему: `xcodebuild` из Xcode.app запускается у меня по прямому пути (проверено 24.09.2026). Собираю только копию проекта в своей рабочей папке, твои файлы и твой DerivedData не трогаю. Скажу прямо, что собиралось (копия, с какими правками). Запуск приложения и работа с твоим проектом Supabase — всегда за тобой.
- Я не подключаюсь к твоему проекту Supabase и не прошу ключи. Секретные ключи (`secret`, `service_role`) в чат не присылай никогда.

## Открытые вопросы

- Сроки показа и рубежей у ИСРП и БД — у каждого свои, пока неизвестны (заносим в `07-journal.md`, как только появятся).
- Принимает ли преподаватель ИСРП диаграммы из draw.io вместо BPwin, ERwin и Rational Rose (в курсе они Windows-only)?
- Корпоративные клиенты (KRP): достаточно типа клиента или нужны минимальные договоры?
- Нужен ли no-code веб-клиент на AppMaster (зависит от того, что придёт в последних лабах ИСРП)?
- Нужен ли репозиторий на GitHub для показа преподавателям?
- Где хранить PLAN: сейчас папка лежит внутри синхронизируемой папки Xcode-проекта (`FitnessCRM/FitnessCRM/PLAN`). Xcode сам включает файлы из такой папки в цель сборки, то есть .md (а позже .sql и .drawio) могут попасть в ресурсы приложения. Варианты: перенести PLAN, `db` и `docs` на уровень выше (рядом с `FitnessCRM.xcodeproj`) или снять галочку Target Membership у этих папок. Решаем в первую неделю.
